# 第 95 轮：真正的启动崩溃原因 —— 抓取"起步"没有限速（build95）

你三次尝试的结果很关键 ✓：**第一次进主页正常**（仅两张封面没出来 ✓）→ **进更多就崩** ✗；

## 一、日志给出的决定性事实

```
HOME apply: ENTER attach 36 rows
IMG: fetching …   （七行，全部在同一秒）
<日志在半行中间被撕裂；没有任何一张封面安装完成>
```

**没有 `IMG: installed`** ✓ → 说明**死在下载阶段** ✓（不是上传 ✓）；
**没有崩溃报告** ✓ → 是被**系统杀掉**（资源耗尽 ✓），不是异常崩溃 ✓。

## 二、根因：我的节流只挡住"安装"，挡不住"起步"

我在 `build89` 加的节流是**"距上次**安装**不足 120 ms 就不启动新的下载"** ✗ ——
**而启动时还没有任何安装发生过** ✓ → `g_lastInstallMs = -1000` ✓ → 节流**完全敞开** ✗✗
→ 主页一次性挂上 36 行 ✓、每个格子同时伸手 ✓ → **十几个下载同时起飞** ✓
（每个抓取过程中最多持有 **1.5 MiB** 缓冲 ✓ = 十几个缓冲同时存在 ✓）→ 这台机器的固定内存预算撑不住 ✓✓。

`build92` 也有同样的漏洞 ✓，只是你那次没撞上 ✓（这正是"偶发"的原因 ✓）。

## 三、修法：**抓取起步也限速**（每 90 ms 最多放行一个）

```
HG_IMAGE_START_GAP_MS = 90 ms     起步闸门
HG_IMAGE_INSTALL_GAP_MS = 200 ms  安装闸门（保留）
image.threads (16)                在飞行上限（保留）
```

于是真实并发**由网络速度决定**（大约 2～5 个 ✓），而不是"一上来十六个" ✗。
**顺带还解决你之前提的排布问题** ✓：封面现在是**按格子顺序、一个一个请求**的 ✓ →
出现顺序天然就是**从第一排往下** ✓，不再由"谁先下载完"决定 ✓。

# 第 53 轮：低画质解码 + 解码缓存（C1 / C3）（build53）

这两行**直接对着 §2.4 的 1080p 卡顿**：交接文档记的根因是"这个 App 走的是 mpv 的**软件输出路径**，
每帧都要过 CPU"，而这两项正是软件解码路径上唯一真正的两个成本旋钮。

---

## 一、C1 低画质解码：默认**关**，理由写在行名上

打开时设三个 mpv 选项（这就是 mpv 里"低画质解码"的实际含义）：

```
vd-lavc-fast=yes            跳过规范里可选的部分
vd-lavc-skiploopfilter=all  非参考帧不做去块滤波
vd-lavc-skipframe=nonref    直接不解码非参考帧
```

**代价是画面质量，换的是解码时间。** 所以：

- **默认关** —— 一个为了流畅而**悄悄降低画质**的播放器，比一个卡顿但说清原因的更糟；
- 设置行叫 **"Low-quality decode"**（不是 "Smooth"）：不能让人一不小心打开它；
- **三个选项各自记返回码** —— 一个被拒绝的选项名和生效的选项长得一模一样，
  这是本项目反复遇到的失败模式。

## 二、C3 解码缓存：阶梯 0/32/64/128/256 MiB，**0 = 不动 mpv 的默认**

- 前向缓冲 `demuxer-max-bytes`，后向缓冲 `demuxer-max-back-bytes` = 前向的一半
  （后向缓冲让**往回拖**不用重新取流；取一半是 mpv 自己的建议，代价最小）。
- 阶梯与"取最近值"的规则在 `hg_ctl` 里，**新增 11 项测试**：
  0 是"默认"、两端**夹紧不回绕**、cfg 里写 100 会落到 128、写 1 会**落到默认而不是更大的缓存**
  （不能让一个没写对的值悄悄变成比用户要求更大的缓冲）。
- 日志会把两条缓冲的实际值与返回码都打出来：
  `PLAYER: decode cache: forward=128MiB (rc=0) back=64MiB (rc=0) [build53]`

## 三、为什么标"需要重启"，这不是偷懒

这两项是 **mpv 的 OPTION**：mpv 在**第一个文件之前**取它们，软件解码路径在加载文件时就建好滤镜链与缓冲。
**事后设置不是同一件事**。所以它们从 `hongguo.cfg` 在 `setupMpv` 时读取，设置界面如实标"需要重启"——
这是事实，不是限制。

## 五、请真机确认

1. 设置 → **播放设置** → 最下面两行：**Low-quality decode**（yes/no）、**Decode cache**（0/32/64/128/256）。
2. **先只改 Decode cache = 128**（不动画质）→ 重启 → 播一集 1080p：
   日志有 `PLAYER: decode cache: forward=128MiB (rc=0) back=64MiB`，看卡顿是否减轻。
3. 若仍卡：再把 **Low-quality decode = yes** → 重启 → 画面应更糊但更流畅
   （日志有三行 `low-quality decode: vd-lavc-… -> rc=0`）。**这一项是用来做取舍实验的**，
   确认结论后可以长期留关。
4. 回归：1080p 以下的清晰度不受影响；改回 `player.cache.mb=0` 就恢复 mpv 默认。

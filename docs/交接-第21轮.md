## 1. ★ 第一件事：一次请求拿全（去掉每集第二次请求）

### 为什么现在做得了

build156 换上的新接口是**单条**的 `/novel/player/video_model/v1/`，**一次响应里就带着整条 `video_list`（五档全给）**。

**而"计划"和"档位"读的本来就是同一个内层文档**，只是走了两个不同的解析器：

```
一次 POST 的 body
  └─ hg_play_model_inner()            解出内层 JSON 字符串（data.video_model，双重编码）
       ├─ hg_play_plan_from_model()   → 计划（选一条源）      ← fetchPlayPlan 用
       └─ hg_api_parse_video_model()  → 全部档位（建菜单）    ← fetchQualityLadder 用
```

**所以"一次拿全"不需要新接口、也不需要新解析**，只需要让这两条路**共用同一次 POST 的那份 body**。

**但现在的代码仍然发两次请求**：

```
player_view.cpp  fetchPlanOnPreferredTier → Client::fetchPlayPlan         ← 请求 1（拿到计划）
                  startQualityLadder       → Client::fetchQualityLadder    ← 请求 2（拿菜单档位）
```

### 真机上看得见的代价（第 21 轮实测）

```
19:48:45 PLAYER: mpv started, plan = 1080p 1920x1080  codec=bytevc1  CENC key derived
19:48:46 QUALITY: ladder ready (1 tiers, first '1080p  ·  HEVC')     ← 同一次会话、前两集都是 5 档
```

服务端**仍会偶发少给档位**。两次独立请求时，谁拿到"少档位"的那份谁就退化 → **菜单显示与实际播放可能不一致**
（这正是交接 §5 老早写下的隐患）。**共用同一次响应之后，两者来自同一份数据，不可能再对不上。**

### 落点与做法

- **改 `hg_client.cpp`（只改这里）**：加一个入口，比如
  `fetchPlayPlanWithLadder(episodeId, plan, tiers)` —— 一次 POST，然后把**同一份** `g_page` 分别喂给
  `hg_play_plan_from_model`（或直接复用 `hg_play_model_inner` + `hg_api_parse_video_model`）。
  两条解析路径**必须都走现有函数**，不要另写解析（这是本项目反复强调的：诊断/新路径另写一套，会在真链路坏了时还是绿的）。
- **`fetchQualityLadder` 不要删**：换档（`fetchPlayPlanForSource`）**仍然要重新取**——URL 是限时签名的，
  缓存的会过期。只有**开播那一次的菜单**应该来自计划的那一份响应。
- `player_view.cpp`：`startQualityLadder` 现在自己发请求；改成"计划成功时把 tiers 一起交出来，直接种菜单"。

### 怎么验（**注意：现在日志里看不出发了几次 POST** —— 先补一行日志，别靠猜）

1. **先加一行可数的日志**：在 `hg_client.cpp` 的 `postVideoModel()` 与 `fetchPlayPlan()` 里各打一行，
   例如 `QUALITY: video-model POST (plan path)` / `(ladder path)`。
   **现在两条路都不打请求行** ✗，所以"只发了一次"这件事**无法从日志证明** —— 这本身就是第一个要补的东西。
2. **再验结构**：开播路径里不应再出现 `Client::fetchQualityLadder`（`grep` 可见）；它只应留在换档那条路上。
3. **真机**：菜单 5 档、"正在播的那一档"与 `plan = …` 一致；日志里**每集只出现一行** POST;
   `PLAYCHECK` 自检仍然全绿（§3）。
4. 顺带**消掉一个已知症状**：`QUALITY: ladder ready (1 tiers…)`（§上面 19:48:46 那次）应当不再出现 ——
   因为菜单不再单独取一次，就没有"单独那次被少给档位"的机会 ✓。

> **也可以不做这个，改做 §5 里别的**（比如 ⑤ 续播、④ 触屏拖动、⑥ 剩余中文）——但 §1 是唯一
> "少一次请求 + 消掉一类偶发不一致"的，而且改动被限制在 `hg_client.cpp` 一处。

## 6. 工作方式铁律（这几轮踩出来的，**违反一次浪费整轮** ✗）

1. **改文件用 `read` + `edit` 工具**；**不要用 PowerShell 字符串替换**（`\r\n`、中文、撇号会失配 ✗）。
2. **每改一处立刻 grep 核对** ✓，全部通过**才**构建 ✓。
3. **构建必须零警告**；**主机测试必须 0 失败**（`app\src\tests\run.ps1`）。
   ⚠️ **测试挂了先看是不是"策略变了"**：本轮改选档策略，`video_model_h264.json` 那条派生夹具就红了 ——
   **那是测试在正确地拦住我**，要按新策略改断言，**并且把它原本要证明的性质用另一条断言补回来**（我补的是
   "把 1080p 那条改成 bytevc2 后仍能从 h264 建出计划" ✓）。
4. **部署后必须 `get` 回来比对 SHA-256** ✓（NRO 与 NSP 都比）。
5. **绝不在 `draw()` 里改视图树** ✗（增删/重建子视图）。要"状态灯"这类东西，**让视图每帧读状态**，
   不要用回调去动视图（`hg_status_dot.hpp` 开头写了为什么）。
6. **先量再改** ✓：本轮我**误判过一次**（说"走软件渲染"），被 cfg 与日志否掉 ⇒
   **顺序永远是 取证据 → 改 → 再看证据** ✓。
7. **一次只交一件** ✓，并明确说"这一版的唯一变量是什么" ✓。
8. ⚠️ **PowerShell 管道的 exit code 会骗人**：`powershell … 2>&1 | Select-Object -Last N` 曾在
   **命令实际成功**时报 `[exit code: 1]`（我单独测子进程拿到 0 ✓）。要看退出码就用 `*> file` 再读文件，
   或单独跑一次取 `$LASTEXITCODE` ✓。
9. ⚠️ **FTP 工具的 `-Save` 会写 `<host-tools-dir>\…`，在沙箱下会被拒** ✗。改成显式传参：
   `-Ip 192.168.1.x -Cache <ascii-scratch>\_switchcache`（用完把它删掉）✓。
10. ⚠️ **`$env:TEMP` 每次 pwsh 调用都可能不同**（本轮实测：`…\Temp\dsh-CDPGT0` → `…\Temp\dsh-yQ7kuQ`），
   而且**旧的临时目录会被清掉** ✗ —— 所以**不要把上一步写进 `$env:TEMP` 的东西当作下一步一定能读到**。
   要跨调用留存就把中间产物写进仓库（`out\`）或一个固定路径 ✓。我本轮就因为这条，回头想核一个数字时
   发现日志已经没了，只能重跑一遍 ✓。

## 1. `definition` 全档位扫描（`web-playinfo-sweep.mjs`，本机 2026-10-16）

| definition | 结果 |
|---|---|
| `360p` | ✅ OK — video `media-video-avc1` + audio `media-audio-und-mp4a` |
| `480p` | ✅ OK — 同上 |
| `540p` | ❌ `400 {"error":"protected_playback_unavailable"}` |

**结论 1**：**没有任何 definition 返回渐进式 mp4** —— 活的档位（360/480/720）**全是 DASH 双路**
（视频一路、音频一路，各自 `format=dash`）。
**结论 2**：**1080p 及以上在这个接口上没有**（不是我们请求写错了；网页自己的 `720p` 也是上限）。
⇒ 这与旧 `video_model` 接口"1080p=bytevc1"完全不同；**新接口封顶 720p**。

## 3. DASH 双路的真实属性（这决定 mpv 怎么喂）

对 `720p` 的 `play_info`，把 `main_url` 与 `audio.main_url` 各拉 `0..index_range[1]`：

```
VIDEO: 206 video/mp4  bytes 0-1824/31731824   ftypisom...
        box: ftyp@4 moov@44 encv@477 sinf@675 schm@695 tenc@723 sidx@1281
AUDIO: 206 video/mp4  bytes 0-1824/3581320    ftypisom...
        box: ftyp@4 moov@44 enca@473 sinf@548 schm@568 tenc@596 sidx@1031 moof@1579
```

- 两路**都是 CENC 加密的 fMP4**（`encv`/`enca` + `sinf` + `tenc`）；
- **加密是真的，不是"只打标记"**：拉 `first_moof_range`（`1825-6927`）实测里面是
  `moof` → `traf` → `senc`（**每样本 IV 表**）+ `saio`/`saiz`（辅助信息偏移/大小）+ `trun`/`mdat`。
  `senc` 原始字节里能看到每条目 8 字节 IV，例如 `5ee61985ae92668a`、`...0000020c`…
  ⇒ **样本数据是 AES-CTR 加密的，没有正确的内容密钥只能得到花屏/黑屏且不报错**；
- `tenc` 原始字节：`0000002074656e63 00000000 00000001 10 6822c083f8818b957fb273630002ebeb …`
  ⇒ version 0、`default_isProtected = 1`、`default_Per_Sample_IV_Size = 0x10`(16)、
  **`default_KID` = `6822c083f8818b957fb273630002ebeb`**，与 `play_info.kid` **逐字节相同**；
- `schm` 的 scheme 是 **`cenc`**（`63656e63`）⇒ **就是现有 `hg_cenc` 实现的那套**，不需要新算法。

**结论 4**：**mpv 无法直接播这两条 URL**——单条 URL 只是一个"视频轨"或"音频轨"，
而且都被 CENC 加密。必须**同时**给出视频+音频，并且**同时**给出解密密钥。

## 4. `player_access_key` **不是** 16 字节内容密钥（关键否定证据）

```
play_info.kid               = 6822c083f8818b957fb273630002ebeb
play_info.player_access_key = "o+Z3xjvaIJRt2k34VeFO+FTiGsI62BvBUthzkm2PcpA5jyOeng=="
                              ^ 52 字符 base64
base64 解码 -> 37 字节: a3e677c63bda20946dda4df855e14ef854e21ac23ad81bc152d873926d8f7290398f239e9e
```

- 长度 **37 字节**，**不是 16**；也不是 32 个 ASCII 十六进制字符。
- 现有 `hg_spade_content_key()`（`hg_cenc.h`）要求输入是 **base64 → 恰好 32 个 ASCII hex 字符**，
  才产出 16 字节内容密钥。**`player_access_key` 不满足这个形状**。

**结论 5**：**旧接口的 `spade_a` → `hg_spade_content_key()` 这条路在新接口上不适用**。
`player_access_key` 是**另一种密钥材料**（形状像信封加密的密钥块）。

> ✅ **已解决（见 §5.9）**：它的推导方式**已经挖出来了**，是网页纯 JS 的 `openBox()`，
> **可在 C++ 里原样重实现**，不需要 DRM、不需要任何离线秘密。
> 本文保留下面这段"当时未知"的记录，是为了留住**否定的证据**（试过哪些假设不成立），
> 但**不要再按"拦路石"来理解它**。

## 5.5 ⭐ 最重要的一条：`play-info` 的失败是**间歇性**的，**重试就能成功**

这是整轮调查里最有价值的发现，它**改写了上面 §1/§2 的悲观结论**。

### 证据 A：同一个请求，重复发，结果不同

对**同一个 vid、同一个 definition**，连发 8 次**完全相同**的请求：

```
ep[16] 720p: 403 403 403 200 403 403 403 200     ← 第 4、8 次成功
ep[ 9] 720p: 403 403 200 403 200 200 200 200     ← 第 3 次起成功
ep[47] 720p: 403 403 200 403 403 200 200 200     ← 间歇
ep[60] 360p: 403 ×8                              ← 真的锁了
ep[50] 360p: 403 ×8                              ← 真的锁了
```

⇒ **`403 protected_playback_unavailable` 不是"这台设备没权限"的稳定判定**，
而是**负载均衡/边缘节点抖动**：同一个 URL 命中不同后端，有的放行有的不放。
**所以"重试"不是绕过风控，而是对这个接口不稳定性的正常应对。**

### 证据 B：`definition` 也会影响成败（同一集）

`ep[16]`（vid `7503780594816404542`）逐档试：

```
aid=8662 720p      -> 403
aid=8662 360p      -> 200  ← 换档位就成功
aid=8662 no-def    -> 403
aid=8662 extra     -> 403
aid=1 / aid=2906   -> 403   (aid 不是关键)
+device_id         -> 403   (设备参数不是关键)
```

### 证据 C：加了重试之后，可达性从 26% 升到接近全部（**直到第 50 集**）

每个 "definition" 最多重试 10 次，按 `720p → 480p → 360p` 依次降档：

| 集 | 结果 |
|---|---|
| 0 | ✅ `720p`，**第 1 次**就成 |
| 9 | ✅ `720p`，第 1 次 |
| 16 | ✅ `720p`，第 4 次 |
| 30 | ✅ `720p`，第 3 次 |
| 46 | ✅ `720p`，第 4 次 |
| 50 / 60 / 75 | ❌ **30 次全败**（三个档位各 10 次） |

### 证据 D：边界**正好在第 50 集**（本剧 76 集）

逐集二分（每集最多 6 轮 × 2 档）：

```
ep[44] reachable=true
ep[45] reachable=true
ep[46] reachable=true
ep[47] reachable=true
ep[48] reachable=true
ep[49] reachable=true
ep[50] reachable=false   ← 边界在这
ep[51] reachable=false
```

⇒ **前 50 集免费（重试可达），第 51 集起是真锁**。
这与"短剧前 50 集免费、之后要登录/看广告"的常见商业模式**完全吻合**，
也解释了为什么**没有任何 definition 能救回第 51 集以后**。

### ⚠️ 对既有结论的修正

- §1 里 `1080p → 400` 是**稳定的真结论**（无重试价值，重试也 400）；
  但 `360p/480p/720p → 200/403` 是**抖动的**，**必须重试**。
- §2 里"公开兜底只有 4/8 集"**也是抖动的**：重测同一批集号，
  原本 404 的 `ep5/ep9/ep40/ep60` 有一次回 `200(7615079)` 等（带 `Origin` 头时甚至更多）。
  ⇒ 公开兜底的真实覆盖率比第一次测的高，但**仍然覆盖不到第 51 集以后**，且**只有 360p**。

### ⇒ 实现的正确方向（**已由数据确定**）

1. **主路**：`play-info`，**带重试**（建议 4–6 次、间隔 300–500 ms），
   档位 `720p → 480p → 360p` 依次降级；**成功即停**。
2. **第 51 集以后**：接口明说不可用 ⇒ **要明确告诉用户"该集需登录/付费"**，
   而不是报 `rc=-5` 这种"解析失败"，更不能无限重试。
3. `1080p`：**不要试**（稳定 400）。

## 5.9 ⭐⭐ 密钥问题**已解决**：`player_access_key` 是**纯 JS 可推导**的，不需要 DRM

这一条推翻了本文 §4 的悲观结论（"那是真正的拦路石"）。**已端到端验证**。

### 结论

`play-info` 的 `player_access_key` 经网页自己的 `openBox()` 解出一个 **16 字节 CENC 内容密钥**。
**没有 Widevine/EME、没有 RSA/ECIES、不需要任何离线秘密。**

决定性证据：网页自己那行配置里写着 **`useEME: false`**
（chunk `t.78fb905b21.js`）：

```js
DASHPlugin:{vid:I.vid, playInfoType:"TOP", secretKey:I.player_access_key,
            useEME:!1, useUnionInfoDRM:!1, defaultFormat:"dash", ...}
```

⇒ `m.ad3954075c.js` 里那套 `requestMediaKeySystemAccess`/`widevine` **是死代码**，
走的其实是纯 JS 的 `XGSecretKey → openBox()`。
（那个 chunk 里**还有**一套真的 `KekHelper`：RSA-OAEP-2048/SHA-256 + `localStorage["player_keypair"]`，
返回 `drmKeK` —— **但那条路由由 `useUnionInfoDRM`/`drmKeyToken` 控制，我们的响应两个都没给**，
**不要走那条路**。）

### 算法（逐字取自 bundle，函数名 `openBox`/`mh`，模块 `od`）

```js
// 辅助
Qh = e => { let t=0; for(t=0; e!==0; t++) e &= e-1; return t };   // popcount
hh = (e,t) => e ^ t;
ph = (e,t,n) => String.fromCharCode((e + Qh(t) + n) & 255);
fh = (e,t,n) => String.fromCharCode((e - Qh(t) - n) & 255);

function openBox(e, t) {              // e = player_access_key 的 base64 解码结果，当作「二进制字符串」
  t = t || e.length;
  // 1) 头：前 3 字节异或后减 '0' 得到 methodLen；再从尾部异或出 method 标签
  const methodLen  = (e[0].charCodeAt(0) ^ e[1].charCodeAt(0) ^ e[2].charCodeAt(0)) - 48;
  const convertLen = t - methodLen - 1;
  const mArr = new Array(methodLen);
  for (let n = methodLen; n > 0; n--) {
    mArr[methodLen - n] = String.fromCharCode(
      e[t-methodLen-2].charCodeAt(0) ^ e[t-methodLen-1].charCodeAt(0) ^ e[t-n].charCodeAt(0));
  }
  let convertKey = e.substring(1, convertLen + 1).split('');
  const method = mArr.join('');

  // 2) 通道选择：11/appdevice/app_v2 -> 0，其余 -> 1
  const lane = (method === '11' || method === 'appdevice' || method === 'app_v2') ? 0 : 1;

  switch (method) {
    case '11': case '22': case 'appdevice': case 'webdevice': {
      // 双通道滚动异或（种子 85 / 250），再做位置相关的 ±21（&255）
      let rLane = 85, aLane = 250;
      for (let o = 0; o < convertLen; o++) {
        const l = convertKey[o].charCodeAt(0);
        let v;
        if (o % 2 === 1) { v = rLane ^ l; rLane = l; }   // 奇数位用 r 通道
        else             { v = aLane ^ l; aLane = l; }   // 偶数位用 a 通道
        convertKey[o] = lane === 0 ? fh(v, o, 21) : ph(v, o, 21);
      }
      break;
    }
    default: throw new Error('unsupported method tag');
  }

  // 3) 去掉首位「长度标记」字符，剩下的就是密钥
  const first  = convertKey[0];
  const marker = (first>='0'&&first<='9') ? first.charCodeAt(0)-48
               : (first>='a'&&first<='z') ? first.charCodeAt(0)-97+10 : 255;
  const s = convertLen - marker - 1;
  const d = new Array(s + 1); d[s] = '';
  for (let c = 0; c < s; c++) d[c] = convertKey[c + 1];
  return d.join('');
}
```

### 实测（本机，2026-10-16）

```
player_access_key : o+Z3xjvaIJRt2k34VeFO+FTiGsI62BvBUthzkm2PcpA5jyOeng==
base64 解码       : a3e677c63bda20946dda4df855e14ef854e21ac23ad81bc152d873926d8f7290398f239e9e (37 字节)
method tag        : "22"   methodLen=2   convertLen=34
openBox() ->      : 86c22eed79003130e78191b09b7588e5      ← 16 字节 CENC 内容密钥 ✅
```

**三重验证**：
1. 我们的独立重实现 **与网页 bundle 里真正的 `openBox()` 输出逐字节相同**
   （`cap-test-openbox.mjs` 在沙箱里加载真 bundle 调用其自身函数）；
2. **端到端解密**：拉真实 DASH 分片，解析 `moof/traf/tfhd/trun/senc`，
   AES-128-CTR 按 subsample 解密 ⇒ **150/150 样本有效，invalid=0**；
3. 解开后的码流**结构正确**：AVCC 长度前缀解析出 NAL 单元
   **type 1（非 IDR 片）×59 + type 5（IDR 关键帧）×1**，正是真实视频的形状
   （`video-decrypted.h264`，745,758 字节）。
   音轨用**同一个密钥**（KID 相同）。

⇒ **C++ 可以实现，不必放弃机内解密。**

## 5.10 C 步的答案：音频轨**确实可以**用 mpv 原生 `audio-add` 加（已核实，非推断）

### 客户端支持：mpv **0.36.0**，命令表里有 `audio-add`

```
libmpv.a 里的版本串: "mpv 0.36.0  GCC: (devkitA64 ...)"
命令名字符串: audio-add ✓  audio-remove ✓  audio-reload ✓  loadfile ✓
```

### 参数形式（mpv 0.36.0 官方手册，原文）

```
audio-add <url> [<flags> [<title> [<lang>]]]
    Load the given audio file. See ``sub-add`` command.
```

**`flags` 是方括号 ⇒ 可选。**`sub-add` 那一条给出取值：

```
<select>   Select the subtitle immediately (default).
<auto>     Don't select the subtitle.
<cached>   Select the subtitle. If a subtitle with the same filename was already added, ...
```

⇒ **不传 flag 就是 `<select>`（默认即选中）**，所以传 `<url>` 一个参数就够，
**不需要**再猜 `select` 的拼写（尾部参数拼错会让 mpv 拒绝整条命令，反而丢掉音频）。

### 音频流本身**可以被独立打开**（这是 `audio-add` 能成立的前提，实测结构）

拉音频的 `init_range`（`0-1026`）分析它自己的 `moov`：

```
ftyp x1  moov x1  mvhd x1  trak x1  mdia x1  minf x1  stbl x1  stsd x1
hdlr x2   →  handler_type = "soun"     ← 是音轨
mp4a x2   esds x2   enca x1            ← 未加密入口 + 加密包装
mvex x1   trex x1   sidx x1            ← 完整的 fragmented mp4 头，且自带索引
```

⇒ 音频**是一个完整、自描述、可单独打开的 fMP4**（不是只能配合视频的分片），
`accept-ranges: bytes`，所以 `audio-add` 有东西可开。

### 密钥：音频与视频**共用同一个**

```
video kid = 6822c083f8818b957fb273630002ebeb
audio kid = 6822c083f8818b957fb273630002ebeb   ← 相同
audio player_access_key == video player_access_key   ← 逐字节相同
```

所以**不需要第二把密钥**：`demuxer-lavf-o decryption_key=` 已经在 `loadfile` 之前设好，
对两条流都生效。

**解密实测**：用同一把密钥按 `senc` 解音频样本 → `plausible=7 implausible=0`
（子代理的脚本只解析出 215 条中的 7 条 `senc`，所以那**不是**完整证明；
但它足以说明**密钥是对的**，与视频那 150/150 的完整证明互相印证）。

### C 步的结论一句话

**走原生 `audio-add`，不合成 DASH manifest。** 依据是上面三条实测：
mpv 支持、音频可独立打开、密钥共用。

> 若真机上 `audio-add` 仍返回负值，日志里会有 `PLAYER setupMpv: audio-add rc=<n>` 原文 ——
> 那时再回报并考虑 manifest，**不要先自造**。

### 关于 C 的两条路（**必须先量，再选**）

1. **合成一个本地 DASH manifest**（`mpd` 指向两条远程 URL + `init_range`/`index_range`），
   让 ffmpeg 的 dash demuxer 自己拉两路；密钥经 `--demuxer-lavf-o decryption_key=`
   传（**这是现有代码已经在用的机制**，`player_view.cpp` 有 `demuxer-lavf-o` 的先例）。
2. **两条流分喂**：视频用 `loadfile`，音频用 `audio-add`。
   项目里已有"两个音频流 = 两个 loadfile"的教训（`player_view.cpp:2060` 附近注释），
   **风险更高**，但如果 (1) 不成，这是退路。

> ⚠️ **C 的坑**：`sidx` 是分段索引，两路的时间轴要能对齐；`init_range` 必须按 Range 拉，
> 否则 ffmpeg 会把整个 31 MB 当 init 段读。
> **不要**在没量清这两点之前改 `renderCtx`/`setupMpv` 的结构。

- ❌ **缺字体/资源** —— smoke 的 `Label` 需要字体且正常

### 剩下的两类嫌疑

`build-hongguo.ps1 -SmokeTest` **排除的是 `.c` 文件和 `hg_client.cpp`**，而 `smoke_main.cpp` 只 push 一个裸 `brls::Label`；真应用 push `HomeActivity`。**差异只有两处：**

| 嫌疑 | 依据 |
|---|---|
| **A. `createContentView()` 里的分离线程**（`home_activity.cpp:125`） | smoke 没有线程；它跑在主循环开始前；`std::thread` 创建失败会抛异常 → abort → **无提示崩溃**，与现象吻合 |
| **B. 视图构造**（`RecyclerFrame` / `HomeCell` / 多个 `Label`） | smoke 只有裸 `Label` |

### 实验（一次一行代码，一次一趟主机）

**第一版：完全不联网、不起线程**，只建视图并把状态写在屏幕上。

- **能启动** → 崩在 A（线程/网络）→ 下一版改成**同步抓取**（同时天然修掉缺陷 #3）
- **仍闪退** → 崩在 B（视图构造）→ 下一版退到最简视图再逐步加

编辑位置：`app/hongguo/home_activity.cpp` 的 `HomeActivity::createContentView()`（第 100–149 行），把 `std::thread(...).detach();` 整块换成一句写死在 header 上的状态文本。

> `detail_activity.cpp` 也有同样的线程模式，但它的抓取发生在**按键选择之后**，不是启动路径，**先不要动它**。

## 五、环境约束（下次一定会再撞上，全部实测过）

| 限制 | 规避 |
|---|---|
| **msys2 全部二进制起不来**（`couldn't create signal pipe, Win32 error 5`，沙箱禁命名管道） | `cmake`/`make`/`ninja`/`sh`/`git` **全部不可用**。要么每次提权，要么**用手写脚本复现构建图**（`build-borealis.ps1` 就是这么做的） |
| 工作区路径非 ASCII（`<repo>`） | 一律在 `$env:TEMP` 的 ASCII 暂存目录里编译，产物回拷。`stage-borealis.ps1` / `build-switch-test.ps1` 都内置了 |
| PowerShell 5.1 按 GBK(936) 解析无 BOM 的 UTF-8 `.ps1` | **`.ps1` 一律纯 ASCII**，非 ASCII 路径走参数 |
| `pwsh` 不在 PATH | 用 `powershell` |
| **`writeFileSync(..., 'ascii')` 会毁掉非 ASCII** | Node 的 `'ascii'` 把每个码元按 7 位截断，**中文字符的低 7 位可能是 `"` 或 `\`，会注入 JSON 流破坏结构**。生成含非 ASCII 的文件**必须用 `'utf8'`** 或写成转义。**这个坑在项目里犯了三次** |
| `elf2nro` 参数 | **`--romfsdir=<目录>` 才是从目录构建**；`--romfs=<镜像>` 是嵌入已构建的镜像。传目录给 `--romfs` 报 `Failed to open input romfs!` |
| `pkg.devkitpro.org` 被 Cloudflare 403 | 预编译包从 wiliwili release 取 |
| `raw.githubusercontent.com` 被墙 | 走 GitHub Contents API |
| `code.videolan.org` 有 Anubis 反爬 | 用 GitHub 镜像 `haasn/libplacebo` |
| `git` 报 `schannel: SEC_E_NO_CREDENTIALS` | 加 `-c http.sslBackend=openssl`；`git config --global` 会因权限失败，只能用 `-c` |
| **`libborealis.a`（126.7 MiB）只活在会话临时目录** | 换会话就要重跑 `stage-borealis.ps1` + `build-borealis.ps1`（~100 秒）。**建议归档到 `third_party/`**——和当初"ELF 只活临时目录导致 NSP 配方失效"是同一类问题 |
| 主机地址 | `192.168.1.x:5000`，用户 `<ftp-user>`，密码 `<ftp-password>`（见 `<host-tools-dir>` 下的本机 FTP 配置）。**sys-ftpd 被暂停时端口不通**，主机上按 `PLUS+MINUS+X` 可恢复 |

## 六、这一会话修过的关键缺陷（避免重犯）

1. **`hg_medusa.c` 的 `concat[80]`** —— 照测试向量的短 URL 定尺寸，而真实查询串是 555 字符 → **每次真实请求都返回 0**。修成按调用方最大 URL 定尺寸。
2. **`HG_REQ_MAX_HEADERS` 是 16，POST 需要 17** —— 视频模型请求永远失败。
3. **`hg_api_parse_home` 在 NULL 校验前解引用 `count`** —— 我只传了 `NULL` → 写地址 0 → 真机 `2168-0002`。库侧全部 15 处写入点都加了保护 + 6 条回归测试。
4. **两段 553/570 字节的简介 vs 512 字节缓冲** —— 严格解码失败 → 单行错误升级成**整页拒绝**。加了 `hg_json_string_fit()`：**展示文本截断，身份（`series_id`）不截断**。
5. **`elf2nro` 没带 romfs** —— borealis 从 `romfs:/shaders/*.dksh` 加载着色器，缺了会**一笔都画不出来且不报错**。三个 `.dksh` 预编译在 `upstream/wiliwili/resources/shaders/`，**不需要跑 `uam`**。
6. **签名搜索接口已死**（200 + `Content-Length: 0`，**用参考实现本机实跑对照确认**）→ 浏览改走网页抓取；**视频模型接口还活着**。
7. **branch 2 未实现** —— 参考实现接受 branch 0 或 2，只避开 1；搜索无重试循环，约 5/16 请求会失败。

## 八、这一会话最该带走的东西

**几乎每一次我"推理出"故障原因，都错了。** 真正解决问题的动作只有一个：

> **把真机上真实失败的那份数据取回来，在主机上重放同一条路径。**

具体地：

- 我断定"i386 通过、aarch64 失败"，**因为我在重写诊断时删掉了 `parse_home` 的调用却不自知**。真相是主机也失败。
- 我把"最后一个字符是 `}`"当成配平验证——**它什么都没证明**。
- 我按"参数名靠猜"补了三次，**而一次逐字节比对就能问清楚**。
- 我差点因为"两组都报 DECODE OK"写下"播放零特殊处理"——**而那个判据测的是未加密的容器头部**。是加上"故意错密钥"这一组才分开的。

**给新会话的三条**：

1. **先做对照实验，再改代码。** 参考实现能跑就先跑它；设备上的数据能取回来就先取。
2. **判据要测到你想测的东西。** "成功了"不等于"对了"——问清楚这个信号在失败时会不会也出现。
3. **工具的输出不是事实。** 这一会话里，坏掉的工具（ascii 写入、被删的调用、空验证）比坏掉的代码更多次误导了我。

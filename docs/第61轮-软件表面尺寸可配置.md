# 第 61 轮：软件表面的尺寸可配置（I2 的第二条杠杆）（build61）

I2 是"1080p 卡顿"。`build53` 给了两条**画质侧**的杠杆（低画质解码、解码缓存），这一轮找到的是**这条路径上最大的一条**。

---

## 一、实测到的问题：**每帧多做了 2.25 倍的活**

```
player_view.cpp:978   impl->swW = brls::Application::windowWidth;
player_view.cpp:979   impl->swH = brls::Application::windowHeight;
```

软件表面按**窗口尺寸**分配。于是：

| 模式 | 表面像素 | 画面实际画进去的逻辑矩形 | 多做的活 |
|---|---|---|---|
| 掌机 | 1280×720 = 92 万 | 1280×720 = 92 万 | 无 |
| **主机** | **1920×1080 = 207 万** | 1280×720 = 92 万 | **2.25×** |

mpv 每帧在 CPU 上转换 207 万像素，然后这整块又被当作纹理上传、再画进 92 万像素的矩形里 ——
**掌机模式不卡、主机模式卡**，这个差异正好对上。

## 二、做法：做成**设置项**，不偷偷改默认

新增 `player.sw.height`（播放设置里的 **Software surface**）：

| 值 | 含义 |
|---|---|
| **0（默认）** | 按窗口高度 —— **最清晰**，也是这一轮之前所有版本的行为 |
| 720 | 按 720p 渲染，由 GPU 放大到 1080p 信号 |
| 540 | 同一思路再进一步 |

**它是一个取舍**（清晰度 ↔ 帧率），只有坐在电视机前的人能决定要哪一个 —— 所以是**选项**而不是新默认。
宽度按窗口宽高比算，画面**不会被拉变形**。日志会说清楚选了哪个：

```
PLAYER: software surface reduced to 1280x720 (player.sw.height=720); the window is 1920x1080, so the GPU scales the picture up
```

## 四、请真机确认（这是一个"一次跑完"的对照实验）

接电视，播一集 1080p 的，按顺序试这三档（**每次改完需要重启**，因为表面在启动播放时分配）：

| 设置 | 期望 |
|---|---|
| `player.sw.height=0` + `player.decode.fast=no` | 当前行为（基准） |
| `player.sw.height=720` | **应明显更流畅**，画面会略软（1080p 信号由 GPU 放大） |
| 再把 `player.decode.fast=yes` | 更流畅、更糊 |

**请告我哪一档是你能接受的**（或者"720 也不够流畅"）—— 有了这个结论我就能定默认值，或者继续往"减少上传"的方向做
（下一层的候选：只在画面变化时上传、以及把上传格式从 RGBA 换掉）。

> 日志里会同时有 `SW surface vs view: surface=1280x720 view=… window=1920x1080 …` —— 这一行现在能直接看出表面是否被缩小了。

## 3. 新接口：怎么找到的

在**相邻路由**上试出来的。把 `multi_video_model` 去掉 `multi_`：

```
POST https://api5-normal-sinfonlineb.fqnovel.com/novel/player/video_model/v1/
```

回的不是空壳，而是**结构化错误**（有 `log_id`、有小写 `code`）：

```json
{"BaseResp":{"StatusCode":100001,"StatusMessage":"invalid param"},"code":100001,"data":{},
 "debug_info":"video_id invalid, param:","message":"参数错误","log_id":"20261013193933…"}
```

**`video_id invalid, param:`** —— 这条路由**活着**，它在等一个叫 **`video_id`** 的参数。

### 实测可用的请求

```http
POST /novel/player/video_model/v1/?<DEVICE 27 项 + ts + _rticket>
（头与签名完全同旧路径：x-gorgon / x-ladon / x-argus / x-helios / x-medusa / x-ss-stub / VIDEO_UA …）

{"video_id":"7692096729776131096","biz_param":{"detail_page_version":0,"device_level":3,
 "disable_digg_stat":false,"disable_video_relate_book":false,"need_all_video_definition":true,
 "need_mp4_align":false,"use_os_player":false,"use_server_dns":false,"video_platform":1024}}
```

- **`video_id` 必须是 JSON 字符串**：传数字 → `HTTP 400`
  `InvalidRequest … expected string, actual value: 7692096729776131000 (json.Number)`。
- 只传 `{"video_id":"…"}` 也能通（7.4 KB），**带 `biz_param` 才是全档位**（24.1 KB，5 档）。
- 甚至 `GET ?video_id=<vid>`（无 body）也通 —— 但**不带签名头一律 110001**。

### 响应形状也变了（这一点会让解析器静默失败）

```
旧（批量）：{"data":{"7692096729776131096":{…,"video_model":"<JSON 字符串>"}}}   ← data 按 vid 分键
新（单条）：{"data":{       "disable_vsr":true,…,"video_model":"<JSON 字符串>"}} ← data 直接就是本条
```

**只差一层嵌套**，而 `hg_play.c` 的 `unwrapModel()` 原来只认"按 vid 分键"那层 ——
只改 URL 不改解析，**症状还是 `rc=-5`**（看起来像"接口又坏了"）。

### 实测内容（本机取回，非推断）

| 项 | 值 |
|---|---|
| 档位 | **5 档**：360p/480p/540p/720p = `bytevc2`，**1080p = `bytevc1`** |
| 加密 | 每条都带 `encrypt_info`：`cenc-aes-ctr` + `kid` + `spade_a` |
| `main_url` | 690 字符，`https://v95-bjb-mc-reading-video.qznovelvod.com/…`（`a=8662`） |
| 派生密钥 | `hg_spade_content_key` 输入一致 → 解出 `96565ee362687d2a2a04c08190d89819` |
| **拉流验证** | `Range: bytes=0-127` → **206 / `video/mp4` / `bytes 0-127/13080187`**，首字节 `ftyp isom` ✓ |

## 7. 还没做的（下一轮，仍然"一次一件"）

2. **★ §5 的"一次请求拿全"**：新接口**一次就同时给了源列表 + 全档位**，
   所以 `fetchQualityLadder` → `fetchPlayPlanForSource` 的**第二次请求应当去掉**（现在是两次）。
   **这不是"优化"，是真机上看得见的一个毛病** —— 第 3 集实测：
   ```
   19:48:45 PLAYER: mpv started, plan = 1080p 1920x1080  codec=bytevc1  CENC key derived
   19:48:46 QUALITY: ladder ready (1 tiers, first '1080p  ·  HEVC')     ← 只剩 1 档
   ```
   前两集都是 `5 tiers`，第 3 集只回 1 档（**同一次会话、同一个接口**）⇒ 服务端仍然会偶发少给档位。
   现在梯子和计划各发一次请求，谁拿到"少档位"的那份谁就退化；**共用同一次响应**之后，
   **菜单显示与实际播放的档位不可能再不一致**（当前是"菜单只列 1080p 而实际就在 1080p"，这次没造成错播，
   但机制还在）。**这是 §5 的正解，现在有了实测支撑。**

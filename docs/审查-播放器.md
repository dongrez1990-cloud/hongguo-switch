# 审查报告 — `app/hongguo/player_view.cpp`

范围：图片菜单 (`drawMenuTick`)、拖动选台 (`drawScrubTick`/`drawScrubAbsolute`)、清晰度切换 (`switchQuality`)、
`mpv_command_ret` 探针 (`runScreenshotProbe`)。只读审查，未改动任何源文件。

---

## 发现（按严重程度排序）

### 1. HANG — `switchQuality` 在主线程上重新 `loadfile`，并把菜单锁死
`player_view.cpp:1155-1157`

```cpp
const char* cmd[] = {"loadfile", plan.url, nullptr};
int rcLoad = mpv_command(impl->mpv, cmd);
```

该回调由 `brls::sync` 投递（`player_view.cpp:1123`），**运行在 UI/渲染线程**。
`mpv_command()` 是同步命令：它等到命令进入 mpv 的播放核心才返回。此时正值播放中，
mpv 需要 teardown 旧流、建立新 HTTP 连接并读 CENC 头 —— 在这个窗口里 `mpv_command`
会阻塞 UI 线程数百毫秒到数秒。整个 `draw()` 停摆，画面冻结，borealis 的输入/渲染
循环一起停摆。同一个函数的头部注释（`player_view.cpp:1085-1094`）自称"mpv 不被拆除重建"，
但 `loadfile` 恰恰就是拆除重建。下面的 `mpv_get_property(path)` 也在同一线程上同步。

### 2. HANG — `runScreenshotProbe` 的阻塞调用确实落在主线程
`player_view.cpp:1213-1214`（调用点）、`956-967`（实现）

```cpp
if (hg::cfgIs("player.shotprobe", "yes")) {
    runScreenshotProbe(impl->mpv);       // mpv_command_ret -> BLOCKS
}
```
而这一整段位于 `start()` 的 `brls::sync` lambda 内部（`player_view.cpp:1183`）。
函数自己的注释（`887-892`）断言它"跑在 plan-fetch worker 上，所以不阻塞任何东西"——
**这个断言是错的**：`setupMpv`、探针、`startQualityLadder`、启动 poller 全部在那个
sync 回调里，即主线程。`mpv_command_ret` 要 mpv 渲染并拷回一整帧，开 `player.shotprobe=yes`
就是启动时的一次明确卡死。注释与代码矛盾，说明作者把 `brls::sync` 当成了后台线程。

### 3. HANG — `setupMpv` 在主线程上有意的 250 ms 阻塞 + `mpv_command`
`player_view.cpp:786-799`

```cpp
int rcLoad = mpv_command(impl->mpv, cmd);
...
svcSleepThread(250000000ULL);
```
同样在 `brls::sync` 回调内（`:1183`）。注释自称"阻塞主线程，每次播放花 250 ms 的 UI 响应性"，
是**明知故犯**，但它与发现 2 叠加后，启动路径的总阻塞不再是 250 ms。这是设计选择而非疏漏，
但在"未上真机验证"的前提下，它是每次进入播放器都会发生的 UI 停顿。

### 4. CRASH（潜在）— worker 线程的 `brls::sync` 回调捕获裸 `self`，无生命周期保护
`player_view.cpp:1014-1018`、`1120-1124`

```cpp
PlayerView* self = this;
hg::runDetached([self, episodeId]() {
    ...
    brls::sync([self, tiers, r]() {
        Impl* impl = self->impl;      // self 可能已析构
```
防护只有 `if (!impl) return;`（`:1019`、`:1125`）。`impl` 是 `PlayerView` 的成员，
而 `PlayerView::~PlayerView()` 在 `delete this->impl;`（`:868`）**之后**仍然继续执行、
并且 `this` 本身随即被释放。因此 `self->impl` 本身就是在读取一个已释放对象的成员 ——
`impl` 为 null 只是巧合下的结果，不是保证。B 键退出播放器时
（`player_activity.cpp:264-273` → `popActivity()`），请求/清晰度 fetch 很可能仍在飞行中，
而 Activity 与 PlayerView 会被销毁。`clearMenuOverlayCallback()`（`player_activity.cpp:73`）
只切断了 `menuOwner` 这一条路径，**不覆盖这两处 worker 捕获**。
这是四个新特性里唯一会真正踩内存的路径。

### 5. SILENT-WRONG / 未定 — `mpv_set_option_string` 在运行时改 `demuxer-lavf-o`
`player_view.cpp:1150-1151`

```cpp
int rcKey = mpv_set_option_string(impl->mpv, "demuxer-lavf-o", plan.decryption_key);
int rcHdr = mpv_set_option_string(impl->mpv, "http-header-fields", plan.header_fields);
```
mpv 自己的头文件写得很清楚（`C:\devkitPro\portlibs\switch\include\mpv\client.h:846-849`）：

> Set an option. Note that you can't normally set options during runtime. It
> works in uninitialized state (see mpv_create()), and in some cases in at
> runtime.

即"运行时通常**不能**设置选项，只在未初始化状态和**某些情况**下可以"。这里调用发生在
`mpv_initialize()` 之后且播放中，属于文档明说的"不保证"区间。更关键的是**返回值只被记录、
从不检查**（`:1152-1153` 只是打印 rc），所以如果 mpv 拒绝、或把该选项缓存在 init 时，
后面的 `loadfile` 会用**旧密钥/旧头**去开新流 —— 结果是无画面且无错误，正是本文件
反复警惕的那种失败。

`demuxer-lavf-o` 是否在 init 时被缓存、从而对**下一次** `loadfile` 无效：**undetermined**。
我在 `client.h` 中找不到关于该选项生命周期或"per-file vs per-instance"的任何说明，
这段头文件里也没有 mpv 的 manpage。运行时的 mpv 版本可得性和该选项的实际语义**没有从
现有代码/头文件中确定**，因此不做猜测。正确做法应是在 `loadfile` 之前用
`mpv_set_property_string()`（头文件 `:1048-1054` 明确允许运行时使用），或在
`loadfile` 命令里带 `demuxer-lavf-o` 作为 per-file 选项；
**在当前写法下，"切换成功"这个结论无法从 rc 得到，必须实测**。

### 6. SILENT-WRONG — 切换失败后菜单行可能永久错位
`player_view.cpp:1137-1145`

```cpp
if (impl->plan.has_quality_type) {
    for (size_t i = 0; i < impl->tiers.size(); i++) { ... }
}
```
若 `has_quality_type` 为 0（从裸对象构造的 plan，注释 `:1034` 承认这种情况存在），
回滚分支整个被跳过，`menu.qualityIndex` 停在用户选的那个失败档位。
而 `lastQualityIndex` 已在 `:2211` 被写入该值，于是 `:2210` 的比较不会再次触发 ——
菜单会一直宣称一个并未生效的清晰度，且无法通过再按一次同一行来重试。

### 7. SILENT-WRONG — 切换成功后 `lastQualityIndex` 与 `qualityIndex` 不再对齐
`player_view.cpp:1149` 与 `2144` 之间

`startQualityLadder` 的到达回调会重写 `menu.qualityIndex`（`:1044-1045`），
但**不**重置 `lastQualityIndex`。若梯子在用户已经打开菜单并翻到某行之后才到达，
新的 `qualityIndex` 可能与 `lastQualityIndex` 不同，`:2210` 便会立即再发一次切换请求 ——
用户没有按键却发起了下载/切流。这是"未上真机"最典型的时序型缺陷。

### 8. MINOR — `switchQuality` 的正整数参数被当作"档位"而非"源索引"混用日志
`player_view.cpp:1100-1101`、`1115-1116`、`1122`

`tierIndex` 是 `tiers` 的下标（best-first），而真正传给网络层的是 `want.sourceIndex`。
两套编号都叫"index"并在同一行日志里并排输出（`:1115`），排错时极易把两者读反。

### 9. MINOR —— 拖动释放判定用的是"当前帧按键为 0"而非"曾经按下"
`player_view.cpp:1812-1822`

`dir == 0 && this->scrub.active` 即判定为释放。这是正确的，但如果 `hg_scrub_begin`
在某一帧因 duration 未知而拒绝（`:1770`），随后 duration 到达、用户仍在按住同一方向键，
下一帧 `dir != 0 && !active` 会重新 begin —— 这是**期望**行为，不是缺陷，记录在此是因为
它意味着 `scrubRefusals` 计数器与 `:1776` 的取模日志在面对"按住不放"时不会像注释设想的那样
每 600 帧记一次，而会在 begin 成功后归零。仅影响诊断密度。

## 确认无问题的部分（A–G）

**A. 线程安全 —— 确认 OK（除发现 4）。**
逐行核对 `pollLoop`（`:247-435`）：它只写 `impl->progress/duration/position/paused`
四个 `std::atomic`（`:92-101`、`:380-396`），`statusText` 在 `statusMutex` 下写（`:419-422`），
`lastLogged` 在 `logMutex` 下写（`:428-434`），另有 `alive`/`started` 两个 atomic（`:115-116`）。
它**不触碰** `menu`、`menuPanel`、`scrub`、`tiers`、`prevButtons` 或任何 brls 对象 ——
这些全部只在主线程的 `draw()`/`drawMenuTick()` 里被访问。`mpvLogLines`（`:138`）由
`drainMpvEvents` 写，而该函数同时被 poll 线程（`:260`）和主线程（`:1277`、`:1500`）
调用的 —— 但它在 `:138` 的注释里声称"只由主线程写"。**这是一处非原子的 int 竞争**，
不过它是纯粹的日志计数上限，最坏后果是多记/少记几行 mpv 日志，不构成崩溃，故未单列为发现。

**B. 见发现 5。** `mpv_set_option_string` 在运行时的合法性 = 文档明说不保证；返回值未检查。

**C. 见发现 2。** 确认 `runScreenshotProbe` 经由 `:1183` 的 `brls::sync` 落在主线程，
与其自身注释（`:884-888`）矛盾。

**D. 一键双重消费 —— 确认 OK。**
两条路径互斥且互斥点唯一：`:1372` 调 `drawMenuTick()`；`:1421` 的相对选台块要求
`!this->menu.open && !dragArm`；`:1626` 的拖动块要求 `dragArm`。菜单打开时 `menu.open=1`
使 `:1421` 直接跳过；`dragArm` 为真时同一块也被跳过，而拖动块只在 `dragArm` 为真时运行，
故 LEFT/RIGHT 在两种 arm 下各只有一条路径。`:2215` 的 `memcpy(prevButtons, st.buttons)`
在 `drawMenuTick()` 末尾、且在两个消费块之前执行 —— 但 `drawScrubTick` 用的是**电平**
（`st.buttons[...]`，`:1751-1761`）而非边沿，所以不受 `prevButtons` 更新时机影响。
`player_activity.cpp:284` 明确没有注册 LEFT/RIGHT/LB/RB 的 action，第二条路径不存在。
唯一的"两个都不跑"窗口是 `overlay=no`（`:1370` 使 `menuEnabled=false`，同时
`:1626` 也要求 `menuEnabled`）—— 这是有意的诊断模式，注释 `:1360-1365` 已说明。

**E. 绘制顺序 —— 确认 OK。**
`draw()` 内顺序为：软件路径 mpv 渲染 `:1276-1327`；deko3d 路径 `mpv_render_context_render`
`:1561`（含 `report_swap` `:1591`）；状态标签 `:1596-1606`；进度条/拖动光标/预览
`:1626-1648`；最后才是 `brls::Box::draw(vg, x, y, width, height, style, ctx)` `:1666`。
即"mpv → bar → overlay → 子视图"，与注释 `:1608-1625` 的论证一致，覆盖层确实在最上层。

**F. 见发现 4。** Activity 侧（`player_activity.cpp`）确实正确地在析构里调用
`clearMenuOverlayCallback()`（`:73`），`menuOwner` 这条路径是安全的；不安全的只有两处
worker 里捕获的 `self`。

**G. 死锁/自旋 —— 确认 OK（除发现 1、2、3）。**
`nowMs()`（`:196-198`）用 `brls::getCPUTimeUsec()`，是单调的 CPU 时钟，仅用于
"距上次重复是否足够久"的比较（`:2174-2179`），不参与任何等待，无自旋。
`drawMenuTick` 的重复计时器是纯粹的 `now >= menuRepeatAt` 轮询（`:2178`），
由帧驱动，且 `:2198-2201` 在无按键时复位，不会残留。
`:272` 的 `!impl->started` 守卫在 poll 线程里每次迭代都读 atomic 并 `continue`，
配 `sleep_for(500ms)`（`:267`），不会忙等。`hg_scrub_end` 在 `!active` 时返回 0
（`hg_scrub.c:88`），所以重复释放不会重复发 seek（`:1816-1817`）；
`hg_scrub_begin` 拒绝时调用 `hg_scrub_init` 清空状态（`hg_scrub.c:44`、`:48`），
所以被拒绝的拖动不会留下半激活状态。拖动期间**不发**任何 mpv 命令 ——
`drawScrubTick` 只在释放时调一次 `seekAbsolute`（`:1819`），这正是模型设计的意图，
确认成立。

**未涉及/未确定：** `client.h` 未包含 mpv manpage，`demuxer-lavf-o` 的 per-file 语义
无法从本仓库头文件判定（见发现 5）；`brls::sync` 在 borealis 中的确切线程归属我按任务
给定的前提（主/UI 线程）采用，未在本仓库中另行查证其实现。

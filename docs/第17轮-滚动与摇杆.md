## 一、主界面"看不到其他预览" —— 根因找到了，是**框架根本没有跟随焦点滚动**

**这不是滚动条的问题，是"焦点移动时没有任何东西滚动"。**

我去读了这一版 borealis 的 `scrolling_frame.cpp`：

```cpp
// draw() 里：
if (this->updateScrollingOnNextFrame && this->updateScrolling(false))   // 行 135-136
    this->updateScrollingOnNextFrame = false;

// 而 updateScrollingOnNextFrame 只在**一个地方**被置真：
void ScrollingFrame::willAppear(bool resetState) {
    if (resetState && behavior == ScrollingBehavior::CENTERED)
        this->updateScrollingOnNextFrame = true;    // 行 347
}
```

`updateScrolling()` 是**唯一**会根据焦点子视图算出居中偏移的函数，而它**只被 `draw()` 调用**、
且**只在那面旗子还立着的时候**。旗子只在 `willAppear` 立一次。

**所以：这个框架的滚动框只在"出现"时滚一次，之后焦点怎么移动它都不管。**
这与"3 个大格子占满屏幕、往右能选中但看不到"完全对上 ——
焦点确实移动了（所以第二个格子被选中了），**但没有任何滚动跟随它**。

**wiliwili 是怎么解决的**：它用同一套框架，**自己做了这件事**。
`wiliwili/source/view/recycling_grid.cpp:525`：

```cpp
void RecyclingGrid::selectRowAt(size_t index, bool animated) {
    this->setContentOffsetY(getHeightByCellIndex(index), animated);   // ← 自己滚
    this->itemsRecyclingLoop();
    ...
}
```

**所以修法就是照它做**：两个网格都加了 `followFocus(index)` ——
用 `hg_grid_layout` **已经算出来**的坐标（卡片就画在那里）算出让该卡居中的偏移，
clamp 到 `[0, contentH - viewH]`，然后 `setContentOffsetY(want, false)`。

- **首页网格**：`getNextFocus` 里两条返回路径（左右 / 上下）都会先调它；
- **选集网格**：同样两处。**选集那边需求最明显** —— 222 集、每行 8 个，按两下下就已经出屏。

**瞬时滚动，不做动画**：这个调用发生在焦点移动过程中，动画还没播完下一次按键就到了。
框架那套带动画的偏移是给触摸拖动的惯性用的，那条路径没动。

## 二、像浏览器一样下拉 —— **框架已经有了，但需要真机确认**

好消息：`scrolling_frame.cpp:42-84` 里**已经装了触摸手势**：

```cpp
addGestureRecognizer(new ScrollGestureRecognizer([this](PanGestureStatus state, Sound* soundToPlay) {
    ...
    if (state.state != GestureState::END)
        startScrolling(false, newScroll);
    else {
        float time   = state.acceleration.time.y * 1000.0f;      // ← 惯性
        float newPos = this->contentOffsetY + state.acceleration.distance.y;
        ...
        animateScrolling(newScroll, time);
    }
}, PanAxis::VERTICAL));

// 点一下停住
addGestureRecognizer(new TapGestureRecognizer([this](brls::TapGestureStatus status, Sound*) {
    if (status.state == GestureState::UNSURE) this->contentOffsetY.stop();
}));
```

**拖动 + 惯性 + 点按停下，全都在，而且是 `ScrollingFrame` 自带的** ——
我们的网格就是 `ScrollingFrame` 的子类，所以**理论上已经能拖**。

**但我不打算说它"好了"**，因为上一条的教训是：**框架里"看起来有"和"真的能用"差一个实测**。
§一 那个跟随焦点的缺失就是这么发现的。**所以这一条请在真机上试一下**：
在主界面上直接**用手指往上/往下拖** —— 如果拖动没有反应，那就是手势没被派发到我们的网格上
（我们的格子是**绝对定位**的，`hitTest` 的命中判定可能有问题），我下一轮按这个方向查。

## 三、左摇杆"只有左右" —— 查到了映射，但**没有把握下结论**

我把 Switch 输入的映射表读出来了（`library/lib/platforms/switch/switch_input.cpp`）：

```cpp
// 完整手柄（HidNpadStyleSet_NpadFullCtrl）用的是这张：
HidNpadButton_AnyUp,     // BUTTON_NAV_UP
HidNpadButton_AnyRight,  // BUTTON_NAV_RIGHT
HidNpadButton_AnyDown,   // BUTTON_NAV_DOWN
HidNpadButton_AnyLeft,   // BUTTON_NAV_LEFT
```

而 libnx 自己的注释说明了 `Any*` 的含义（`libnx/include/switch/services/hid.h:294`）：

```c
HidNpadButton_AnyUp = HidNpadButton_Up | HidNpadButton_StickLUp | HidNpadButton_StickRUp,
///< Bitmask containing all buttons that are considered Up (D-Pad, Sticks)
```

**也就是说：在这张映射表里，摇杆的四个方向本来就该和 D-Pad 一样触发导航。**

**但用户报告的是"只有左右"。** 这两件事对不上，而**我在构建机上无法验证到底哪一环断了**：
`padGetButtons()` 是否真的回填了 `StickLUp/Down/Left/Right` 这些**伪按键位**，
取决于 libnx 的 `padUpdate` 配置和手柄样式。**这一点我不猜。**

三种可能，下一轮按顺序排除：

1. **摇杆的伪按键位没被回填**（需要 `padSetStickLRThreshold` 之类，或者 `padGetButtons`
   只返回真实按键）→ 修法是**读 `axes[LEFT_X/LEFT_Y]` 自己合成导航**，
   这在 `state->axes` 里**已经有了**（`switch_input.cpp:251-252` 已经填了左右摇杆的轴值）；
2. **摇杆能触发导航，但触发的是"半手柄"那张表**（`StickLRight → NAV_UP` 那种**旋转映射**），
   于是四个方向全错位、看起来像"只有左右"能用；
3. **摇杆触发的是 `BUTTON_UP/DOWN/LEFT/RIGHT` 而不是 `BUTTON_NAV_*`** ——
   那是四个不同的位，而导航只监听 `BUTTON_NAV_*`。

**请你在真机上补一个观察**：进主界面，**把左摇杆往"上"推到底**，看焦点是
①不动 ②往上走 ③往右走。**这三个答案分别指向上面三种原因**，我下一轮就能一次修对。

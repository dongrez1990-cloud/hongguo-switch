## 五、画面为什么曾经不呈现（已解决）

### 已经排除的（都做了对照实验）

| 假设 | 如何排除 |
|---|---|
| 媒体链路坏了 | Arm A（`renderctx=no` + `vo=null`）实测解码出 hevc/aac、`time-pos` 稳定推进 |
| 音频后端不存在 | Arm C 实测 `AO: [hos]`，有声 |
| 硬件解码问题 | 一直跑 `hwdec=no`（软件解码）仍然如此 |
| `advanced_control` 旗标门控 | `advanced=no`（`render()` 无条件渲染的契约）实测 `update flags=0x0`，画面依旧不在帧里。<br>**⚠ 这条推理要修正**：mpv 的 `render.h` 写着——**关闭 advanced control 时 `mpv_render_context_update()` 本来就恒返回 0**。所以那一臂**并没有测到旗标**，我当时把"按设计就是 0"当成了异常。<br>**真正该看的数字是 advanced=1 时的 flags**：控制台上现在部署的正是 advanced=1 的配置，而 `MPV draw #n` 那几行**已经会打印 `update flags=0x... update_frame=N`**。若 `update_frame` 恒为 0，说明 mpv 从未向渲染 API 产出可渲染的帧（那问题在渲染调用之前）；若为 1 却仍无画面，说明写进去了但没落到被呈现的那一帧。**这是下一次上机最该看的一行。** |

| 下层 Activity 遮挡 | `isTranslucent()=false` 已修，照片确认过 |
| fence 顺序 | `fencewait=cpu`（`dkFenceWait` 强制 CPU 等 mpv 的 GPU 工作完成）实测无变化 |
| FBO 类型错 | 已修（#4） |

### 已经逐字对齐 wiliwili 的（核对了每一项）
建上下文的参数、`mpv_fbo` 一次性初始化只改 `.tex`、`ready_fence`/`done_fence` 指针、
`mpv_render_param` 数组内容（`{{DEKO3D_FBO,&fbo},{INVALID,nullptr}}`）、
`queueSignalFence → queueFlush → render → queueWaitFence → report_swap`、
以及 Switch 专用选项集（`vd-lavc-dr=no`、`vd-lavc-threads=4`、`demuxer-lavf-analyzeduration=0.4`、
`demuxer-lavf-probescore=24`、`vo=libmpv`、`audio-channels=stereo`、`idle=yes`、`ytdl=no`）
和 `mpv_render_context_set_update_callback`。

**结论：wiliwili 渲染路径上的每一环都与本项目一致，而画面仍然不在被呈现的帧里。**
所以剩下的嫌疑在**"我们交给 mpv 的那块 image 是否就是被呈现的那块"**，而不是"怎么驱动 mpv"。

**最后一处实测到的真实差异（第 7 轮发现，不影响"看不见"，但影响布局）**：
wiliwili 的 `MPVCore::setFrameSize()`（`mpv_core.cpp:684-743`）在 deko3d 分支里除了设
`mpv_fbo.w/h = windowWidth/windowHeight`（**与我们一致**）之外，还会把**视图矩形换算成 mpv 的
`video-margin-ratio-top/left/right/bottom`** 并 `command_async("set", ...)` 下发。
我们一次都没设过。全屏视图下这 4 个值本来就是 0，所以它**不会**让画面消失；
但等到画面能显示之后，要按视图位置摆放画面就得补这一步。`setFrameSize` 本身由
`MPVCore::draw()` 在 `!rect == area` 时触发（`mpv_core.cpp:785`），默认 rect 是 `{0,0,1920,1080}`。

### 控制台上已部署的三个判据（下一次上机看这三行就够）

第 5 轮把这些加进了 `player_view.cpp`，并已部署。三行各自独立地回答一个问题：

| 判据 | 日志长什么样 | 读法 |
|---|---|---|
| **1. mpv 有没有可渲染的帧** | `MPV draw #n: ENTER (fbo=… imageBytes=… declared=1280x720) update flags=0x… update_frame=N` | 本版是 **advanced=1**（cfg 里没有 `advanced=no`）。若 `update_frame` **恒为 0** → mpv 从未向渲染 API 产出帧，故障在渲染调用**之前**；若为 1 却仍无画面 → 写进去了但没落到被呈现的那一帧 |
| **2. 渲染调用本身成不成功** | `MPV draw #n: render returned rc=…` | `mpv_render_context_render()` **有返回值，之前一直被丢掉**——所以失败的调用和成功的调用在日志里长得一模一样。前 6 次必打，之后只在非 0 时打 |
| **3. VO 到底配置了没有、有没有在出帧** | `POLL: vo-configured=… current-vo='…' estimated-vf-fps=… display-fps=…` | `vo-configured=0` 的话根本不存在可渲染的视频输出，下游全部无意义——**这也是"render 返回 0 却什么都没画"唯一不矛盾的解释**。`estimated-vf-fps>0` 说明帧确实在产出 |

另外新增 cfg 键 **`mpv.msglevel`**（默认 `info`）：控制台上现在是
`all=info,cplayer=info,vo=v,libmpv=v,gpu=v`，把渲染相关模块提到 verbose。
**在代码里限了 500 行上限**——每条面包屑都 fsync，无上限的 verbose 会让日志 I/O 变成被测行为本身。
（`mpv_request_log_messages` 的返回码也会打出来，所以这个级别串被拒的话会看见。）

## 七、环境约束（本轮实测）

| 限制 | 规避 |
|---|---|
| **`std::thread` 不可用** | 用 `hg::runDetached`（libnx `threadCreate`）。`std::this_thread::sleep_for` 可用（就是 `nanosleep`） |
| msys2 全家桶起不来（沙箱禁命名管道） | 构建脚本一律直接驱动编译器，不经 cmake/make/sh |
| 工作区路径非 ASCII（`<repo>`） | 一律在 `$env:TEMP` 的 ASCII 暂存目录编译，产物回拷 |
| PowerShell 5.1 按 GBK 解析无 BOM 的 UTF-8 `.ps1` | `.ps1` 与 C/C++ 源文件**一律纯 ASCII**（本轮自己破过一次规矩，已改回） |
| `$env:TEMP` 每个会话都不同 | `build-hongguo.ps1` 缺库时自动 stage+build；`libborealis.a` 另存 `third_party\prebuilt\` |
| sys-ftpd 对正在被打开的文件返回 450 | 日志改成 append-and-close |
| mpv 属性名 | 是 `current-ao`，**不是** `ao-current`（搜 `libmpv.a` 字符串：前者 1 次，后者 0 次） |
| 网络流 | CDN 是 fMP4 + CENC，`demuxer-lavf-o=decryption_key=<hex>` 是已验证路径 |

# 第 71 轮：控制条"设置"格被挡住 + 给左右键加决定性诊断（build71）

`build70` 修掉了三条崩溃，但它还没来得及验证（你的日志仍停在 `build69`）。这一轮修**照片里能确定的那一条**，
并给"左右没反应"加上一行**能把歧义一刀切开**的日志。

## 一、"设置"格到不了 —— 其实是被**文字盖住了**

**照片与代码对上了**：控制条的五个芯片**固定 72 px 宽**，而"清晰度"那个芯片的文字是
`1x 1080p · HEVC`（**编码后缀是我在 `build55` 加的**），在这个字号下约 **140 px** ✓ →
**文字溢出自己的芯片、压在左边那个上、把最右边的"设置"整个盖住** ✓✓。

后果不止是难看：**"设置"外侧的选中框也被盖住了** ✓ —— 所以你选中它却**看不见**
（"最后一个设置……到不了那个设置界面"✓）。**一个隐藏了焦点的布局 bug，读起来就像按键坏了** ——
所以这条写在代码注释里，而不是悄悄改掉。

**修法**：每个芯片的宽度**按自己的文字实测**（`nvgTextBounds`，带 72 px 下限让短标签保持原样）。
另外加一行"布局变了就打印"的日志，把这次的情况变成数字：

```
PLAYER: control bar chips start at x=… (bar width …, quality chip … px, all five measured) [build71]
```

## 二、"左右没反应"：一行把两种可能切开

从代码看，这个症状有**两种同样的表现**的可能：**键根本没到**这个函数（被别的路径吃掉），
或者**到了但值没变**。`tickControls` 的左右分支现在**每次按下都打一行**：

```
PLAYER: control bar saw LEFT with selection 3 -> adjusting
```

配合 `adjustControl` 本来就有的那行（`PLAYER: speed -1 -> volume=… speed=…`），
下一次日志就能直接判定是"键没到"还是"改了没效果" —— **不用再猜一轮**。

（另外我核对过：拦左右的那道门 `dpadOnAControl` 的代码是**对的**（控制条升起且选中项不是进度时，
拖动定位会被让开），种子的 `controlsSeeded` 守卫、`settingsIsOpen()` 初值、`adjustControl` 的 switch
覆盖面也都排除了 ✓。）

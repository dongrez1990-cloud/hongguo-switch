**第二轮把覆盖面补齐了**：第一轮只有前 5 组（签名器与基础密码学），第二轮补上了
CENC 穷举扫描、MP4 夹具、AesV3 四分支、计数器进位、hex/base64——
即主机上那 119 项所对应的**全部算法面**都上了真机。

> 具体检查数以屏幕显示为准（我没有亲眼看到那个数字）。程序自己打印总数，
> 不需要依赖谁的转述。

**真机与主机的检查数不相等，这是粒度差异不是覆盖缺口**，例如主机把 `sha512` 拆成 4 项、真机 3 项，
主机把 `_ROUTER_DATA` 的 5 条拒绝路径各自单列、真机合并成 4 项，
主机另有一条独立的 AES-128 FIPS-197 已知答案（真机由 NIST CTR 覆盖，它同样验证了
S-box、密钥扩展与轮函数）。

**一处明知故为的取舍**：真机程序**没有**复刻那 1024 字符的 vendor S-box base64 校验。
那是生成器侧的事、主机已覆盖，把 1024 个字符再抄一遍进这个文件**只会凭空引入抄写错误**。
取舍写在 `app/switch-test/main.c` 的注释里。

## 一、已验证完成的部分

所有验证都跑在 **i386（TinyCC 主机）** 上，同时**每个源文件都通过 aarch64 交叉编译**（零警告）。
当前 **119 项检查、0 失败**。

| 层 | 检查数 | 验证依据 | 可信度 |
|---|---|---|---|
| MD5 / SHA-512 / SM3 | 10 | RFC 1321 / FIPS 180-4 / GB-T 32905 **公开向量** | 独立真值 |
| 标准 AES-128 / CTR | 7 | FIPS 197 + NIST SP 800-38A F.5.1 | 独立真值 |
| 厂商变体 RC4、AesV3 | 5 | 参考实现导出（这两个**没有公开向量**） | 与参考一致 |
| 签名器 5 字段 | 60 | 仓库提交的 12 组 `signing.json` | 与参考一致 |
| CENC 解密 | 5 | NIST 向量 + **每个非对齐区间穷举** | 独立真值 |
| MP4 解析 / 样本表 | 13 | 合成 ISO-BMFF 夹具 + 拒绝路径 | 自建夹具 |
| spade 密钥 / URL | 3 | 参考实现导出（含**反推构造**输入） | 与参考一致 |
| 网页抓取 | 10 | Kotlin 边界用例 + 拒绝路径 | 与参考一致 |

> "独立真值"与"与参考一致"是**不同的可信度**。前者证明算法对；后者只证明我们和参考实现一致——
> 如果参考实现本身错了，我们也跟着错。这条区别写进了每个测试文件的注释。

```powershell

powershell -File app\src\tests\run.ps1 -SrcDir <ASCII别名>\app\src -TccPath <tcc.exe>
```

## 二、没做完的部分，以及为什么

### 2.1 接口层（唯一还带未知的代码）

12 个端点里，**搜索与视频模型**是签名 API，**首页／详情／榜单**是网页抓取（`_ROUTER_DATA`，已实现）。
缺少的是把它们串起来的 HTTP + JSON 层。

**这件事无法离线验证。** 它的未知不是"算法对不对"（那些已经证实了），而是
**"上游现在长什么样"**——而按 hongguoTV 自己的记录，签名与设备指纹是钉死版本号的逆向产物，
上游一改就可能失效。

### 2.2 真机验证：逻辑层 ✅ 全部通过；硬件相关部分完全未做

**逻辑层已经在真机上跑通 8 组全部通过**（见上文）——签名器、密码学、CENC、MP4、spade、网页抓取。

**完全没动的**：mpv/ffmpeg 解码、deko3d 渲染、手柄焦点。
目前只有"wiliwili 能编成 NRO"这个基线，**wiliwili 本身从未在真机上运行过**。
这是剩下最大的一块未知，也是唯一还需要动硬件的一环。

### 2.3 CENC 与 mpv 对接

已确认 switch 版 `libavformat.a` 带 `decryption_key`、`libmpv.a` 支持 `demuxer-lavf-o`，
所以**不需要自写解密解复用器**——但这条链路**从未真实链接验证过**。

### 2.4 NSP 打包：**阻塞点已解除**（第 12 轮）

第 3 轮判定"`hacbrewpack` 是 Linux ELF、仓库又 404，所以待解决"——**两处判断都错了，已更正**：

- 那个 404 是**测试写错**：我用 `gh.mjs ls <repo> releases` 查，而 GitHub Contents API
  没有 `releases` 这个目录，**必然 404**，与仓库是否存在无关。
- `scturtle/hacBrewPack` **一直都在，而且是纯 C**（`main.c`/`nca.c`/`npdm.c`/`pfs0.c`/`extkeys.c`
  + 内嵌 mbedtls 863 个文件），不是 C#。

于是改用**自己编译**：用你机器上的 `w64devkit`（gcc 16.2.0 + GNU Make 4.4.1）从源码构建：

## 四、这套工程最值得带走的四条经验

1. **"同一份 C 必须在 i386 与 aarch64 两边都编过"这条自定约束，每一轮都在兑现价值。**
   至少两次：`hg_ror64` 被隐式声明成返回 `int` 把 64 位结果截断（而 `hashF13` 只用 32 位旋转、
   "恰好对"，把问题盖住了）；`hg_cenc.c` 缺 `hg_crypto.h`（TCC 只警告且链接还能成功）。
   两次都**只有 aarch64 报错**。
2. **穷举式测试抓到了真 bug。** CENC 的"每个非对齐区间都验一遍"发现我的 CTR skip
   整块跳过了计数器——整块解密测试是通过的，只有"从偏移 24 解 1 字节"才暴露。
   这是照搬 Kotlin 测试的收益。
3. **变换要反推，不能搜。** `deriveContentKey` 要求派生的 32 字节全是十六进制字符，
   随机输入被接受的概率约 `(22/256)^32`。反推变换是构造性的、必然成功。
4. **"我以为"比"我写错"更容易出错。** 这一系列里三次失败**全部**是测试的期望写错，
   而不是代码写错（64 位进位、非字符串值、嵌套对象取值）。
   把假设写成断言，比写错实现更隐蔽。

## 六、环境限制备忘（下次接手会再撞上）

| 限制 | 规避 |
|---|---|
| 本机 schannel 损坏（`SEC_E_NO_CREDENTIALS`） | HTTPS 走 Node 的 OpenSSL 栈；git 加 `-c http.sslBackend=openssl` |
| 沙箱禁命名管道 → msys2 全家桶起不来 | 每次需一次性提权；或直接驱动 compile/link（本项目多数脚本这么做） |
| 工作区路径非 ASCII | 目录 junction 映射成 ASCII 路径 |
| PowerShell 5.1 按 GBK 解析无 BOM 的 UTF-8 `.ps1` | `.ps1` 一律纯 ASCII，非 ASCII 路径走参数 |
| `pkg.devkitpro.org` 被 Cloudflare 403 | 预编译包从 wiliwili release 取；缺的库自己交叉编译 |
| `raw.githubusercontent.com` 被墙 | 走 GitHub Contents API |
| `code.videolan.org` 有 Anubis 反爬 | 用 GitHub 镜像 `haasn/libplacebo`（它还返回 HTTP 200 + 假 HTML，别只看状态码） |
| PowerShell 的 `>` 重定向默认写 UTF-16LE | 生成器自己以 ASCII 写文件，不靠调用方重定向 |
| `@('-I' + $dir, ...)` 在 PowerShell 里会拼成一个参数 | 加括号：`@(('-I' + $dir), ...)`（`+` 比 `,` 结合更紧） |

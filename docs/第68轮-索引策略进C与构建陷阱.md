# 第 68 轮：索引合并策略进 C（带 27 项测试）+ 构建系统的一个真陷阱（build68）

这一轮把"能悄悄错"的逻辑搬进 C，并**在过程中撞上构建系统的一个静默陷阱** —— 后者比前者的价值更大。

---

## 一、把索引的合并策略变成有测试的 C

`SearchIndex::build` 里的合并原本是一个嵌套循环，**位于一个会联网的 C++ 成员函数里**，
所以主机测试**够不着它**。而它决定三件会**悄悄错**的事：

1. **按 id 去重** —— 同一部剧出现在多个分类里（实测：首页"热播短剧"的 9 张里有 2 张也在 real-drama）；
   搜索里列出同一部剧两次看起来就是 bug；
2. **必须有上限** —— 索引是逐页长起来的，**没有上限时，上游一个"永远返回同一页"的 bug 会把索引长到主机内存耗尽**：
   崩溃的原因与症状相隔十万八千里；
3. **保持顺序** —— 结果按页到达的顺序展示，合并不能打乱它。

现在这三条在 `hg_index.h/.c` 里，**27 项主机测试**（新增第 18 套），包括：

- 第二页里已存在的 id 被跳过、新的被追加、顺序不乱；
- **同一页内部重复**只加一次（否则日志会说"24 条新"，实际只加了 23）；
- 满了**不是错误**：`added=0 / overflow=n`，列表不变；
- 既是重复又超上限时**算重复**（用户看到的就是"它已经在列表里了"）；
- `count` 超过 `cap` 的调用直接被拒（调用方自己都数不清了，那是 bug 不是溢出）；
- 空 id 被当作**值**：两条都没有 id 时视作同一条（否则坏记录会一直重复进入）。

C++ 侧只剩"取页面 + 转换 + 记日志"；**索引上限 512**（三个分类 × 6 页 × 24 = 432，所以这是"防失控"而不是"限定规模"）。

## 二、顺带撞上的构建陷阱（**这才是这一轮最值得记的**）

新文件 `app/src/hg_index.c` 与已有的 `app/hongguo/hg_index.cpp` **同名**。构建脚本这样命名目标文件：

```powershell
$o = Join-Path "$stage\obj" ($f.BaseName + '.o')     # hg_index.o —— 两个文件同一个名字
```

于是 **C++ 的目标文件覆盖了 C 的**，C 符号消失，而**编译阶段一声不响**，
错误出现在**链接**阶段：`undefined reference to hg_index_append` ✗✗。

**这正是一个静默 clobber**，本项目最不能接受的那类失败。已修：目标文件名**保留扩展名**
（`hg_index.c.o` / `hg_index.cpp.o`），两个名字立刻不同，成本为零 ✓。
注释里写明了实测经过，免得以后有人"简化"回去。

## 四、真机可见的变化

只有日志更详细（索引的 `dup`/`overflow` 计数），**行为不变**：

```
INDEX: real-drama page 1 -> 24 series (24 new, 0 duplicate, 0 over the cap, 24 total) [build68]
```

日志里出现 `over the cap` 就是上游分页出了问题 —— 那一行现在会让原因**挨着症状**。

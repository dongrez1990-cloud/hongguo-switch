# 第 4 步：刷新按钮 + 网络诊断页

交接文档 §二 的第 4 步。**代码已完成、已构建已部署、未上机。**

## 一、做了什么

### 1. 首页刷新按钮

标题行右侧多一个 **Refresh** 按钮（可聚焦，方向键能够到，按 A 触发）。

- 重新跑**同一条**取数路径（`fetchHomeAsRows`），结果交给**同一个** `applyHome`。
  刷新和首次加载不可能给出不同的屏幕形状，因为它们是同一段代码。
- **刻意不清屏**：新数据到之前旧卡片留着。刷新失败时是「标题行报错 + 页面仍然可用」，
  而不是「整页空白让人以为 App 坏了」。
- 并发守门：`reloading` 标志挡住第二下按键——两个取数在飞会互相盖结果，
  而输的那次赢了是用户完全看不出来的。
- 退路：`home.refresh=no`（去掉按钮）。

### 2. 设置界面新增 Network 标签页

| 分组 | 行 |
|---|---|
| Connection | WiFi 状态（**联网状态**，不只是"无线开关开着"）、IP、DNS 服务器 |
| API test（端到端） | API 测试结果、HTTP 状态码、响应字节数、`_ROUTER_DATA` 字节数、解析出的卡片数、耗时 |
| Clocks | 主机时钟、服务器时钟（Date 头）、**时钟偏差** |

**任何一行按 A 都重跑一次测试**——wiliwili 只在顶部放一个按钮，
在主机上「不用滚回去再点一次」就是诊断和苦役的区别。

## 二、三个刻意的设计决定

### 1. 探针返回一串测量值，不是一个布尔

wiliwili 的网络页用**绿字/红字**回答「API 能用吗」。这个项目至今的失败有五种
（DNS、TLS、连接、HTTP 状态、**200 + 空 body**），其中四种在布尔下**长得一模一样**。
所以 `NetworkProbe` 逐段报告：传输层 rc、HTTP 状态、字节数、`_ROUTER_DATA` 字节数、
解析出的卡片数。`200 + 0 字节` 正是这个服务在搜索接口上出现过两次的东西，
没有这个数字就是不可见的。

### 2. 时钟偏差用服务器自己的 `Date` 头，不发明接口

wiliwili 有一个专门的取网络时间请求——那是 B 站的 `get_unix_time`。
**这个服务从没观察到提供类似接口**，所以不去猜一个。HTTP 响应自带的 `Date`
头测的是同一件事（签名请求暴露的那个偏差），而且是真实存在的。
服务器没发 `Date` 时这一行显示 "no Date header sent" 并标注 unknown——
**未知不等于零**，"0 秒" 是读起来像健康的谎话。

### 3. 探针复用已经取到的那一份响应

第一版探针自己又 `fetchRouter` 一次，于是探测路径和它要诊断的路径**不是同一条**——
一条绿的前提是自己重新发了一次请求，而被诊断的那条可能是坏的。
改成对内存里那份 body 直接 `hg_router_extract`。

### 顺带修掉的一个真隐患

首页刷新让「能重新加载」成为可能，而 `HomeGridView` 原先存的是
`std::vector<HomeRow>*`（指向 Activity 的成员）。一次加载没问题，
**第二次取数把那个 vector 换掉时，每个卡片的点击动作都还捕获着一个正在被重建的
vector 的下标**。已改成 `setRows` 收**拷贝**，并在重建前 `clearViews(true)`
（否则旧屏幕的视图会留在新视图底下）。

## 四、观察点

**屏幕**：首页标题行右侧有 Refresh，按 A 后标题变 `Refreshing...` 再变回 `36 cards in 4 sections`。
设置（首页按 Y）→ 最后一个标签 **Network**：WiFi/IP/DNS 立刻有值，API 测试几秒内从
`running...` 变成 `OK`。

**日志**：

```
HOME: refresh button added to the header row
HOME reload: fetch returned ok=1 n=40 err=''
NET: ip=192.168.1.x mask=255.255.255.0 gw=192.168.1.1 dns=192.168.1.1/0.0.0.0
NET probe: ok=1 http=200 body=521034 router=498112 cards=36 ms=1204 skew=+2 date='...' err=''
```

判读：

| 现象 | 结论 |
|---|---|
| API test `FAILED: transport: ...` | 传输层没通；`transportError` 的文本（`strerror`）区分 DNS/TLS/连接/超时 |
| `FAILED: HTTP 403` 之类 | 连上了，服务器拒绝——看 HTTP 状态行 |
| `Body size: none` 且 HTTP 是 200 | **就是那个"200 + 空 body"**，这个服务出现过两次 |
| `_ROUTER_DATA: not found` 但 body 很大 | 页面加载了但不是我们认识的页面 → 上游改版，不是网络问题 |
| `Clock skew` 超过 ±60 秒且方向为 BEHIND | **这才是签名请求会失败的原因**，去校准主机时钟 |
| `No Date header sent` | 服务器没发 `Date`；**不是失败** |
| `not run (no worker thread)` | 起不了 worker（见 `hg_thread.hpp`），探针没跑 |

## 六、两个"查了 API 才知道"的事实

1. **libnx 的 `Result` 与 `hg::Result` 撞名**。同一个文件里既有 `hg_client.hpp` 又有
   `<switch.h>` 时，不加限定的 `Result` 是 hg 的那一个，`R_SUCCEEDED(rc)` 直接编译不过。
   所以状态变量一律叫 `nifmRc`、类型写 `u32`。
2. **这个 libnx 版本的 `nifmGetCurrentIpConfigInfo` 没有结构体**，是五个出参：
   `(u32* addr, u32* mask, u32* gw, u32* dns1, u32* dns2)`。
   第一版照着一个不存在的 `NifmCurrentIpConfigInfo` 写，编译报错——**查头文件，别凭记忆**。

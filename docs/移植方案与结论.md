# 红果短剧 → Nintendo Switch 移植：勘察结论与方案

调研日期：2026-10-08。参考仓库：[N3urda/hongguoTV](https://github.com/N3urda/hongguoTV)（Android TV 版红果客户端，GPL-3.0）
复用基础：[xfangfang/wiliwili](https://github.com/xfangfang/wiliwili) `yoga` 分支 v1.6.0（GPL-3.0）

---

## 0. 一句话结论

**"抄 wiliwili"这条路线是对的方向，但清单里的四项没有一项能"原样"复用**——不是思路错，
是每一项都差一个必须自己补的环节。其中 **视频流是 CENC 加密的**这一条最要紧，它决定了播放器方案；
而**签名算法反而比预期好办**，因为它有纯粹自包含的实现和 12 组已提交的测试向量。

| 你的清单 | 实际结论 | 为什么 |
|---|---|---|
| `scripts/build_switch*.sh` + dkp-pacman 包 **原样** | ❌ 不能原样 | 脚本本身没问题，但 **devkitPro 仓库在本机被 Cloudflare 403**，且 msys2 需提权、gcc 拒绝非 ASCII 路径 |
| mpv/ffmpeg 硬解管线 **原样** | ⚠️ 需要补一层 | 流是 **CENC AES-CTR 加密**的，URL 本身也是加密的。**但好消息**：不需要自写解复用器，ffmpeg 原生支持 |
| 手柄焦点导航框架 **原样** | ✅ 这条成立 | borealis 的焦点系统正是干这个的，且已含 Switch 手柄支持 |
| B 站 API 层 → 红果接口 + C++ 签名 | ⚠️ 可做，但工作量在后半句 | 签名是纯 Kotlin、可移植；但**API 层不是"一层"**，见 §2.2 |

## 1. 环境实测：这台机器上的真实约束

这些都不是推测，是逐条跑出来的。它们决定了后面所有做法。

| 约束 | 证据 | 后果 |
|---|---|---|
| **本机 schannel 损坏** | `curl`/`git` 全部报 `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS` | HTTPS 只能走 Node 的 OpenSSL 栈，或给 git 显式加 `-c http.sslBackend=openssl` |
| **沙箱禁止命名管道** | msys2 的 `bash`/`make`/`git`/`pacman` 一律 `couldn't create signal pipe, Win32 error 5` | 所有 msys2 操作都要一次性提权；`git submodule update` 也因此不可用（内部调 `sh.exe`） |
| **工作区路径非 ASCII** | `<repo>`；gcc 会错乱非 ASCII 参数 | 构建必须经纯 ASCII 路径（用目录 junction 映射，源码仍留在工作区） |
| **ANSI 代码页是 GBK(936)** | PowerShell 5.1 `ParseFile` 把无 BOM 的 UTF-8 `.ps1` 按 GBK 解码 → 中文注释破坏语法；加 BOM 即通过 | `.ps1` 一律纯 ASCII，非 ASCII 路径走参数传入 |
| **devkitPro 仓库被 403** | `pkg.devkitpro.org` 任何路径都返回 Cloudflare `Attention Required!`（`cf-ray` 头），UA 无关；而 `api.github.com` 正常 | `dkp-pacman -S` 完全不可用，必须自建缺失的库 |
| **`raw.githubusercontent.com` 被墙** | `fetch failed`（同机 `github.com`/`codeload` 正常） | 取源码走 GitHub Contents API（`Accept: application/vnd.github.raw`） |
| **无 Docker、WSL 无发行版** | `docker` 不存在；`wsl -l -v` 只打印帮助 | wiliwili 官方推荐的 Docker 构建路线不可用 |

### 工具链现状

- devkitA64 GCC **16.1.0**、libnx 4.12.0、deko3d 0.5.0、CMake 4.0.2（msys2）、GNU Make 4.4.1
- **注意**：wiliwili 官方 CI 钉的是 `devkitpro/devkita64:20251117` 镜像，我们这里是 2026 年的更新工具链。
  GCC 16 + CMake 4 对老代码是已知风险点（CMake 4 已移除 `<3.5` 兼容，mbedtls 2.28 就因此翻车，需 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`）

## 2. 对原方案的三处修正

### 2.1 【最重要】视频流是加密的，mpv 不能直接播

Android 端的实际做法（`kotlin-tv/core/.../MediaCrypto.kt`）分两层：

1. **URL 是加密的**：上游返回的 `main_url` 是"Spade"加密 URL，要用 `key_seed` 做
   双重 SHA-512 派生密钥 + AES-CBC 解密，去掉填充和尾部 NUL，才得到真实地址。
2. **媒体内容是 CENC 加密的**：MP4 里是 `encv`/`enca` sample entry，需要从 `spade_a` 派生密钥，
   然后逐 sample 做 **AES-CTR** 解密。Kotlin 端甚至自己解析了 ISO-BMFF box 树
   （`moov/trak/stbl`、`saiz`/`saio`/`stsz`/`stsc`/`stco`,`co64`），支持子样本加密表，
   并从 `frma` 还原原始 codec fourcc。

好消息是它**没有**自定义混淆、没有 XXTEA/XOR、没有私有容器格式——**就是标准 CENC**。

#### 因此结论：不需要自写解密解复用器

我在下载到的 Switch 版静态库里直接验证了 ffmpeg 的能力（`findstr` 计数）：

| 检查项 | `libavformat.a` |
|---|---|
| `decryption_key`（mov 解复用器私有选项） | 3 处命中 |
| `senc` / `saiz` / `saio`（CENC 辅助信息 box） | 49 / 25 / 26 处 |
| `pssh` | 19 处 |
| `cbcs` | 1 处 |

且 `libmpv.a` 含 `demuxer-lavf-o`。所以可行路径是：

```
解密 URL  →  从 spade_a 派生 CENC 密钥  →  喂给 mpv：
   --http-header-fields="Referer: https://novel.snssdk.com/,User-Agent: <VIDEO_UA>"
   --demuxer-lavf-o=decryption_key=<hex>
```

mpv/ffmpeg 的 mov 解复用器原生认得 `encv`+`frma`，会自己处理 `senc`/`saiz`/`saio`。
**待实测确认**的是 mpv 0.36 的 `--demuxer-lavf-o` 传参路径能否把 `decryption_key` 送进 libavformat，
以及 CDN 的 Range/206 行为是否被 ffmpeg 的 http 协议满足（Android 端要求 206 + 匹配 `Content-Range`
+ `Accept-Encoding: identity`）。这两点只能拿真实链接验。

> 因此"少走几个月弯路"依然成立——省下的是**自写 CENC 解密解复用器**，但不是"一行不改"。

### 2.2 签名比预期好办，但"API 层"远不止一层

#### 好消息：签名是纯算法、可移植、有测试向量

`kotlin-tv/core/src/main/kotlin/com/hongguotv/core/Signer.kt` 是**纯 Kotlin，无 JNI、无 .so、
无 Frida、无外部签名服务、无硬编码 Bearer token**。它产出这些头：

`x-ss-req-ticket`、`x-tt-request-tag`、`x-khronos`、`x-ladon`、`x-argus`、`x-gorgon`、
`x-helios`、`x-medusa`、`x-tt-dt`、`sdk-version`、`passport-sdk-version` 等；
POST 还要 `x-ss-stub`（body 的大写 MD5）。

组成部件：`branch()`/`hashF13()`、`gorgon()`（RC4 + 半字节交换）、`medusa()`、
`helios()`（类 XTEA）。移植到 C/C++ 需要：

- **SM3（GB/T 32905）**——Kotlin 用 BouncyCastle，C 端要自己实现
- **`AesV3`——不是标准 AES**。它用一张 256 字节 S-box，按 `timestamp & 3` 选表，
  加一张置换顺序表，只做 2 轮。必须**逐字照搬**，不能"修正"成真 AES
- 硬编码常量：签名密钥、medusa 的 AES key/IV、版本字节、64 项 `hashTable`

**关键的验证闭环已经现成**：`Signer.kt` 只实现 branch 0，靠把 ticket 在 128 个偏移里试到
`branch()==0`（`Signer.kt:156-158`）。而 `kotlin-tv/core/src/test/resources/signing.json`
（16 KB）**已提交了 12 组真值向量**，每组含 `ts`/`url`/`body` 和 `hash`/`gorgon`/`helios`/`medusa`
四项期望值，由 `tools/signing-oracle.cjs` 用**确定的时钟 + 固定 LCG 随机数**生成。

这意味着 C++ 移植**可以完全在这台 Windows 机器上离线验证**，不需要 Switch、不需要联网。
这是整个项目里最容易做扎实的一环，也是应该最先做的一环。

#### 坏消息：上游接口是"签名 API + 网页抓取"的混合体

真正要替换的不是"B 站 API 层"这一个抽象层，而是：

| 用途 | 上游 | 方式 |
|---|---|---|
| 搜索 | `api5-normal-sinfonlinea.fqnovel.com/reading/bookapi/search/tab/v` | HTTP GET，**需签名** |
| 视频模型 | `api5-normal-sinfonlineb.fqnovel.com/novel/player/multi_video_model/v1/` | HTTP POST，**需签名** |
| 首页 / 分类 / 榜单 / 详情 | `hongguoduanju.com/category`、`/search/{kw}`、`/detail?series_id=`、`/rank/hot-comic-drama` | **HTML SSR 抓取**，从页面里抠 `_ROUTER_DATA` JSON 和 `<script>` |
| 封面图 | `Series.cover` 绝对 URL | 普通 GET，无特殊头 |

也就是说：**一半是签名 API，一半是解析网页**。前者是密码学问题，后者是脆弱的结构解析问题
（`ContentRepository.kt:154-164` 用大括号配对来抠 JSON）。

而且整个链路**没有任何账号体系**——无 cookie、无登录、无 session，观看记录只存本地。
这对移植反而是好事（少一大块）。但同时意味着**上游一改，签名和设备指纹就可能失效**。

设备指纹是硬编码的 Android/Redmi 参数（`VendorConstants.kt`）：`device_id`、`iid`、`aid=8662`、
`version_code=71332`、`device_type=25053RT47C`、`device_brand=Redmi` 等，连 proto 编码里的
经纬度浮点都是写死的。**Switch 端要不要继续伪装成 Redmi 手机，是必须做的产品决定**——
大概率必须，否则上游可能拒绝。

### 2.3 构建脚本不能原样跑

`scripts/build_switch.sh` 的逻辑本身没问题，但它依赖三件在本机不成立的事：

1. `curl -LO` 下载包 → 本机 curl 因 schannel 损坏不可用（改用 Node 已解决）
2. `dkp-pacman -U` / `-S` → 仓库 403（见 §1）
3. `cmake` / `make` 直接跑 → msys2 需提权，且源码路径必须 ASCII

另外 **wiliwili 依赖 10 个 git submodule**，其中 `library/borealis`（就是那套焦点导航 UI 框架）
必须正确取回。GitHub 的 zip **不含 submodule**，而 `git submodule update` 因需要 `sh.exe` 在本沙箱不可用
→ 必须用 `git ls-tree` 读出 gitlink SHA 后逐个手动克隆（已实现，见 `fetch-submodules.ps1`）。

| 项 | 值 |

**这一步跨过了"能编"到"能进 homebrew 二进制"之间的鸿沟。** 前 10 轮只做到 `-c` 编译（compile-only），
而链接会暴露完全不同的失败：缺失符号、ABI 不匹配、`__SWITCH__` 下独有的库依赖。
现在全部八个翻译单元加一个测试主程序一起链接通过。

**而且它不只是个链接证明**——`app/switch-test/main.c` 是一个真机可跑的自检程序：
在 Switch 上重跑签名器 12×5 字段、NIST CTR、spade 加解密、`_ROUTER_DATA` 抓取，
把结果打在屏幕上。**绿字本身就是证据**，不是打印一句写死的成功。

拷到 `sdmc:/switch/` 从 hbmenu 启动即可。这是"真机验证"里**逻辑层**那一半——
硬件相关的那一半（解码、渲染、手柄）还得靠 wiliwili 那侧。

#### 构建脚本对两个既有环境限制的复用

`scripts/build-switch-test.ps1` 沿用了本项目已经确立的两条规避：
非 ASCII 路径 → 在 `$env:TEMP` 的 ASCII 暂存目录里编译；
msys2 make 不可用 → 直接驱动 compile/link/elf2nro，不走 Makefile。
产物只回拷到工作区。它的 `-AppSrc` 把 `src/*.c`、`src/*.h`、`src/tests/*.h` 摊平复制，
因为测试用的生成头文件（`sign_vectors_gen.h`、`hg_media_vectors.h`）上游在 `tests/` 下。

### ★ 第 10 轮：网页抓取层

```
crypto: 21/21   signer: 60/60   cenc: 15/15   mp4: 13/13   router: 10/10
合计 119 项检查，0 失败；aarch64 compile OK ×8
```

红果有 **三个端点根本不返回 JSON**：首页、详情、榜单是服务端渲染页面，
真正的数据嵌在 `window._ROUTER_DATA = {...}` 里。`hg_router_extract()` 用大括号配对把它抠出来。

**唯一的难点**是字符串里的括号不能计入深度。剧集简介里出现 `}` 或转义引号是完全正常的，
而一旦算错，你会得到一个**被截断的、却仍然"解析成功"**的 JSON——失败表现是"内容为空"而不是报错。

这个测试直接对应 Kotlin 的 `routerParserHandlesEscapedQuotesAndNestedBraces` 用例。
另外加了 5 条拒绝路径（无标记、标记后无对象、括号不配对、缓冲区太小、键不存在），
以及"字符串里的 `]` 不计入深度"。

#### 必须说清的脆弱性

**这是整个移植里最脆弱的一块。** 它依赖上游的页面布局，而没有任何人承诺过那个布局稳定。
签名算法和 CENC 解密是协议、会稳定；网页抓取是 DOM 结构猜测、会变。
所以这一层**只用不同的错误码响亮地失败**，绝不返回半解析的文档——上游一改，报错好过悄悄给空数据。

#### 又一条我自己的测试期望错了

我最初断言 `hg_json_find_string(json, "loaderData", ...)` 应该成功。但 `loaderData` 的值是**对象**
不是字符串，而这个辅助函数的契约就是取**字符串**值——**它拒绝是对的，我的测试是错的**。
已改成断言"非字符串值被拒绝而非被弄坏"。

盘点一下：这已经是本轮系列里**第三次**"失败的是测试的期望而不是代码"
（前两次：64 位进位、`hg_ror64` 之外的隐式声明）。这不是巧合——
**把"我以为"写成断言，比写错实现更容易发生，而且更难发现。**

### ★ 全部纯计算组件完成（第 9 轮）

```
crypto: 21/21   signer: 60/60   cenc: 15/15   mp4: 13/13      ← 109 项检查全绿
aarch64 compile OK ×7，零警告
```

第 9 轮补上最后两块：`hg_spade_content_key()`（spade_a → 16 字节 CENC 内容密钥）
与 `hg_spade_decrypt_url()`（Spade 加密 URL → 明文）。这两块 **`MediaCryptoTest.kt` 并未覆盖**，
所以向量是从 JS 参考实现导出并构造的。

#### 这轮最值得记的一点：变换要**反推**，不能搜

`deriveContentKey` 的最后一步是 `Buffer.from(work[1..33].toString('ascii'), 'hex')`——
**32 个派生字节必须全部是十六进制字符**，随机输入被接受的概率约 `(22/256)^32`。
我最初写了 20000 次候选搜索，自然一个都没找到。

正确做法是**反转变换**：给定想要的 `work[i]` 和当前的 a/b 状态，可以解出唯一需要的输入字节
```
old = previous ^ ((work[i] + 21 + popcount(i)) & 255)
```
于是直接构造一个输入让输出恰好是 `0123456789abcdef...`。生成器里现在写的是这条反推路径，
并且**参考实现确认它返回了我设定的那个值**——这同时验证了反推和参考实现本身。

#### 两个真实收获

1. **穷举非对齐区间测试抓到了一个真 bug。** 我的 CTR skip 实现是"整块跳过并推进计数器"，
   而正确做法是**生成当前块后从块内第 `skip%16` 字节进入、不推进计数器**。
   `skip=1` 时前者会丢掉整整 16 字节。整块解密测试**通过**，只有从偏移 24 开始解 1 字节才暴露问题——
   **这正是 Kotlin 那边要写这个 sweep 的理由，也证明了它的价值。**
2. **一个我在动手前就拦下的语义陷阱**：`Sample.iv` 是 **16 字节**（aux 的前 8 字节 + 8 个零），
   而 `BigInteger(1, iv)` 把它当**完整 128 位大端数**——所以 **aux 的 8 字节是计数器的高半部分**，
   块索引填低半部分。我最初写的 `iv8` 辅助函数把两者放反了，会让**每一个样本都用错计数器解密**。
   现在改为忠实的 128 位加法 `hg_aes_counter_add`。

#### 一处我自己的测试写错了

`carry out of the top byte` 断言失败，但**是测试的期望错了**：`0xff + 1` 不会产生跨 64 位的进位
（低半必须全 1 才会）。代码是对的。已改成两条正确的断言：跨半进位、以及 2^128 回绕。

#### 顺带的设计选择

标准 AES 的 S-box **用数学方式生成**（GF(2⁸) 乘法逆元 + 仿射变换），而不是手抄 256 字节常量。
手抄错一个字节是 AES 最典型的静默 bug；推导出来的实现如果错了，FIPS-197 已知答案会**立刻失败**。
这次它一次就过了，说明生成路径正确。

1. **抽取顺序**。`buildMedusa` 消费 **5 次**随机数，顺序是

2. **`envLaunch`/`envPid` 是 `floor(random()*N)` 不是 `random()%N`**。

#### 必须记住的实测结论

1. **厂商的"RC4"不是 RC4**（`hongguo.cjs:360-364` 核实）。KSA 的 `s[i] = s[j]` **缺了交换的另一半**；
   PRGA 的 `i` 从 0 起**先自增**（首索引是 1）；密钥流取 **`s[(y+y)&255]`** 而非 `s[y]`。
   按 RFC 6229 实现会产出完全不同的头，**每一个签名请求都会失败**。
   这条不是我先发现的——是上一轮那个耗尽上下文的子代理留下的注释，我核实后确认它是对的。

2. **JS 里 `con` 是死代码，真正用的是 `con2`**（`hongguo.cjs:380-385` 逐处核对）。
   参考实现同时声明了 `con` 和 `con2`，两者下标 1 处不同（`[1,3,0,2]` vs `[2,0,3,1]`）。
   但 `addCon()`、`sub()`、`shiftCon()` **全部读 `con2`**——`con` 从未被引用。
   Kotlin 只保留了一张表（等于 `con2`），**因此是正确的**，不要照 `con` 去"修正"它。

3. **SM3 的长度域是 8 字节，不是 SHA-512 的 16 字节**。我一开始套用了 SHA-512 的填充结构，
   结果既算错摘要、又让 `pad[72]` 越界（padlen 可达 63，16 字节域需要 79 字节）。
   两条 SM3 向量当场失败，改对后通过——**向量测试在这里挡住了一次真实的缓冲区溢出**。

4. **AesV3 的轮密钥是 4 字节不是 16 字节**。参考实现里 `expanded` 存的是字节值，
   `keys` 是 12 个 4 元素切片。上一轮保留的头文件写 `HG_AESV3_KEY_LEN 192`
   （当"12 轮 × 16 字节"），**会越界读**；已改为 48，并把接口从裸数组换成
   `hg_aesv3_ctx`——因为 S-box 取哪 1/4 和两张置换表都由 `(timestamp & 3)` 决定，
   只传轮密钥不够用。

5. **表必须脚本生成**。`sbox` 是 1024 字节 base64、`hashTable` 64 项、UA 是 163/90 字符的精确匹配串、
   设备指纹 27 项。`gen_tables.mjs` 从 Kotlin 直接提取并**断言尺寸**（sbox ≠ 1024 字节就报错）。
   交叉验证：解出的 sbox 是 **0x00–0xff 的完整排列**，符合 S-box 的双射性质。

#### 两个隐蔽的工具链坑（都已修并注明）

- `@('-I' + $dir, '-o', $exe)` 在 PowerShell 里**不是**三元素数组：`+` 比 `,` 结合更紧，
  会被解析成 `'-I' + ($dir, '-o', $exe)`，**整个参数表拼成一个字符串**。
  表现为 TCC 报 "include file not found"，极易误判成非 ASCII 路径问题。已加括号。
- PowerShell 5.1 的 `>` 重定向**默认写 UTF-16LE**，生成的 `.h` 第一行就让编译器报
  `';' expected (got "/")`。已改为由生成器自己以 ASCII 写文件。

> 注意：GitHub 镜像归档的 sha256 是 `2f1e624e…`，**与 recipe 里钉的 `d029adbe…` 不同**。
> 这是归档打包工具差异（GitLab vs GitHub），不是源码不同——同一 tag。安装前应自行核对文件树，
> 不要盲目信任任一哈希。

### wiliwili 编译探针：三个已定位的问题（均已解决，留档）

1. **unity build 与 msys/非 ASCII 路径冲突** — msys2 的 `cmake` 是 msys 构建，传 `C:/...` 会被当相对路径；
   而 aarch64 gcc 是原生 Windows 程序、打不开 `/c/...`。unity 生成的 `includes` 正是 `/c/...` 形式。
   → `-DBRLS_UNITY_BUILD=OFF` 绕开。
2. **缺 GLM** — `borealis/.../nanovg/deko3d/dk_renderer.cpp` 需要 `<glm/vec2.hpp>`。
3. **`hacbrewpack` 是 Linux ELF** — 只服务 `BUILTIN_NSP` 的 NSP 转发器，却挡住整个主编译。
   → `-DBUILTIN_NSP=OFF`；NSP 打包另行解决。

> **`libborealis.a`（那套手柄焦点导航 UI 框架）与 wiliwili 全部 332 个目标文件都编译通过、零报错。**
> 这是"wiliwili 趟平了"这条判断最有力的正面证据：GCC 16 + CMake 4 并没有摧毁它。

### libfribidi：为什么要自己写一个

fribidi 官方 recipe 走 autotools，在本机两次失败于同一个怪点。`config.log` 显示
`aarch64-none-elf-gcc` 编译 conftest **成功**（`$? = 0`，`sizeof int = 4`），
但同一个 configure 稍后又用**无前缀**的名字去找 `gcc`/`cc`/`cl.exe` 并放弃。

与其继续跟 autotools 纠缠，更划算的做法是量化需求后替代：用 `aarch64-none-elf-nm -u` 查得
**libass 只需要 7 个 fribidi 符号**，ffmpeg 和 harfbuzz **一个都不需要**：

```
fribidi_get_bidi_types          fribidi_get_bracket_types
fribidi_get_joining_types       fribidi_get_par_embedding_levels_ex
fribidi_join_arabic             fribidi_reorder_line
fribidi_shape
```

这 7 个足以写一个**LTR 正确、RTL 降级**的最小实现（全部类型记为 LTR、嵌入层级恒为 0、
重排序为恒等映射、shape 空操作）。对中文短剧的字幕**没有任何影响**，
代价只是丢掉阿拉伯语/希伯来语的正确排版。这是一个**有意的、需记录在案的简化**，
不是"差不多就行"。头文件直接用源码包里的真实头（ABI 与 libass 编译时一致）。
源码包已解出，其中 `lib/fribidi-unicode-version.h` 已生成，只差 `fribidi-config.h`（由 `fribidi-config.h.in` 生成）。

## 4. 路线建议

### 第一优先：把签名器在 Windows 上做扎实（不需要 Switch）

这是全项目唯一**可以完全离线验证**的密码学组件，且是所有内容接口的前置条件。
做法：

1. 从 `signing.json` 用 Node 生成一个 C 头文件（避免在 C 里解析 JSON）
2. 写 `hg_crypto.{h,c}`：MD5、SHA-512、SM3、RC4、`AesV3`
3. 写 `hg_sign.{h,c}`：`branch` / `hashF13` / `gorgon` / `helios` / `medusa` + 请求头组装
4. 用 **TinyCC**（`<tcc.exe>`）编译运行，逐项断言 12 组向量的四个字段

**TCC 是 i386（32 位）**，`sizeof(long)==4` 而最终目标是 aarch64/LP64（`sizeof(long)==8`）
→ 只用定宽整数，禁用 `long` 和 `__int128`。同时用 devkitA64 gcc 做一次 `-c` 编译验证。

### 第二优先：确认 CENC 播放链路

拿一部真实剧的 `multi_video_model` 返回，验证：
- `key_seed` 解出的真实 URL 是否可直连
- 派生出的密钥喂给 mpv 的 `--demuxer-lavf-o=decryption_key=` 是否真能解码出画面

**这一步不做，整个移植的可行性就没有落地**——它是唯一"看画面"的判据。

### 第三优先：两条架构路线，建议先走 B

| | 路线 A：本机全实现 | 路线 B：伴生服务（推荐先行） |
|---|---|---|
| 做法 | 签名 + CENC 解密全在 Switch 上 C++ 实现 | 签名与取流放在 PC/NAS 上的 Node 服务，Switch 只做播放 |
| 参考 | — | hongguoTV 自带的 bridge 协议（`docs/API.md`）、`563617356/hongguo-tv`（Apple TV）、`dawei233/hongguo-monorepo`（NAS 后端） |
| 优点 | 单机、无依赖 | 上游接口一改，改服务即可，**不用重新签发 NRO**；签名算法留在易调试的环境 |
| 缺点 | 上游一变就要重刷；密码学 bug 全在设备上 | 需要局域网内一台常开的机器 |
| 风险 | 高 | 低 |

hongguoTV 自己的 `kotlin-tv` 是"直连上游"的，但它的 `docs/API.md` 已经把**面向客户端的服务协议**
定义好了（`/api/home`、`/api/search`、`/api/series/:id`、`/api/episodes/:id/play`），
Switch 端只要实现这个消费者即可——**这比移植密码学快得多**，而且不影响以后替换成路线 A。

## 5. 风险与许可证

| 风险 | 说明 |
|---|---|
| **上游脆弱** | 签名与设备指纹都是钉死版本（`version_code=71332`）的逆向产物，上游一改就可能全废。hongguoTV 自己也在 `PROJECT_STATUS.md:40` 承认"平台变化可能需要更新 APK" |
| **未在真机验证** | hongguoTV 的验收全部在模拟器完成，从未在物理 Android TV 上验证过硬解、音频、遥控器与长时间播放 |
| **GCC 16 / CMake 4** | wiliwili 官方钉 2025 镜像，本机是 2026 工具链，可能需要针对性修补 |
| **法律** | ⚠️ 见下 |

### 许可证：不是阻塞，但要说清楚

- hongguoTV 是 **GPL-3.0**；wiliwili 也是 **GPL-3.0**

- 二者合并**没有许可证冲突**，但整个产物必须是 **GPL-3.0**，且需保留 `NOTICE.md` 里的署名

> 需要更正一个容易搞混的点：GPL-3.0 与"Nintendo SDK 授权不兼容"在这里**不适用**——
> 这是 devkitPro/libnx 的 homebrew，不涉及任天堂官方 SDK。GPL-3.0 只是要求开源整个工程。

另外，**接口是逆向得来的**，与内容平台的条款可能存在冲突，这属于使用者的判断范围，不是技术问题。

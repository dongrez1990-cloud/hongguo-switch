# 搜索页（build38）

**做了**：主页按 **Y** 进搜索页；页面自己**呼出主机的系统键盘**（可拼音，见下）；结果列表可以打开详情页。
**状态**：已构建、已部署 `build38`，**待真机确认**。

## 1. 先说键盘："呼出虚拟键盘，英语的拼音输入" —— 用**系统键盘**，不自己画

这台机器上 borealis 已经包好了 libnx 的软件键盘：

```
brls::Application::getImeManager()            platform.hpp:227
  -> SwitchPlatform::getImeManager()          switch_platform.cpp:283
     -> SwitchImeManager                      switch_ime.cpp: SwkbdConfig + swkbdShow, SwkbdType_All
```

调用形状照抄 borealis 自己的 `views/cells/cell_input.cpp:30`：

```cpp
brls::Application::getImeManager()->openForText(
    [this](std::string text) { this->runSearch(text); },
    hg_tr(HG_T_SEARCH), hg_tr(HG_T_SEARCH_SUB), 40, this->query);
```

**系统键盘自带 IME**：敲拉丁字母由系统的拼音输入法出中文 —— 这正是用户说的"英语的拼音输入"。
自己画一个屏幕键盘意味着**再实现一套输入法**，而且是更差的一套，所以不做。

**焦点这件事在写之前就处理了**：搜索页在还没结果时，如果屏幕上只有文字和不可聚焦的滚动框，
框架**没有地方放焦点**，焦点会留在下面主页的卡片上 —— 这是这个项目已经记录过一次的回归
（"在详情页按 A 会不停打开新的详情页"）。所以页面上有一个**可聚焦的关键词按钮**
（第一次进来显示"按 A 输入关键词"，之后显示当前关键词），它既是唯一的聚焦点，也是用户真正需要的控件。

## 2. 数据源：**搜索页 HTML**，不是那个死掉的签名 API

签名搜索接口 200 + `Content-Length: 0`（`probe_search_cursor.mjs` / `probe_sources.mjs` 用参考实现本身复现过），
所以走站点自己的搜索页。这一轮**重新实测了一次**（`app/src/tools/probe_search_page.mjs`，现场跑的结果）：

```
GET https://hongguoduanju.com/search/ai
  status=200  html=214850b  router=23347b
  loaderData keys: "search_layout" -> null
                   "search_(keyword)/page" -> object {req, query, isSuccess, searchList,
                                                     totalCount, accessibleEpisodeCnt}
  searchList: 10 项
  条目字段: doc_type, name, keyword, video_data, user_info, video_list
  video_data 字段: series_id, episode_cnt, create_time, series_status, pay_type, series_title,
                   series_intro, series_cover, episode_right_text, vid_list, hot_score_data,
                   category_list, celebrities, genre, favorite_text, like_text
  totalCount = "201"
```

**三条关键事实**（都是实测，不是从别的页面推断的）：

1. **卡片字段在 `video_data` 里面**：条目的 `name` = 标题、`keyword` = ID，而
   `video_data.series_id` / `series_title` / `series_cover` / `category_list` / `episode_right_text`
   和首页卡片**同名**。
2. **所以按形状找内容的老办法在这一页找不到东西**：本文件里两处"看这个数组像不像剧集"的判断
   都要求**条目自己**带 `series_id`/`series_name`/`series_cover`，而这一页一个都没有 ——
   这就是当初"搜索页没有内容列表"的结论（而页面其实有 108 条）。
3. **没有第二页**：`/search/ai?page=2` **逐条返回第一页**；HTML 里也没有游标字段（只有 `totalCount`）。
   所以结果列表**显示 10 条**，而状态栏老实写成"显示 10 条（共 201 条）"，
   而不是假装那就是全部。

另外实测到一个上游现象：**同一个关键词会偶发 500**（"重生"连续 500、"短剧"和"ai"正常，
同一条 URL 再跑又可能 200）。所以搜索失败时页面**报错误原因**，不会显示成"没有找到"
——这两个是不同的事实。

## 3. 这一路上抓到并修掉的一个真 bug（会让搜索页永远显示"没有结果"）

`collect_array`（`hg_api.c`）在遍历一个对象时，**只要看到 `video_list` 就往下钻**（因为首页的分区
结构是 `section.video_list[]`）。而**搜索页每一条结果都带一个空的 `video_list`:[]** ——
于是它钻进空数组、什么都没收、**从来没看过条目本身**，整页解析成 `HG_API_ERR_EMPTY`。

修法：**只往非空的 `video_list` 里钻**（空数组本来就没什么可贡献的）。
主机测试里那条 `two usable hits parsed from searchList` 就是为它写的，也是它先失败才暴露出来的。

同时 `series_from_card` 学会了**剥开 `video_data`**：卡片层没有 `series_id` 时，就把内层对象
交给**同一个函数**解析（内层的字段名和首页完全一样），所以没有第二套字段抽取代码。

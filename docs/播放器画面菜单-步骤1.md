# 第 1 步：播放器内画面调节菜单（X）

交接文档 §二 的第 1 步。**代码已完成、已部署、未上机**——
真机验证需要按 §四 的观察点看一眼屏幕（本项目一贯的规矩：构建机能编译，但看不到主机屏幕）。

## 一、做了什么

播放页按 **X** 弹出右侧面板，8 行：

| 行 | 值 | mpv 属性 | 出处 |
|---|---|---|---|
| 亮度 Brightness | −100..100，0 中性 | `brightness` | wiliwili `setBrightness` `mpv_core.cpp:1263` |
| 对比度 Contrast | 同上 | `contrast` | `:1270` |
| 饱和度 Saturation | 同上 | `saturation` | `:1277` |
| 伽马 Gamma | 同上 | `gamma` | `:1284` |
| 色相 Hue | 同上 | `hue` | `:1291` |
| 画面比例 Aspect | Auto / Crop / Stretch | `keepaspect` + `video-aspect-override` + `panscan` 三件套 | `setAspect` `:1225` |
| 镜像 Mirror | On / Off | `vf=hflip` | `setMirror` `:1246` |
| 全部重置 Reset | —— | 上面 7 项回默认 | `player_setting.cpp:284-291` |

按键（面板打开时）：

| 键 | 行为 |
|---|---|
| X | 开／关；**开启时立即把当前值写进 mpv** |
| ↑ / ↓ | 移动高亮行（循环） |
| ← / → | 精确步进 ±1 |
| LB / RB | 粗步进 ±5（同 seek 的 6 倍关系） |
| A / B | 关闭面板 |

按住可连发（首次 400 ms，之后每 90 ms）。

## 二、四个关键决定，都有理由

### 1. 面板**不可聚焦**，这是整件事的前提

自然的选择是 `brls::Slider`，而它是这个屏幕上**唯一不能用**的控件：

```cpp
View* Slider::getDefaultFocus() { return pointer; }   // slider.cpp:119  无条件
void Slider::buttonsProcessing() { if (pointer->isFocused()) ... }  // slider.cpp:130
```

`pointer` 构造时就是可聚焦的，而 `getDefaultFocus()` **无条件**返回它——
所以只要屏幕上有 Slider，borealis 的焦点搜索就可能落到它身上，`buttonsProcessing()`
随即吃掉 **LEFT/RIGHT**，而那正是本播放器用来 seek 的两个键。
症状是"seek 键坏了"，而"按键是坏的还是没收到"这个项目已经耗过一整轮。

**所以面板里没有一个可聚焦视图，也没有注册任何 action**：全是 `Box` + `Label`，
所有按键在 `PlayerView::draw()` 里**每帧读原始手柄状态**（和 hold-seek 曲线同一套机制）。
附带的好处：`View::isFocusable()` 是 `focusable && visibility == VISIBLE`，
所以隐藏的面板不只是看不见，而是**结构上不可能参与焦点竞争**。

### 2. 逻辑放 C 层，主机可测

行、范围、夹紧、循环、以及"aspect 一个整数 → mpv 三个属性"的映射，全在 `app/src/hg_pmenu.c`，
配套 82 项主机测试。理由和当初把行模型放进 C 一样：**索引/映射错了是静默的**，
而这个项目为此崩过一次控制台（无任何信息）。

其中最重要的一组测试是映射：`hg_pmenu_aspect_props()` **无条件写满三个属性**。
如果只写变化的那一个，"Stretch" 会留下一个又拉伸又带黑边的画面——
看起来像播放器坏了，而不像设置错了。

### 3. 打开菜单时**立即应用**，这是 cfg 退路成立的条件

`player.brightness=-20` 写在 `hongguo.cfg` 里，只有按下 X 那一刻才进 mpv。
所以：**一次按键 = 显示状态 + 让状态生效 + 日志记录用的是哪条臂**，不用重编译。

### 4. 菜单**不写文件**

`hongguo.cfg` 对本 App 是只读的（写入走设置界面的轮转+改名路径，见 `hg_cfg.hpp`）。
所以菜单是"每集生效"，而**文件才是持久化手段**——
`player.*` 那几个键既是种子也是退路，一个存储而不是两个会互相矛盾的。

## 三、退路（不用重编译）

| 退路 | 效果 |
|---|---|
| `player.menu=no` | **整个功能关闭**：X 不响应、也不在底栏提示 |
| 不按 X | 菜单是纯增量：不按就与改动前**完全一致**（默认全 0 / auto / off） |
| 面板里 Reset | 值回中性，画面立刻回到原始观感 |

打开菜单时会把底部信息行与进度条**临时**隐藏（面板是不透明的，会盖住它们）；
Y 的显示/隐藏状态**不被改写**，关掉菜单后恢复成用户原来的选择——
否则菜单会静默地抵消一次 Y。

## 四、观察点（真机怎么看／日志怎么读）

**屏幕**：按 X → 右侧出现深色面板，8 行，高亮行是青色底；按 ←/→ 数字变；
调亮度后**画面肉眼变亮**；按 B 面板消失、画面保持已调的状态。

**日志**（`sdmc:/switch/hongguo.log`），每一条都印证一件事：

```
PLAYERMENU: panel built (8 rows, w=460, non-focusable)     面板建出来了
PLAYERMENU: seeded from cfg -- bright=.. contrast=.. ...    读到了哪个臂
PLAYERMENU: X -> OPEN (row=0, cfg-seeded=0)                 按键收到了
PLAYERMENU: brightness = 20 -> set rc=0, read back 20 (rc=0)  写入且回读一致
PLAYERMENU: keepaspect = yes -> set rc=0, read back 'yes' (rc=0)
PLAYERMENU: vf = 'hflip' -> set rc=0, read back 'hflip' (rc=0)
PLAYER: overlay hidden because the picture menu is open
```

**为什么每次都回读**：`set rc=0` 只证明 mpv **接受**了这次写入。
写入被接受然后什么都没发生（属性名对该 mpv 构建不存在、还没有视频轨），
外观与成功**一模一样**——这个项目栽过好几次，所以回读值直接进日志。

判读：

| 现象 | 结论 |
|---|---|
| `set rc=0` 但 `read back` 不同 | 属性被拒或该 mpv 不支持 → 看回读值 |
| `apply IGNORED -- mpv is not started yet` | X 按得太早（worker 线程还没建 mpv），再按一次 |
| 完全没有 `X -> OPEN` | 按键没到（先查 `player.menu=no`） |
| 有日志但屏幕不动 | 面板没画出来 → 查 nanovg 绘制顺序 |

## 五、代价与已知取舍

- **画面调节在软件渲染路径上生效**（本 App 跑 `hwdec=no`），此时滤镜链一定经过。
  wiliwili 在开镜像时还会把 hwdec 切成 `auto-copy`（`setHwdecCopyMode`，`mpv_core.cpp:1254`），
  因为直连硬解会绕过滤镜——本 App 是软解，所以**没有复制那一半**，日志里的回读会暴露它是否需要。
- **步进是 5 而不是 wiliwili 的 10**：它的滑杆 0..1、步长 0.05、换算 `(int)(pos*200-100)` ⇒ 每步 10。
  这里没有滑杆，值就是状态，5 已经肉眼可见，20 次覆盖全量程。
- **不持久化**：见 §二.4。wiliwili 是每季存档并写回配置的。
- **`overlay=no` 诊断臂下菜单也不响应**：那条臂连 `Box::draw` 都不调用，
  按设计就只剩裸视频。这是有意的，不是缺陷。

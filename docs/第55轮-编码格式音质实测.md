# 第 55 轮：C4 / C5 / C6 实测 —— 两项是"上游没有"，一项改成"显示编码"（build55）

这一轮没有先写代码，**先量**：C4（视频格式）/ C5（视频编码）/ C6（音质）能不能做，取决于上游给不给多个可选值。
量完的结论推翻了两项、改写了第三项 —— 这正是先量的意义。

---

## 一、实测：从**两份已抓取的真实响应**里量（不联网、不重放签名）

`app/src/tests/fixtures/video_model.json` 与 `video_model_h264.json` 是同一集、两次抓取的播放模型：

| 档位 | `video_model.json` | `video_model_h264.json` |
|---|---|---|
| 360p | bytevc2 | **h264** |
| 480p / 540p / 720p | bytevc2 | bytevc2（720p 另有一条 h264） |
| 1080p | **bytevc1** | bytevc1 |

其它同时量到的：

- **`vtype` 全部是 `mp4`**（两个文件、每一条源）→ 没有 FLV 之类可选；
- 两份响应的请求 URL 里**都是 `codec_type=4`** → 差异**不是**这个参数造成的；
- **音频相关字段出现 0 次**（`audio` / `audio_quality` / `dobly` / `hi_res` / `audio_list` 全部 0）。

## 二、结论

| 待办 | 判定 | 依据 |
|---|---|---|
| **C4 视频格式**（DASH/FLV） | ❌ **上游只有一个** | 每条源 `vtype=mp4`；没有第二种容器 → 做成下拉框就是只有一项的假菜单 |
| **C6 视频音质**（杜比/Hi-Res/高/中/低） | ❌ **上游只有一个音轨** | 模型里音频字段 0 次出现；本 App 一直是 `audio-channels=stereo` |
| **C5 视频编码**（AVC/HEVC/AV1） | 🔧 **做成"显示"而不是"选择"** | **编码是按档位固定给的**（同一档没有第二种可选），而且 1080p **只有 bytevc1（HEVC）** —— 这恰好是 §2.4 卡顿最可能的原因 |

**C5 之所以值得做**：用户现在能**看见**自己在看什么编码。1080p 那条只有 HEVC，而本项目走软件解码路径，
HEVC 比 H.264 贵得多 —— 所以"1080p 卡"这件事，现在在清晰度行上就写得明明白白。

## 三、实现：编码进入档位标签

- `HgQualityTier` 新增 `codec[16]`，由 `hg_quality_build` 从源的 `codec_type` 填（并行数组多一个参数）；
- `hg_quality_label` 在档位名后追加 **`  ·  HEVC`** / **`  ·  H.264`**；
- **`bytevc2` 保持上游自己的拼写**：它的真实身份**没有实测**，给它编一个友好名字就是把猜测印在屏幕上；
- `Codec` 也带进了 `Client::QualityTier`，所以控制条的清晰度方块与 X 菜单的清晰度行都会显示它。

**新增 6 项测试**，其中 4 项在实现的第一版就**抓到一个真 bug**：我写 `putStr(buf + len, …)` 时
`len` 还是 0 → 编码**覆盖**了档位名而不是追加，菜单会显示成"  ·  HEVC"。
**另有 1 项抓到我把测试数据顺序写反**（FIX 是低→高、ladder 排成高→低）。
这两次都是"缓冲区算术"这类最容易悄悄错的东西。

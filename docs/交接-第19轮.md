> ### 本文里**已被实测推翻**的三处
>
> 1. **§2.4/§2.5 关于解码的说法要分开看**：`hwdec` 是 **cfg 项**，两次真机日志各见过一种 ——
>    `build32` 那次是 `HARDWARE (nvtegra-copy)`，而我最近取回的那次是 **`CFG: option hwdec = 'no'`（软解）**。
>    结论：**不要把它当成固定事实，去读当时那次运行的 cfg**。
> 2. **§2.5「滤镜改了没变化」根因已找到并修复（`build60`）**：不是硬解绕过滤镜
>    （`hwdec=no` 时根本没有硬解），而是 **这个 App 用 `MPV_RENDER_API_TYPE_SW` 软件渲染**，
>    而 mpv 的 brightness/contrast/… 五个属性是 **GPU 视频链的 shader 参数** —— **软件路径没有那一级**，
>    所以"写入成功、读回正确、画面不变"。修法是改用 ffmpeg 的 `eq`/`hue` **滤镜**表达同一件事。
>    见 `docs/第60轮-画面滤镜根因与修复.md`。
> 3. **§3.5 的 `hacbrewpack --icon`**：该工具**没有**这个开关（`--help` 实测），图标是控制区文件。

> ### 一条新增的硬规矩（`build65` 审计得出）
>
> **谁销毁视图，谁必须先移开焦点。** borealis 的删除池
> （`application.cpp:209-224`）会 `delete` 视图，但**不会清 `Application::currentFocus`** ——
> 所以"重建网格/列表"这类操作如果恰好销毁了当前聚焦的那个视图，框架手里就留下一个**悬空指针**，
> 下一次按键或绘制会走到已释放内存上。`View::ptrLock` 保护的是回调，**不保护焦点**。
>
> 已经合规的有：主页（`applyHome` 后 `giveFocus`）、搜索（结果到达后聚焦）、分类（第 1 页后聚焦，
> 后续页是追加）、详情（`setEpisodes` 后立刻聚焦）。`build65` 修掉了唯一一处不合规的
> —— 收藏/历史页**切标签**时（触屏点标签不会先把焦点移到标签上）。修法是**只在该移的时候移**：
> 用 `focusIsInside()` 判断"焦点原本是否在将被销毁的子树里"，是才搬。
> 见 `docs/第65轮-重建视图必须先移开焦点.md`。

## 2. 现在什么坏了，以及**已查到的根因**

### 2.1 设置界面一改任何一项就闪退 —— **已修（`build27`），真机确认**

**根因：一个悬垂引用，而且是我把一个正确的写法改坏的。**

```cpp
cell->init(rowLabel(*row), shown, cur, [&row, opts, offList](int index) {
                                      ^^^^^ 捕获的是局部变量的引用
```

`row` 是 **`const Row*` 参数**，`[&row]` 捕获的是**这个栈上变量的引用**。
`addRow` 一返回它就失效 —— **而回调只在用户切换那一项时才执行**。

**这完美对应症状**：打开设置界面不崩（回调还没执行）→ **一改就崩**（读到悬垂引用）→
**崩溃没有规律**（读栈上残留，有时恰好还是旧值就不崩）→ **日志里什么都没有**（进程死在 logger 之前）。

**修法**：改回 `[row, opts, offList]`（**按值捕获指针**）。表是静态的，指针永久有效。

**这是回归**：上一代代码本来就是按值捕获，我在改中文标签时改成了按引用。
**已经全局搜索过**：`app/hongguo/` 下只剩一个 `[&...]`，在 `hg_thread.cpp:115` 的
`std::thread` 死路径里（那套工具链上永远抛异常，从不执行）。

#### 2.2.4 **下一步：把"上下"作为独立的小补丁加回来（不要接管导航）**

这是本文件对下个会话最重要的指示。

**为什么上下不能靠框架**：框架的 `Box::getNextFocus` 是**按插入顺序遍历**的走法，
**做不到"往下一行、同一列"**。这正是我当初接管导航的理由 —— 而接管**整体**就是错误所在。

**推荐做法（按可行性排序）**：

1. **只给上下加一个补丁**：保留框架对左右的遍历，另外**只拦截 UP/DOWN** 两种方向，
   由网格自己算"相邻行的最近列"并 `giveFocus`。**左右完全不放自己手里。**
   这样即使补丁算错，坏的也只是上下，左右不受影响 —— 而这次坏就坏在"整体接管"。
2. 或者**接受只有左右**，把上下改成用肩键 / 摇杆纵轴翻页。

**不论选哪种，两条硬约束**：

- **绝不能让"框架遍历"和"自己的移动"同时对同一个按键生效** —— 这就是两格的成因
  （`application.cpp:386-403` 的派发 + `draw()` 里的轮询，两个都动了）。
- **改完必须真机确认左右没被弄坏** —— 回退证明了左右本来是好的。

#### 2.2.5 保留的技术调查（**仍有价值，但都是"为什么我的补丁无效"**）

**框架的重复派发机制**（`application.cpp:386-403`）：

```cpp
if (!oldControllerState.buttons[i])
    controllerState.repeatingButtonStop[i] = cpuTime + BUTTOM_REPEAT_TRIGGER;   // 重置 250 ms
if (!oldControllerState.buttons[i] || repeating)
    Application::onControllerButtonPressed(i, repeating);                       // 重新派发
```

**如果按键读数在按下/松开之间闪烁**（`oldControllerState` 时真时假），那么每次都满足
`!oldControllerState.buttons[i]` → `repeating` 被算成 **false** → **被当成"全新按下"重新派发** →
而 `navigate()` 的防重复检查 `if (repeating && repetitionOldFocus == currentFocus) return;`
**因为 `repeating==false` 而不生效**。

**这就是日志里 `moveFocus` 每 183 ms 被调用一次的原因** —— 一次物理按住被框架派发成多次"新按下"。
摇杆的伪按键会闪烁，因为 libnx 把它们折进了和 D-Pad 同一个 `AnyUp` 掩码（`hid.h:294`）。

**这一条在"上下补丁"里仍然要注意**：**如果补丁依赖 `getNextFocus`，它会在同一个闪烁下被多调**；
所以要**在补丁里自己做防抖**（要求松开持续 ≥300 ms 才算松开），而不是信任这一帧的读数。

**以下是最初的记录，保留作为"我为什么在错误的方向上花了五轮"的证据：**

#### 根因一：框架的导航没有被真正取消（已修，`build28`）

`getNextFocus` 原来返回 `nullptr`，但框架拿到 `nullptr` 之后走的是**报错 + 抖动**那条路
（`application.cpp:564-570`），**它整个导航流程仍然为每次按键跑了一遍**，
而 `draw()` 里的轮询又自己动一次。

**修法：返回 `currentView`（焦点自己）**。框架派发的最后一句是

```cpp
if (nextFocus->getDefaultFocus() && getCurrentFocus() != nextFocus->getDefaultFocus())
    giveFocus(nextFocus);
```

返回自己 → 比较相等 → **不调 `giveFocus`、不报错音、不抖动** → 框架成为真正的空操作。

#### 根因二：两个重复计时器（`build29` 已修）

- 框架自己的重复：`application.cpp:65-66`（250 ms 后每 100 ms）
- 我的轮询自己的重复：`HG_NAV_REPEAT_DELAY_MS` / `HG_NAV_REPEAT_PERIOD_MS`（400 ms 后每 120 ms）

**同一个"按住"的动作有两个东西在推进。**

#### 根因三（真正的机制）：闸门窗口和重复间隔互相咬住

实测数字放在一起就清楚了：

| 量 | 值 |
|---|---|
| 主机按键重复间隔（**用户实测**） | **133–183 ms** |
| 我最后一道闸门窗口 | 250 ms（**比重复间隔还长**） |
| 我的轮询重复延迟 | 400 ms |

**闸门（250 ms）把重复吃掉了，所以轮询永远到不了 400 ms** ——
于是"按住连发"这条路**根本走不通**，我唯一能拿到第二格的方法就是**再按一次**。
**每一次"两格"其实是用户按了两下**，这正好对上他最精确的那句观察：
「**速度够快就能一格一格**」（快按间隔大、慢按间隔小，落在闸门的两侧）。

**这就是"闸门治标不治本"的结构性原因：闸门分不清"用户又按了一次"和"系统重复了一次"。**
无论窗口取多少，总有一类情况是错的 —— 所以四道闸门全部失败。

#### `build29` 的修法：只认"按下"这个边沿

两个网格的 `draw()` 现在自己做边沿检测：

```cpp
static int heldDir = 0;
const int dir = hg::navPollInput();
if (dir == 0)              heldDir = 0;             /* 松开：清状态 */
else if (dir != heldDir) { heldDir = dir; 移动; }   /* 从松到按：只有这一次算按键 */
```

**这是关于输入的事实，不是关于时间的猜测** —— 任何来源的重复都不会产生"边沿"。
同时 `navPollInput` 里的重复逻辑**已删除**，全项目**只剩一处**决定"什么算一次按键"。

**代价（诚实记录）**：**按住方向键不再连续移动**。用户的抱怨是步进准确性，
不是按住滚动，而准确性要求"重复来源唯一"。

**如果 `build29` 之后仍有两格，下一个会话不要再加闸门**，先确认两件事：
① `getNextFocus` 是否真的没被再调用（加一行日志即可）；
② 是否还有第三处在调 `moveFocus`（目前全局只有 `draw()` 的两处）。

#### 3.8.4 收藏界面：**做类似排版，包含历史记录和收藏**

**用户原话**：「**收藏界面做类似的排版，包含历史记录和收藏**」。对照图 5 是 wiliwili 的"我的"页：

```
[侧边栏]  [头像][昵称]   [206 动态][661 关注][89 粉丝][915.5 硬币]
          [历史记录][我的收藏][我的订阅][我的追番][我的追剧][稍后再看]   ← 横向标签
          ┌────┬────┬────┬────┐
          │封面│封面│封面│封面│   每张带：左上"今天 08:19"、右下"00:04/00:59"、
          └────┴────┴────┴────┘             下方标题、下方 UP 名
```

**本 App 对应的实现**（**数据层已完成、92 项测试**，见 `hg_history.h/.c`）：

- **标签只做两个**：`历史记录` + `我的收藏`。订阅 / 追番 / 追剧 / 稍后再看
  **全部依赖账号体系，而本 App 没有登录**（上游也没有）。**不要假装提供五个标签。**
- **统计栏（动态/关注/粉丝/硬币）不做** —— 同上
- **每张卡片显示**（数据都在 `HgHistoryEntry` 里，都已实现）：
  - **封面**（`cover`）
  - **标题**（`title`）
  - **进度** `00:04/00:59` → **用 `hg_fmt_clock()`**（有测试）
  - **时间** `今天 08:19` / `3 分钟前` → **用 `hg_fmt_age()`**（有测试，中英双语）
  - **第几集**（`episodeLabel`，如"13"）
- **X 键 = 刷新**（对照图底部 `X 刷新历史记录`）—— 对本地数据是**重读文件**，不是网络请求
- **收藏页与详情页/播放页的收藏按钮共用同一份本地列表**（`hg_fav_add/remove/find`）

## 4. 这个项目的硬规矩（违反过会付出代价）

1. **源码必须纯 ASCII**。构建机是 GBK/936，非 ASCII 源码会以乱码进编译器。
   中文一律写成 `\xNN` 字节转义（见 `hg_lang.c`）。**已因此踩过三次**。
2. **零警告**。构建结果是要用眼睛读的，"大概没事的警告"会训练读者跳过下一个。
3. **不要改 `upstream/`**。那是只读参照树，至今没有任何一处被修改过。
4. **每个构建带 `[buildNN]` 标记**，部署后读回验证（§0）。
5. **不要在 `registerAction` 回调里直接 `popActivity()`** —— 会 use-after-free
   （回调注册在自己身上，pop 会销毁自己）。已经修了三处，**必须 `brls::sync` 推迟一帧**。
   详见 `detail_activity.cpp` 的注释和 `application.cpp:201-204` 的顺序证明。
6. **加改动前先加日志、取回来再改**。我这几轮连续四次在"输入走哪条路"上判断错误，
   每次都是靠日志才纠正 —— 读代码猜不可靠。
7. **不要一次改多件界面骨架的事**。这一轮我改出两次崩溃（GPU、B 键），
   原因都是上下文不足时硬塞改动。

# 真机修复记录（红果短剧 Switch 移植）

这份文件只记录**在真机上被观察到、并被证据定位**的问题，以及每条的证据来源。
每一条都区分「现象」「证据」「根因」「修法」。凡是没有真机证据的推理，一律标注为推测。

时间：同一会话内连续多轮上机。

---

## 0. 起点与终点

**起点**：`out/hongguo.nro`（26,761,240 字节）在真机上**启动瞬间闪退**，无提示。
交接文档判定的两个嫌疑是「`createContentView()` 里的分离线程」和「视图构造」。

**终点**：真机上 —— 首页 36 张卡片 → 详情页 76 集 → 按 A 播放，**画面出现、声音出现（`ao=hos`）**，
B 返回正常、焦点正常、播放稳定运行（实测连续 120 秒、`time-pos` 到 120.5s）。

## 1. `std::thread` 构造抛 ENOSYS → 进程 abort

**现象**：启动瞬间闪退，屏幕上什么都来不及显示。

**证据**（`sdmc:/switch/hongguo.log`，逐行 fsync，崩溃不丢）：

```
HOME: setDataSource done (rows now = 0)
HOME: ENTER std::thread(...).detach()
FATAL std::terminate reached (uncaught exception or explicit call)
FATAL exception what() = Function not implemented
```

**根因**（读二进制得到，不是推理）：

| 事实 | 位置 |
|---|---|
| `std::thread::_M_start_thread` 调 `pthread_create`，返回非 0 就 `__throw_system_error(w0)` | `hongguo.elf 0x11bfac0` / `0x11bfac4` |
| `pthread_create` 只有两处返回 ENOSYS(88)，都在 `__syscall_thread_create` 的 GOT 槽为 0 时 | `libsysbase.a:pthread.o` 偏移 `0x74`/`0x88`：`mov w0, #0x58` |
| libnx 的 `__syscall_thread_create` **没有** ENOSYS 出口（只有 22=EINVAL、12=ENOMEM、1） | 反汇编 `hongguo.elf 0x10c6a70` |
| `libpthread.a` 里只有一个 `dummy.o`，**连符号表都是空的** | `ar t` + `readelf -sW` |

**修法**：新增 `app/hongguo/hg_thread.{hpp,cpp}`，用 libnx `threadCreate`/`threadStart` 实现
`hg::runDetached()`；`home_activity` / `detail_activity` / `player_view` 三处全部替换。
创建失败时**回退成同步抓取**，而不是留一个永远"Loading..."的页面。

**附带发现**：borealis 自己的任务线程 `Threading::Threading()` 也用 `pthread_create`
（`core/thread.cpp:217`）且**忽略返回值**，所以 `brls::async()` 在这套构建里从来没跑过。
`brls::sync()` 不受影响（它只是主循环排空的队列 + 一把可用的 mutex）。

**真机复核**（诊断版自带自检，同一次运行里对比两个 API）：

```
SELFTEST std::thread: no throw; body ran=1
SELFTEST threadCreate: rc=0x00000000 / threadStart rc=0x00000000 / body ran=1
```

> 注意：`std::thread` 在**链接了 libnx `threadCreate` 之后**就通了。也就是说这条修复的真正
> 机制是链接层面的（GOT 重定位 / 弱符号），而 `hg::runDetached` 是同时提供的保险。

## 2. 0 行的 `RecyclerFrame` 首次布局越界

**现象**：修好线程后，崩溃点后移——Stage A（裸 Label 活动）连续 60 帧正常，
Stage B（真正的 HomeActivity）在布局之后死掉，日志停在 `Cell #0 - added`。

**证据**（borealis 源码）：

- `RecyclerFrame::reloadData()` 无条件调用 `selectRowAt(defaultCellFocus, false)`（`recycler.cpp:270`）
- `selectRowAt` 的循环 `for (int i = -1; i <= indexPath.row; i++) offset += cacheFramesData[count++].height`（`recycler.cpp:319-320`）
  —— `row = 0` 时读 `cacheFramesData[0]` **和 `[1]`**
- 而 `cacheCellFrames()` 对 0 行列表只 push **1** 项（`recycler.cpp:341-367`：只有 `row == -1` 那一趟表头）
- `selectRowAt` 头上自带 `// TODO: Implement it normally`（`recycler.cpp:307`）

**修法**：**视图先建，`dataSource` 后挂**。
`ReloadData` 整段主体（含 `selectRowAt`）都在 `if (dataSource)` 内，所以 `dataSource == nullptr`
的 RecyclerFrame 布局时是空框、**永远走不到越界那条路**。数据到了再 `setDataSource` + `reloadData`。

## 3. 焦点回归（本条是修 #2 时自己引入的）

**现象**：详情页显示了 76 集，但按 A 不播放，而是**又打开一个详情页**，屏幕停在 `Loading episodes...`。

**证据**（日志）：

```
Pushing hg::HomeCell to the focus stack          ← 每次按 A 都是"首页的格子"在响应
DETAIL: ENTER createContentView; list waits for rows
DTH: thread started for series 7527125460430375961   ← 另一个 series id
```

而整份日志里**从未出现 `Giving focus to hg::EpisodeCell`**。

**根因**：把 `RecyclerFrame` 改成"拿到数据才 addView"之后，`pushActivity` 那一刻活动视图里
**没有任何可聚焦控件**，borealis 的焦点就留在上一个活动的 `HomeCell` 上。

**修法**：视图从 `createContentView` 起就存在（满足焦点），但**先不给 dataSource**（满足 #2），
数据到达后 `setDataSource` + `reloadData` + `brls::Application::giveFocus(frame)`。
两条要求能同时满足，靠的就是 #2 里那个 `if (dataSource)` 保护。

**真机复核**：`Giving focus to hg::EpisodeCell, and removing it from the focus stack`。

## 4. `MPV_RENDER_PARAM_DEKO3D_FBO` 传错类型

**现象**：播放器界面能建起来、能画出文字，但**一渲染就整进程死掉**，无任何提示。

**根因**：该参数要的是 `mpv_deko3d_fbo*`
（`C:/devkitPro/portlibs/switch/include/mpv/render_dk3d.h`）：

```c
typedef struct mpv_deko3d_fbo {
    DkImage *tex;
    DkFence *ready_fence;
    DkFence *done_fence;
    int w, h;
    DkImageFormat format;
} mpv_deko3d_fbo;
```

而我们传的是**一个裸 `dk::Image*`**。mpv 于是把 image 对象的前几个字节当成纹理指针、
接着当成两个 fence 指针、再把后面当成长宽和格式——**每个字段都是垃圾**。

**修法**：`Impl` 里持有真正的 `mpv_deko3d_fbo` 与两个 `DkFence`，`fbo` 建好一次
（`tex` 每帧只改这一项），fence 指针一次性写入；每次绘制 `queueSignalFence(ready)` →
`queueFlush` → render → `queueWaitFence(done)` → `report_swap`。
这与 wiliwili 完全一致（`mpv_core.hpp:423-429`、`mpv_core.cpp:826-834`）。

**定位这条用的对照实验**（值得记住）：把 cfg 里加上 `renderctx=no` + `vo=null`，
也就是 play-test 那套**已被证明能解码**的配置搬进 App，结果：

```
MPVLOG [cplayer/info]  (+) Video --vid=1 (*) (hevc 360x640 30.000fps)
MPVLOG [cplayer/info]  (+) Audio --aid=1 (*) (aac 2ch 44100Hz)
MPVLOG [cplayer/info] AO: [null] 44100Hz stereo 2ch floatp
MPVLOG [cplayer/info] VO: [null] 360x640 yuv420p
MPV: PLAYING time-pos=0.1s → 7.3s （持续 15 次）
```

**一次运行同时证明两件事**：整条媒体链路（流 + CENC 解密 + HEVC/AAC 解码）在本 App 内完全正常；
而唯一被排除在外的就是那个渲染上下文。这正是「一次只动一个变量」的收益。

## 5. 下层 Activity 盖住视频

**现象**：有画面之后，播放时屏上是**详情页的内容** + 播放器文字叠在上面，视频只在退出瞬间露一下。

**根因**：`Application::frame()` 从栈顶往下收集视图，**"直到遇到一个不透明的"**
（`application.cpp:770-780`）；而 `View::isTranslucent()` 返回 `fadeIn || inFadeAnimation`
（`view.cpp`）。同时两种绘制的**提交方式不同**：

- nanovg：整帧先记录，`nvgEndFrame` 时统一提交（`application.cpp:811`）
- mpv：在视图 `draw()` 里**当场提交到 deko3d 队列**

于是 GPU 实际执行顺序是 `清屏 → mpv 视频 → 所有 nanovg UI`，下层 Activity 的列表就落在视频上面。
（`SwitchVideoContext::clear()` 在 Switch 上是空实现，清屏被做成静态命令在 `beginFrame()` 提交，
`switch_video.cpp:194-196`／`212-225`，所以清屏一定在 mpv 之前。）

**修法**：`PlayerActivity::isTranslucent()` 显式返回 `false`（播放页是全屏不透明页面）。

**真机复核**：照片上出现完整竖屏画面（360x640 竖屏，居中、两侧黑边），播放器文字叠在其上。

## 6. 音频：这个 libmpv 真的有 Switch 音频后端

**之前的判断**：所有测试都跑 `ao=null`，"这套 mpv 编了哪些音频后端未知"。

**证据**（读 `libmpv.a`，不是猜）：

- `ao.c.21.o` 的 `audio_out_drivers` 表是 4 个指针：
  `audio_out_hos`（**第一个，即默认**）、`audio_out_null`、`audio_out_pcm`、`audio_out_lavc`
- `ao_hos.c.21.o` 导入的是 `audrenInitialize`/`audrvCreate`（**audren** 服务，不是 audout），
  一个 `audout*` 都没有
- mpv 的 configure 串里带 `--enable-hos-audio`，feature 标签 `hos hos-audio`

**修法**：`ao=hos` + `audio-fallback=null` + `audio-channels=stereo`（最后一条与 wiliwili 的
`mpv_core.cpp:311` 一致；wiliwili 在 Switch 上**不设 ao**，等于让第一个驱动胜出）。

**真机复核**：

```
PLAYER setupMpv: ao=hos audio-fallback=null hwdec=no vo='' renderctx=1 loadfile=1
MPVLOG [cplayer/info] AO: [hos] 44100Hz stereo 2ch s16
```

## 7. + 退出：应用侧是干净的，问题在"没告诉控制台怎么退出"

**现象**：按 + 弹出"由于发生错误，软件已关闭"，**没有任何错误代码**；从首页直接按也一样
（所以与 mpv 无关）。

**证据**（应用侧一路干净）：

```
SHUTDOWN: mpv_render_context_free ENTER → OK
SHUTDOWN: mpv_terminate_destroy ENTER → OK
SHUTDOWN: PlayerView destructor done
OK    mainLoop ended after 3967 frames
ENTER logClose() and return from main; libnx userAppExit follows
ENTER return EXIT_SUCCESS
```

没有 `FATAL`、没有 terminate、borealis 自己的日志也只有正常的 `Exiting...`。
所以报错发生在 `main` 返回**之后**（newlib 静态析构 / libnx `userAppExit`）。

**修法（照 wiliwili）**：`wiliwili/source/main.cpp:45-46`，在 `Application::init()` 之后、
`createWindow` 之前：

```cpp
// Return directly to the desktop when closing the application (only for NX)
brls::Application::getPlatform()->exitToHomeMode(true);
```

在 Switch 上它就是 `__nx_applet_exit_mode = value`
（`switch_platform.cpp:223-226`）——libnx 用这个标志决定 homebrew 返回时控制台做什么。
不设它，就会显示那个错误框。**这一条尚待真机复核。**

## 8. 仪器：让"看不见屏幕"不再是障碍

这些是让上面每一条能被定位的东西，值得保留：

| 设施 | 作用 |
|---|---|
| `hg_log.{hpp,cpp}` | 面包屑日志，**逐行 fsync**，且**每行 fopen/append/fclose**——所以应用**还在运行时**也能通过 FTP 读（sys-ftpd 对已被独占打开的文件会返回 450，本会话真的撞上过）。borealis 的 logger 另写 `hongguo-brls.log`，因为它必须常驻 FILE* |
| `std::terminate` 处理器 | 把未捕获异常的原因写进日志。`brls::fatal()` 在这套平台上就是 `throw std::logic_error`，所以它也被覆盖 |
| `-Diag` 构建 + Stage A/B | `diag_main.cpp`：先用裸 Label 跑 60 帧（这就是原项目从来没有过的**对照**：同一个可执行文件、同一套 mpv/ffmpeg/curl 静态初始化，只是不建 HomeActivity），再压入真正的 HomeActivity |
| `hg_diag_view.hpp` | 用子类包住 `RecyclerFrame::onLayout()/draw()` 前后各打一行——**不改 upstream 一行**就能判定崩溃是否发生在 recycler 内部 |
| `hg_cfg.{hpp,cpp}` + `sdmc:/switch/hongguo.cfg` | 把实验变量变成 FTP 上一个文件：`ao` / `hwdec` / `vo` / `renderctx` / `loadfile` / `advanced` / `fetch`。本轮多次关键对照（Arm A）就是靠它一次重编都不用 |
| mpv 自己的日志 | `mpv_request_log_messages("info")` + 抽 `MPV_EVENT_LOG_MESSAGE`。这是**唯一**能看到 mpv 内部决定的途径 |

**两个自己踩过的仪器坑，都写进注释了**：

1. **cfg 读取截断**：读取缓冲 1024 字节，而文件自己的注释头把 `ao=null` 顶到了截断线之后。
   日志还写着"file present but contains no key=value lines"——看起来像一条结论，其实是错的。
   → 改成整文件读（上限 16 KiB，超限**明确报警**），并且设置项放文件最前面。
2. **属性名写错**：要读的 mpv 属性叫 **`current-ao`**，不是 `ao-current`。
   搜 `libmpv.a` 的字符串：`current-ao` 出现 1 次，`ao-current` **一次都没有**。
   原来那行会安静地返回"属性不存在"，然后在日志里看起来像"拿不到音频信息"。

## 10. 一句话方法论

这一轮里**每一次"我推理出故障原因"仍然都错了**，真正解决问题的一律是同一种动作：

> **把变量变成可以在 FTP 上翻的一个文件，然后一次只动一个；看日志的最后一行，而不是看代码。**

具体的反面例子，全都发生在这一轮：

- 我一度认定"崩在 recycler 视图构造"，而真正的第一现场是 `std::thread` 抛 ENOSYS；
- 我一度认为 0 行 recycler 的越界读"应该不至于崩"，因为读 4 字节越界通常落在下一个堆块里
  ——**这个推理没有被验证过**，是后来把 dataSource 后挂之后才不再发生；
- 我修 #2 时引入了焦点回归，而日志把机制写得很清楚（`Pushing hg::HomeCell`），
  是我一开始没看它；
- cfg 截断那次，**工具的输出（"没有 key=value 行"）本身就是错的**，而它看起来完全像一条结论。

# 播放链路自检（build157）

> **一句话**：发现"取不到播放计划 / 取不到清晰度"时，程序**自动**把整条播放链路自己走一遍
> （首页 → 详情 → 签名请求 → 解析计划 → 清晰度 → 拉流首字节），把**每一步的实测结果**写进日志并弹一条提示；
> 设置页也开了一个 **Play check** 页签，可以随时手动跑同一套检查。

---

## 1. 为什么是"失败时自动跑"，而不是"启动时自动跑"

用户问的正是这个。选**失败时**，三个理由：

| | 失败时跑（**采用的**） | 启动时跑（未采用） |
|---|---|---|
| 成本 | 一切正常时**一个包都不发** | 每次开机都打一套**签名请求** |
| 误报 | 不可能误报（本来就是坏了） | WiFi 未就绪/门户未认证 → 假报警 ✗ |
| 信息量 | **最全**：哪一集、哪一步、服务端原话 | 只有"通/不通" |
| 风控 | 只在已经坏的时候发 | 这个服务本身限流（上游为此做设备池轮换）✗ |

**更关键的一层**：第 21 轮真正的代价**不是"发现得晚"**——用户 5 秒后就看到了 `Playback failed`。
代价是**"发现得说不清"**：`rc=-5` 分辨不出"服务端拒绝了""返回结构变了""解析器不匹配""响应被截断"，
我为此花了一整轮加日志才拿到那 125 字节。**所以价值在定位，而失败那一刻正是信息最全的时刻。**

---

## 2. 它检查什么（六步，全部走**生产代码**）

用的是播放器自己调的那几个函数（`Client::fetchPlayPlan` / `fetchQualityLadder` …）——
**"用另一套代码写的诊断，可以在真链路坏了的时候还是绿的"**，所以这里不另写一套 HTTP。

| # | 阶段 | 走的东西 | 失败意味着 |
|---|---|---|---|
| 1 | `home page` | `Client::fetchHome` | **网络/首页不通** → 后面全部跳过（不制造五条网络失败掩盖事实） |
| 2 | `detail page` | `Client::fetchEpisodes` | 网页在、**分集列表解析**坏了 |
| 3 | `video model` | `Client::fetchPlayPlan`（**签名 POST**） | 接口层问题；详情里带**服务端原话**（`HTTP 200 | 125 bytes | first 512: …`） |
| 4 | `quality ladder` | `Client::fetchQualityLadder` | 计划能拿、**清晰度菜单**坏 |
| 5 | `stream` | `hg_http_request` + `Range: bytes=0-63` | 接口都正常，**CDN 拒绝流** |
| — | 结果 | 全绿 / 首个失败阶段 | 一行 headline，见下 |

**第 5 步看的是 `ftyp` 四个字节，不是状态码**——错误页也会回 200。

日志形如：

```
PLAYCHECK: ==== play chain check, triggered by: plan failed: play_plan rc=-5 (see hg_play.h) [build157] ====
PLAYCHECK: the episode the player was asked for: 7692354467328429118
PLAYCHECK: 1 home page      OK    36 cards
PLAYCHECK: 2 detail page    OK    series 7692043430955863102 -> 126 episodes, first 7692096729776131096
PLAYCHECK: 3 video model    OK    1080p 1920x1080  codec=bytevc1  CENC key derived
PLAYCHECK: 4 quality ladder OK    5 tiers, first '1080p  ·  HEVC'
PLAYCHECK: 5 stream         OK    206, 64 bytes, ftyp present
PLAYCHECK: RESULT PASS -- Play check OK: ... (1832 ms)
```

失败时 headline 会指名道姓，例如 build156 那种情况：

```
Play check: THE PLAY INTERFACE ANSWERED 200 WITH NO PLAYABLE SOURCE -- PLAY-PLAN FAILED ... | HTTP 200 | 125 bytes | first 512: {"Code":110001,...
```

## 3. 两个入口

1. **自动（worker 线程，不挡住错误弹窗）**：`player_view.cpp` 里
   - 计划**重试也失败**时 → `hg::startPlayChainCheck("plan failed: …", episodeId)`
   - **清晰度请求失败**时 → 同一个调用（**1 分钟冷却**，两次失败只跑一次，不会变成请求风暴）
   - 结果：日志一整块；**屏幕上不再弹文字框**（见下）
2. **手动**：**设置 → Play check 页签**（`settings_activity.cpp` 的 `makeSelfCheckGroup`）
   - 进入即跑一次；点任意一行重跑；行上按阶段显示 `OK/FAIL + 实测值`
   - 先显示**上一次自动检查的结果**，再被新结果替换（用户点进来往往正是为了看刚那次）

### ★ 结果是**一个点**，不是文字框（build158，用户要求）

> 用户的原话："把检测的结果用绿色点表示就可以了，如果不通过就红色的，不需要用这种文字框框表示。"

| 颜色 | 含义 |
|---|---|
| 🟢 绿 | 最近一次检查**每一阶段都通过**；或**真实播放**同时证明了计划与清晰度两步 |
| 🔴 红 | 某阶段失败（哪一步见 Play check 页签与日志） |
| ⚪ 灰 | **还没测过** —— 灰不是红，不能把"没测过"显示成"坏了" |

**位置**：主页**顶部导航条最右端**（`hg_sidebar_view.cpp` 末尾加一个 `StatusDotView`）——
那是"按播放之前"站着的地方，也正是这个答案值得不用问就看到的时刻。

**为什么是一个 View 每帧读状态，而不是回调去改视图**：检查在 worker 线程上、失败后几秒才结束。
让它去动视图树，正是这个项目已经付过代价的一类错误（`brls::App` Data Abort：回调写进已被释放的 cell，
见 `hg_alive.hpp`）。所以检查线程**只写一个全局状态**，点**每帧读它画**——
全程**没有任何视图树增删改**，也就没有会失效的回调。

**为什么真实播放也会点绿**：检查只在**失败**时跑，所以一个一切正常的用户永远看不到绿点，
灰会被读成故障。播放器在"计划 + 清晰度都答了"的那一刻调 `hg::notePlayChainWorked()` ——
那两步正是检查要看的东西，而且是**真实路径**给的证据，比探测更硬。

Play check 页签的 **Result 行也是这个点**（`ResultDotCell`），阶段行仍保留文字实测值——
"诊断"那部分本来就是拿来读的。

## 4. 顺带修掉的一个真隐患：客户端不是线程安全的

`hg_client.cpp` 的 `g_page`(1 MiB) / `g_router`(512 KiB) 是**文件级静态缓冲，全类共用**。
两个请求并发 → 互相覆盖整份响应 → **两个解析器读到的都是两份页面的混合物**，
结果是**一个错误答案而不是崩溃**（更坏）。项目早先已经踩过一次（`player_view.cpp:1566` 有记录，
用 `g_ladderMutex` 把"取阶梯"串行化）。

build157 引入了**第三个调用者**（自检线程，而用户可能同时开始放另一集），
所以这次把串行化放到**缓冲所在的地方**：`hg_client.cpp` 里一把 `std::recursive_mutex`，
九个公开入口全部加锁（`fetchHome/fetchHomeRows/fetchEpisodes/fetchSearch/fetchCategory/
fetchPlayPlan/fetchQualityLadder/fetchPlayPlanForSource/networkProbe`）。
**递归**是因为公开入口会调私有帮手（`fetchPlayPlan → postVideoModel`）；普通 mutex 第一次就会死锁。

代价：以前能并发的请求现在排队 —— 这正是原来的行为（一次一个阶梯、一个计划），
而**排队的请求是对的，混合的响应不是**。

## 5. 怎么验证（一次就够）

1. **正常播放**：随便点一集 → 应当照常进播放（build156 的能力不能丢）。
2. **设置 → Play check**：六个阶段应当全绿。**这一步同时验证了自动路径的全部代码**
   （同样是 `runPlayChainCheck`，只是触发者不同）。
3. 下次真的再坏，**不用再靠用户点播放去撞**：日志里会出现 `PLAYCHECK:` 那一整块，
   第一行失败阶段就是答案。

## 6. build158：默认 1080P（**没有**重犯 build143）

用户要求"初始用 1080P"。**没有**去复活 build143 那套（选档 → 取档位计划 = **两次请求**），
那正是 `-5` 的来源。**新接口一次就把五档全给了**，计划本来就从那一份响应里出来 ——
所以只改了**从列表里挑哪一条**：

| | 改前 | 改后 |
|---|---|---|
| 选法 | **第一条**可解码的 = 360p（上游是**从低到高**排的） | **最高分辨率**那条（像素数最大，同像素比码率）= **1080p** |
| 请求数 | 1 | **1（没变）** |

落点：`app/src/hg_play.c` 的 `hg_play_plan_from_model`。

**一个安全性细节**：以前"第一条能用就返回"，所以**它后面那条**畸形行永远不会被读到；
改成挑最好就必须把每条都读一遍 —— 那会把"第 5 档 URL 超长"变成"这一集不能播"，
**用播放能力换了个零收益**。所以：**单条行的硬错误先记下、继续找**；
**真的没有一条能用时，才把它报出来**（报的还是真实错误，不是笼统的"没有源"）。

**测试也跟着改了，而且原来那条性质没丢**：`video_model_h264.json` 那个派生夹具
（entry 0 = h264 640x360，entry 4 = bytevc1 1920x1080）原来断言"取 entry 0"，
现在断言"取 entry 4（最好那条）"；紧接着**在内存里把 entry 4 改成 bytevc2**，
断言这时**能从 h264 那条建出计划** —— 也就是这个夹具原本要证明的"h264 可播"仍然成立。

> 顺带纠正一条**本会话我自己的错判**：我曾根据日志里
> `PLAYER hwdec: requested='auto' in-force='(empty = software)'` 说"走的是软件渲染"——
> **错了**。卡上 `hongguo.cfg` 一直带 `renderer=deko3d`（与 `.old` 逐行相同），
> 日志也有 `renderctx=1` + "on the deko3d path"。那行"empty = software"是**这个诊断自己的误判**：
> `hwdec-current` 是在 `mpv_initialize` 之后、**loadfile 之前**读的，那时 mpv 还没挑解码器，`rc=-3` 是正常的。

## 7. 没做的（说清楚，免得以为是漏了）

- **没有做启动自检**：理由见 §1。真要加，是在 `main.cpp` 里一行 `hg::startPlayChainCheck(...)`，
  但那就把"每次开机打一套签名请求"这个代价买回来了 —— **要单独决定**。
- **没有做"自动换源"**：接口换了就没有第二个源可换（这正是 build156 的情形）。
  自检给的是**结论**，不是替代品。
- **Play check 页签的标题是英文**（`"Play check"`），和这个设置页剩下的 7 处英文一致，
  没有为它单独改 `hg_lang.h` 的多语言表。

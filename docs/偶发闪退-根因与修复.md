# 偶发闪退：根因与修复（build36）

**症状（用户报告）**：「整体偶尔有闪退的情况，我在第一次遇到，后面又没了我大概开了 3 次」——
**偶发**、屏幕无提示、约三次里一次。

**根因**：**图片加载的异步回调在"卡片已经被销毁"之后仍然去读写它的成员**。
`ptrLock` 只锁住了 `brls::Image`，而回调同时还要碰 `slot` 和 `settled`——**那两个成员属于卡片，
不属于图片**。按"刷新"重建网格时卡片会被真正删除，于是回调写进了已释放的内存，
堆被写坏，之后主线程执行队列里的某个任务时跳飞到非可执行地址 → 崩溃。

---

## 1. 证据链（四步，每一步都可复现）

### 1.1 应用日志：**这一次没有留下 FATAL**

`/switch/hongguo.log` 只覆盖**最后一次**运行（每次启动会重写），而崩溃那次不是最后一次，
所以日志里查不到。这一条本身是信息：**不是** `std::terminate` 那一类（那一类会打出 FATAL 行）。

### 1.2 Atmosphère 的崩溃报告：这才是关键

控制台把崩溃报告写在 `/atmosphere/crash_reports/`，按标题 id 命名（我们的标题 id 是
`0101000000000000`）。最近一份对应这次崩溃：

```
Process Name:  hongguo-net        (NPDM 里的名字，所有 NSP 都是这个，与版本无关)
Result:        0x2A8 (2168-0001)
Type:          Instruction Abort                     <- 跳到不可执行的地址，不是 abort
PC:            0000000075baa680                      <- 落在模块之外（野地址）
Stack Trace:
   ReturnAddress[00]: hongguo + 0x129874
   ReturnAddress[01]: hongguo + 0x10d010
   ReturnAddress[02]: hongguo + 0x1090c8
   ReturnAddress[03]: hongguo + 0x9b944
```

（顺带说明：另外两份更早的报告是 `Type: User Break`、PC 在模块内 —— 那是 `build34`
主题键那次 `abort()`，和这次不是一回事。）

### 1.3 用**同一个 ELF** 把地址还原成函数

`hongguo + 0x…` 是相对模块基址的偏移，而我们有这一版链接出来的 ELF，所以可以直接符号化：

```powershell
& aarch64-none-elf-nm.exe -C --numeric-sort out\hongguo.elf   # 找每个地址落在哪个符号里
```

| 报告里的地址 | 符号 |
|---|---|
| `+0x129874` | **`brls::Threading::performSyncTasks() + 0xe4`** ← 崩溃点 |
| `+0x10d010` | `brls::Application::internalMainLoop() + 0xd0` |
| `+0x1090c8` | `brls::Application::mainLoop() + 0x58` |
| `+0x9b944`  | `main() + 0xa4` |

**`performSyncTasks()` 就是 `brls::sync` 队列的执行者**（`application.cpp:204`，每帧一次）。
所以：**崩溃发生在"执行某个主线程任务"的过程中**，而且 PC 跳到了模块外的野地址——
也就是那个任务里调用了**已经不存在的对象的函数**。

（用 `addr2line` 会把这行报成上一行的 `runLoopEvent.fire()`，是 `-O2` 内联造成的偏差；
用 `nm` 找符号所属区间才是可靠的。）

### 1.4 崩屏截图：崩溃时停在**设置界面**

`/atmosphere/crash_reports/01791607444_….jpg` 是 Atmosphère 存的画面，
上面是设置界面的"诊断"标签页（`out/crash-1244.jpg`）。
这说明崩溃与"当前显示哪个界面"无关——**是之前某个界面留下的坏账**在这一刻爆掉。

## 2. 根因：`ptrLock` 锁错了对象

`hg_image.cpp` 的异步流程是：worker 取网络 → `brls::sync` 回主线程安装纹理。回调里用到了三样东西：

| 用的是 | 它住在哪 | 被 `ptrLock` 保护了吗 |
|---|---|---|
| `target`（`brls::Image`） | 卡片里的子视图 | ✅ 锁住的是它 |
| `slot`（`ImageSlot`） | **卡片**的成员 | ❌ |
| `settled`（`std::atomic<int>`） | **卡片**的成员 | ❌ |

卡片（`HomeGridCard`）被销毁时，`Box::~Box`（`box.cpp:759-772`）对每个子视图
`setParent(nullptr)`，**锁住的 Image 会被重新排进删除队列（活下来），而卡片自己照删**。
于是正在飞行中的回调手里那三个指针，有两个变成了悬垂指针：

```cpp
if (slot && !slot->stillWants(full)) { ... slot->currentUrl() ... }   // 读已释放的 std::string
...
if (settled) settled->store(HG_IMG_INSTALLED);                        // 写已释放的内存
```

**什么时候会发生**：网格重建的那一刻，只要还有封面请求在飞。
按"刷新"（`reloadHome` → `applyHome` → `HomeGridView::setRows` → `contentBox->clearViews(true)`）
就会重建，而 `tickCoverRetries` 每 400 ms 还会为新卡片再发一批请求——
所以**是否踩中完全取决于时序**，这正好解释"偶发、开了三次才遇到一次"。

**为什么堆坏了却在这里崩**：写坏的是已释放内存（可能已被别的对象复用），
真正致命的一跳发生在之后某一帧、由删除池或队列任务执行到那块内存时。
所以崩溃现场（设置界面）和肇事现场（首页刷新）**可以相隔好几个界面**。

## 3. 修法

**核心**：让"锁"保护回调真正依赖的那个对象——**卡片**，而不是只保护图片。

| 改动 | 内容 |
|---|---|
| `hg_image.hpp/.cpp` | `loadImageAsync(...)` 新增第 6 个参数 `brls::View* owner`；入口处 `owner->ptrLock()`，六个退出路径统一走 `releaseFetch(target, owner)`（同时解锁两个） |
| `hg_image.cpp` | 回调里**先写 `settled` / 先取 `slot->currentUrl()`，再解锁**——解锁就意味着卡片可以被删，之后不能再碰它的成员（原来的顺序依赖"删除池只在本帧稍后才倒"，能跑但没必要依赖） |
| `home_activity.cpp` | 三个调用点都传 owner：网格卡片传卡片自己（`this`），列表单元格同理 |

**为什么这是"结构性"修复而不是打补丁**：所有权被写进了函数签名，
"谁必须活到回调结束"从注释里的期望变成了参数里的约定；调用点漏传时，
`slot`/`settled` 为空的场景依然安全（详情页那个一次性封面就是 `slot=nullptr`）。

**这一条也顺带修正了 `hg_image.hpp` 里的一句过宽的断言**（"持有锁就保证这个视图不会被释放"）：
锁保护的是**被锁的那一个视图**，不是回调捕获的全部东西。

## 4. 验证与怎么继续盯着它

| 项 | 结果 |
|---|---|
| 构建 | `hongguo.nro` 零警告（`out/build36.log`） |
| 主机测试 | 16 套 / 1052 项 / 0 失败 + 主题键检查通过（`out/host-tests-build36.txt`） |
| 部署读回 | `/switch/hongguo.nro` **SHA-256 与本地一致**（`D18EB2CD55D475D7…`） |

**诚实说明**：偶发问题的修复**不能靠一次运行证明**——它需要"在飞行中重建网格"这个条件再次出现。
所以：

* 如果之后**还有**闪退，报告在 `/atmosphere/crash_reports/`，**不要删**；
  我可以按本文 §1.3 的方法用对应版本的 ELF 直接符号化，一次定位。
* 这次留下的工具就是这条路径：**崩溃报告 + 同版 ELF + `nm`**，不需要在控制台上复现。

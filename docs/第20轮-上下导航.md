# 第 20 轮：方向键上下 —— 按 wiliwili 的结构重做导航（build32）

**这一轮不是"给上下打个补丁"，而是把导航的结构改成 wiliwili 的样子。**
上一轮交接文档（`交接-第19轮.md` §2.2.4）建议"保留框架的左右，另外只拦截上下"。
拦截**仍然是我在做移动者**，也就是那个出过两次问题的角色；所以按用户的要求重新整体考虑，
最后采用了 wiliwili + 框架本身的做法：**网格不移动焦点，只回答"下一步是谁"**。

---

## 0. 一句话结论

| 之前 | 现在 |
|---|---|
| 网格自己**移动焦点**（每帧轮询输入 + 自己的重复计时 + 自己的闸门） | 网格**只回答**框架的问题；焦点永远由 `Application::navigate` 移动 |
| UP/DOWN 在 `getNextFocus` 里返回 `nullptr`，框架报错抖动 | UP/DOWN 由 `getNextFocus` 算出"下一行最近列"的**目标视图**并返回 |
| `getDefaultFocus()` 永远答"第一张卡" → 框架的跟随滚动被指到顶部 | 答"当前有焦点的那张卡" → 框架滚动到正确位置 |
| `hg_nav.cpp`（轮询）+ `moveFocus` + `followFocus` 三套并行机制 | 全部删除；`followFocus` 只从框架的焦点钩子 `onChildFocusGained` 进入 |

## 1. 这一轮最重要的发现：**框架本来就有"跟随焦点滚动"**

上一轮（`第17轮-滚动与摇杆.md` §一）的结论是：

> 「`updateScrolling()` 只被 `draw()` 调用，且只在那面旗子还立着的时候……
> **所以这个框架的滚动框只在"出现"时滚一次，之后焦点怎么移动它都不管。
> 这与……完全对上。**」

**这个结论漏掉了一个调用点。** `updateScrolling()` 有两个调用者：

```cpp
// 调用点 1：draw() 里，受 updateScrollingOnNextFrame 控制（上一轮只看到这个）
if (this->updateScrollingOnNextFrame && this->updateScrolling(false))
    this->updateScrollingOnNextFrame = false;

// 调用点 2：scrolling_frame.cpp:478-487 —— 每次**子视图获得焦点**都会被调用
void ScrollingFrame::onChildFocusGained(View* directChild, View* focusedView) {
    Box::onChildFocusGained(directChild, focusedView);
    this->childFocused = true;
    if (Application::getInputType() == InputType::GAMEPAD && behavior == ScrollingBehavior::CENTERED)
        this->updateScrolling(true);        // <-- 跟随焦点滚动，每次焦点变化都跑
}
```

而 `View::onFocusGained()` 无条件通知父节点（`view.cpp:1305-1306`），所以只要焦点在网格里
动一下，这条路就会走一遍。**框架确实跟着焦点滚**，wiliwili 的网格也正是靠它。

### 那为什么真机上看起来"没滚" / 或者"弹回第一行"？

因为 `updateScrolling()` 会问**我们的** `getDefaultFocus()` 该滚到哪：

```cpp
View* focusedView = getDefaultFocus();      // scrolling_frame.cpp:534
...
float newScroll = localY + itemHeight / 2 - this->getHeight() / 2;
```

而我们两个网格的 `getDefaultFocus()` 都写成"**永远第一张卡**"（当初是为了"从外部进入网格时
焦点落在第一张"，这对进入是对的），于是**每一次焦点变化都在要求框架滚回顶部**。
这正是更早记录下来的那条症状："从第四行开始弹回第一行"。

### 真机日志给出的硬证据（这一条是决定性的）

我从主机取回了 build31 的真机日志（`out/console-log-build31.txt`，构建时间 01:20:08）：

| 日志里搜什么 | build31 里的次数 |
|---|---|
| `HOMEGRID scroll`（上一轮写的 `followFocus` 打的） | **0** |
| `NAV:`（轮询打的） | **0** |
| `moveFocus`（自定义导航打的） | **0** |

也就是说：**部署版里上一轮那套跟随滚动代码一次都没跑过** —— 因为轮询被 `if (false)` 关掉之后，
`followFocus` 唯一的调用者（`moveFocus`）就再也没有人调。交接文档 §1 里"跟随焦点滚动 ✅"
那一行，**不是我们的代码做的**，而是框架在滚，而且滚的目标是错的（第一张卡）。

## 2. wiliwili 到底怎么做的（读代码的结论，这是这一轮的骨架）

`wiliwili/source/view/recycling_grid.cpp:561-638`：

```cpp
brls::View* RecyclingGrid::getNextCellFocus(brls::FocusDirection direction, View* currentView) {
    // 上下：按 spanCount 整行跳（index +/- spanCount，也就是保持同一列）
    if (contentBox->getAxis() == ROW && (direction == UP || direction == DOWN)) {
        int row_offset = spanCount;  if (UP) row_offset = -spanCount;
        ... 找到目标 cell，itemsRecyclingLoop(); return cell;
    }
    // 左右：在当前行里 ±1；到行首/行尾就交给父节点
    if (contentBox->getAxis() == ROW) {
        if ((LEFT && position == 0) || (RIGHT && position == spanCount - 1)) -> 交给父节点
    }
    ... 其余情况 ±1 线性走
}
```

**四个要点，全是我们过去没有照做的**：

1. **网格不移动焦点**：它只是**回答** `getNextFocus`。焦点是框架移动的
   （`Application::navigate`，`application.cpp:518-583`），声音、抖动、重复计时都在那里。
2. **上下 = 整行**：按 `spanCount` 算，而且**保持同一列**。
3. **左右到边界就交给父节点**，不是自己算。
4. **没有轮询、没有自己的计时器、没有任何 `giveFocus()` 调用** —— 所以
   "一次按键走两格"这件事在这套结构里**不可能发生**，因为只有一个移动者。

我们这一轮就是把这四点搬进两个网格，只是算术换成我们自己的行模型
（heading 占一行、末行可能短）并放进 `hg_grid.c` 用主机测试覆盖。

## 4. 为什么这次不会"一次两格"（结构性理由，不是又一次打补丁）

| 上一轮的失败结构 | 现在 |
|---|---|
| `draw()` 轮询 + 框架派发 = **两个移动者** | `getNextFocus` 只返回目标，**移动者只有框架** |
| 轮询有 400/120 ms 重复，框架有 250/100 ms 重复 | 只有框架的重复 |
| 用 30/120/250 ms 闸门区分"重复"和"新按键" | **没有闸门**：一次派发 = 一次移动，这是框架的性质 |
| 三个地方各存一份"按住状态" | 没有任何输入状态 |

换句话说：上一轮的四道闸门都是在**事后**判断"这一次算不算按键"。
现在这个问题根本不存在——因为**没有第二个东西可以产生"额外的一次"**。

## 5. 上下到顶 / 到底会怎样（这是行为变化，请注意）

网格内部有目标行 → 就是那一行；**网格内部没有** → 把方向交给父节点：

```cpp
if (this->getParent()) return this->getParent()->getNextFocus(direction, this);
```

这正是 `Box::getNextFocus` 对"做不到的方向"的做法（`box.cpp:416-419`），wiliwili 的网格也一样。
在这台机的效果是：**在第一行按上 → 焦点到右上角的"刷新"按钮**（以前这条完全出不去，
因为网格把上下整个吞掉了）。从刷新按钮按下 → 回到网格第一张卡。

### 顺带从这份日志里读到的三件事（下一轮可以直接用）

1. **`hwdec` 探针第一次在真机上给出答案**：`PLAYER decode: HARDWARE (nvtegra-copy)`
   —— 解码**是硬解**；慢的是**渲染**（`SW surface 1280x720 ... 3686400 bytes` 每帧上传）。
   交接文档 §2.4 把这两件事写成一件了，需要分开记录。
2. **§2.5「画面设置改了没变化」的推测可能是错的**：硬解用的是 `nvtegra-copy`
   （copy 模式，帧会回拷到内存），而交接文档猜的是"直接硬解绕过滤镜链"。
3. **§2.3「每集开头 3 秒跳回 0 秒」找到了根因**（`build33` 已修，见
   `docs/起播跳回0秒-根因与修复.md`）：这一集 11:05:59 起播（plan 已经是 360p），11:06:01 又出现
   `QUALITY: switching to '360p' (tier 4, source 0, 640x360)`
   → 11:06:02 `QUALITY: loadfile issued` —— **切到自己已经在用的那一档，却重新加载了整条流**。
   时间点（起播后约 2-3 秒）与用户描述的症状一致。
   *注意*：这份日志里的 `end-file reason=2` 是用户按 B 退出播放器造成的
   （紧跟着就是 `PLAYER: B pressed -> popActivity`），**不是** §2.3 的重播。

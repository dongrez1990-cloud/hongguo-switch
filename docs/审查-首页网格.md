## 发现（按严重程度）

### 1. CRASH — `home_activity.cpp:684`（配合 `:643-696`、`box.cpp:240-259`、`view.cpp:1546`、`application.cpp:1057-1065`）

```cpp
cell->registerClickAction([this, i](brls::View*) {
    this->openDetail(i);
    return true;
});
```

`setRows()` 第 649 行 `clearViews(true)` 并不立即释放。`Box::clearViews(free=true)` 走
`view->freeView()` → `Application::addToFreeQueue()`（`view.cpp:2569`）→ 只把指针压进
`deletionPool`；真正 `delete` 发生在 `internalMainLoop()` 末尾（`application.cpp:212-224`）。
**关键缺陷：`View::~View()` 只是 `if (deletionToken) *deletionToken = true;`（`view.cpp:1546`），
从不清理 `Application::deletionPool`。** 因此 `clearViews(true)` 是“延迟释放”，不是“立即释放”，
而 `HomeGridView` 持有的 `this->cells` 里的指针在本次 relayout 之后仍然有效、仍然可以触发。

后果：用户在按下刷新按钮（`refreshButton` 的点击回调）之后、`deletionPool` 被清空之前按下 A，
被聚焦的仍是**旧 cell**，`handleAction`（`application.cpp:712-741`）沿父链取到那个已被移出视图树、
但尚未析构的回调并执行 → `openDetail(i)` 用**新**的 `this->rows` 去索引**旧**的下标 →
打开错误的详情页（静默错误），或在行数变少时越界（`rows.size()` 检查只挡住越界，挡不住错配）。
这不是理论：清空发生在入队回调所在的 `performSyncTasks()` 之后，同一帧内焦点指针必然悬空。

### 2. CRASH — `home_activity.cpp:712-716`（配合 `:805`、`application.cpp:152`）

```cpp
const float width = this->getWidth();
if (width <= 0.0f) return;
...
this->contentBox->setHeight(total);
```

`relayout()` 只在 `getWidth() > 0` 时设置内容高度，**没有任何 else 分支**。`onLayout()` 是
Yoga 的 `NodeLayout` 事件监听（`application.cpp:151-152`）触发的，首次布局时宽度可能为 0；
更关键的是 `ScrollingFrame::setContentView()`（`scrolling_frame.cpp:298-317`）——构造函数第 579 行
调用的那个——会先 `Box::addView(contentBox)`（内部 `invalidate()`），**然后**才设置
`view->setWidth(this->getWidth())`（第 314 行）。所以框架自己就保证了“内容盒被加入时帧宽还是 0”。
一次以 0 高度入队的内容盒会一直等到宽度变化的 relayout 才被修正；在这期间
`contentBox->getHeight()==0` → `getContentHeight()==0` → `ScrollingFrame::draw()`
（`scrolling_frame.cpp:142` 附近的 `nvgIntersectScissor`）与 `updateScrolling()`
（`:548-558`，`bottomLimit` 为负）都在用 0 高度区域做裁剪/计算。同时 `getParentNavigationDecision`
在 CENTERED 行为下也是用它做边界判断的。这条路径在真机上就是“首页进去是黑的”。

## 已确认无误（逐条核对，附依据）

**A. `relayout()` 末尾的 `giveFocus` 不会递归 —— 确认安全。**
`Application::giveFocus()`（`application.cpp:882-903`）只做五件事：`getDefaultFocus()`、
两个焦点回调、`currentFocus` 赋值、两个事件 `fire()`。它不调用 `invalidate()`、不跑 Yoga、
不触发 `onLayout`，因此 `onLayout → relayout → giveFocus` 不会重入布局。
`onWrite` 全链上唯一可能回头的是 `ScrollingFrame::onChildFocusGained` → `updateScrolling(true)`
（`scrolling_frame.cpp:478-487`），它只动滚动动画（`startScrolling`/`animateScrolling`），
不碰 `onLayout`。注意 `onChildFocusGained` 是自己实现的、不转调 `View::onChildFocusGained`，
所以那条链是终止的。第 728 行的双键缓存（宽度 + 密度）也是多余的保险。

**B. `brls::Application::getCurrentFocus()` 名称正确，文件能编译 —— 确认安全。**
`application.hpp:284` 声明 `static View* getCurrentFocus();`，`application.cpp:639-642` 定义。
`:791` 用的未限定 `View*` 能编译是因为 `view.hpp:101-1559` 的 `namespace brls` 一直到文件结尾，
而 `home_activity.hpp` 里 `class HomeGridView` 在**全局命名空间**，`OpenDetail` 等成员声明先解析
`brls::View*`，`:641` 的类定义才补齐类体——所以匹配的是 `View` 与 `brls::View` 同一个类。
`hg_client.hpp:46-93` 的 `namespace hg` 在 `:93` 就关闭了，`:791` 的确在全局作用域。

**C. `contentBox` 非空 —— 确认安全。** 构造函数 `:576-579` 无条件 new 并 `setContentView`；
只有 `setRows`/`relayout` 使用它；没有其它构造函数，没有 `= default`，没有会把它置空的路径。
`clearViews(true)` 后内容盒自身仍持有焦点是安全的：`~View()` 的
`if (Application::getCurrentFocus() == this) Application::giveFocus(nullptr);`（`view.cpp:1532-1533`）
是通用的兜底，而 `:1259` 的 `giveFocus(this->grid)` 又会在数据到达时重新落焦到某个 cell 上。
（C 里唯一**不**安全的是“cell 持有焦点”那一半，已单列为发现 1。）

**D. 旧 cell 的回调能被触发 —— 已单列为发现 1（这才是真正的问题）。**
指针在重建后并不立即失效，`this->rows` 被整体替换而回调捕获的 `i` 是旧编号，
`openDetail` 的 `rows.size()` 检查只防越界、不防错配。

**E. `loadImageAsync` + `ptrLock` 在重建时是安全的 —— 确认安全（但要配 D 一起看）。**
`hg_image.cpp:191` 在启动 worker **之前** `target->ptrLock()`；主循环
`application.cpp:212-224` 对 `isPtrLocked()` 的视图拒绝 `delete`、放回 `undeletedViews`。
所有六条退出路径（worker 起不来 `:334-340`、传输失败 `:275-278`、状态码 `:283-286`、
空 body `:291-294`、slot 不匹配 `:312-317`、成功 `:323-324`）都会 `ptrUnlock()`，
且 `slot` 指向的是 `HomeGridCard` 的成员，视图被钉住 ⇒ slot 也钉住，`:312` 读 `slot->stillWants`
不会读到已释放内存。`brls::sync` 闭包按值捕获原始指针，这一点由 ptrLock 兜住。
真正的问题在 D：视图被钉住只是“不崩”，它的回调仍然可以在重建后触发。

**F. 空列表 / 宽度为 0 / 极窄 —— 确认安全（除发现 2 的“旧高度残留”）。**
`:713` 空行提前返回；`hg_grid_layout` 在 `contentW <= 0`（`hg_grid.c:65`）、
`cellW < HG_GRID_MIN_CELL_W`（`:98`）、metrics 非法（`:81`）时都返回 0，
`:769` 的 `placed != rows.size()` 分支会把所有 cell 设为 GONE 并 return——不画半张网格，也不会
走到 `:836` 的 `places[0]`。`:801` 的 `placed > 0` 守卫是多余但正确的。
`:807-830` 的索引是安全的：`:810` 用 `cells[i]` 判断、`:811` 用单独的 `headingIndex`
对 `headings` 做边界检查，heading 与 card 的数量互不影响。
`setRows` 之后 `contentBox->getHeight()` 也不会被“忘掉”：`Box::addView` 会 `invalidate()`，
非 absolute 子节点的高变化会触发父节点重新布局（子节点都是 ABSOLUTE，所以不会反过来撑高父节点，
这正是能读到框架计算高度的原因）。

**G. compact 路径的字符串与可见性 —— 确认安全，但有一处受 A 影响。**
`setData`（`:505`）先 `tagText = s.tags;` 再在 `isCompact` 时使用，`setCompact` 在
`compact==true` 时才 `tags->setText(tagText)`——没有“先 setText 后赋值”的时序问题；
`:476` 的 `if (this->isCompact == compact) return;` 不会跳过必要的设置，
因为 `compact` 为真就说明 `tagText` 已经就位，而 `setData` 自己会补上可见性。
`Visibility::VISIBLE` 会让 `isFocusable()`（`view.cpp:2461-2464`）在 `visible && alpha != 0`
时才为真，不影响 `:829` 的 `setCompact` 调用本身。
**唯一受影响的是已移除 cell 的 `setCompact`（`:829`）——见发现 1，它可能让一个已经脱离视图树、
但尚未析构的 cell 进入 compact 状态。**（静态指针不失效，这是 MINOR 不是 CRASH。）

# 第 13 轮代码审查：发现与修复

**为什么要审查。** 第 13 轮加了六个功能，全部**构建通过、部署完成、零警告**，
而**一行都没在真机上跑过**（控制台自 10:56 起没再运行）。在这种状态下，从构建机上能做的
**最有价值的事不是再加功能，而是找出"一上机就崩"的缺陷**。

所以这一轮对两个风险最高的文件做了**定向审查**（各处一个新会话、互不知情），
逐条核对框架源码里的假设，而不是靠记忆。审查报告：
`审查-首页网格.md`、`审查-播放器.md`（两份都在 `docs/`，保留原始证据）。

**审查真的抓到了真缺陷** —— 其中三个是我自己写进去的，而且**每一个都只会在真机上才暴露**。

---

## 一、已修复的四个缺陷

### 1. HANG —— 探针阻塞了 UI 线程（**我自己写的注释在说谎**）

`player_view.cpp` 的探针用了 `mpv_command_ret`（**阻塞到回复到达**），而它被放在
`brls::sync` 回调里 —— 那**跑在主线程上**。更糟的是**它根本不可能工作**：
mpv 通过**事件队列**投递命令回复，调用方必须同时在 drain 事件；
而主线程只在 `draw()` 里 drain —— 那个阻塞调用**恰好阻止了 draw()** 。**自我死锁。**

**我的注释还写着**「ran on the worker」而调用点明确在主线程 —— 审查指出这一点比 bug 本身
更值得记：**注释和代码不一致时，读注释的人会放弃核对。**

**修法**：改成 `mpv_command_async` + `MPV_EVENT_COMMAND_REPLY`，回复在 `drainMpvEvents` 里处理
（`handleShotReply`）。这**也正是探针的判定所推荐的机制** —— 于是探针现在跑的就是它推荐的
那条路，而不是另一条仅仅"对诊断也够用"的路。

### 2. HANG —— 换清晰度时阻塞了帧循环

`switchQuality` 在 `brls::sync` 回调里（主线程）调 `mpv_command(loadfile)`。
`loadfile` 要等到**流开始打开**才返回 —— 于是**整个网络加载期间帧循环是停的**。

**修法**：`mpv_command_async`；并把原来的回读改成说**实话**：
异步加载刚发出时，mpv 打开的**仍然是旧流**，所以日志从「mpv reports path=」改成
「mpv currently has path=… (the load is async; the switch is confirmed by the file-loaded event)」。

### 3. SILENT-WRONG —— 换档时**不检查** mpv 是否拒绝了选项写入

`mpv_set_option_string(…, "demuxer-lavf-o", …)` 在活动句柄上是**可能被拒绝**的，
而返回值**只被打印**。后果很具体也很糟：**解密密钥还是上一档的**，
`loadfile` 用错密钥打开新流 → **没画面、也没错误** —— 正是这个项目一直在设计防范的那种失败。

**修法**：两个返回值都检查；任一被拒就**中止这次切换**，保留正在播的流，
通知用户，并把菜单行拨回真实档位。

### 4. CRASH —— 刷新后旧 cell 的回调**还在**

首页网格 `setRows` 调 `clearViews(true)`，看起来是"释放旧 cell"。**它不是**：
borealis 把被移除的视图压进 `Application::deletionPool` **延迟释放**
（`box.cpp` → `view.cpp:2569` → `application.cpp:1064`）。

于是**刷新之后**，旧 cell 仍然持有已注册的点击动作 —— 激活它就会用**新 rows 的索引**跑
`openDetail(i)`：**要么是错的剧集，要么越界**。审查把这条定为 CRASH。

**修法**：**世代计数器**。每次重建自增，每个 cell 的回调捕获自己构建时的值，
不匹配就拒绝执行并记一行日志。比追踪"哪些 cell 还活着"更便宜也更明显。

## 二、审查同时确认为**无误**的部分（这部分同样重要）

两份报告都要求列出「确认无误」的项，以免把"没看"当成"没问题"：

- `relayout()` 末尾的 `giveFocus()` **不会递归**：`giveFocus` 只做焦点赋值与事件，
  不触发 invalidate、不跑 Yoga；
- `brls::Application::getCurrentFocus()` 这个精确名字**存在**（`application.hpp:284`）；
- `hg_image` 的 `ptrLock` **六条退出路径全部解锁**，且槽位随视图被钉住 —— 刷新时不会漏引用；
- 空行 / 零宽 / 极窄三种退化情形都被 `hg_grid.c` 与视图的分支挡住，索引安全；
- `setCompact()` 的 `tagText` 赋值时序正确。

### 那条"不确定"的项：**目前有证据了，但仍未在真机上定论**

审查明确拒绝猜的问题：**`demuxer-lavf-o` 是否在 `mpv_initialize` 时被缓存**，
从而运行期重写对下一次 `loadfile` 无效 —— 若如此，换清晰度会用**上一档的密钥**打开新流：
没画面、也没错误。

**查到的证据偏向"不缓存"**：mpv 手册说，一般性的选项
"if any option is changed at runtime (via input commands), they are not reset when a new file is
played"（[mpv(1) 手册](https://man.sourcentral.org/debian-unstable/1+mpv?pdf#44#2)）；
而 `demuxer-lavf-o` 是**文件局部选项**，现有的 `loadfile` 路径本来就是靠"播放前设好"工作的。

**但那是推理，不是测量。** 所以加了**回读**，把"应该能用"变成**下一次真机运行就能定论**的东西：

```
QUALITY: demuxer-lavf-o set rc=0, readback rc=0 length=64 (wanted 64), matches=1
```

`matches=0` 时日志会**明说**"mpv 没有接受新值，这次切换会用旧密钥打开新流"。
只打印长度与是否一致 —— 那是密钥，不是可打印的东西。

**真机上要确认的仍是最后一步**：`MPVEVT file-loaded` 之后**画面是否真的换了档**。
日志能把"写没写进去"和"写进去了但没生效"分开，而**后者只能靠眼睛**。

## 四、结论：为什么这一步值得做

审查花的是**一个会话的时间**，换来**两个 HANG、一个 CRASH、一个"没画面也没错误"**。
这四个里**没有任何一个**会被编译器、单元测试或我此前所有的静态推理发现 ——
它们全都依赖**框架的实际行为**（延迟删除池、事件队列、主线程 identity），
而那些行为**只有读框架源码才能确认**，靠记忆和直觉都会错。

**这比再写一个功能更符合目标里"从能用到好用"的意图**：一个换清晰度会黑屏、
刷新后按 A 会开错剧集的客户端，功能再多也不算"好用"。

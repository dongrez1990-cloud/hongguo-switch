# 封面图可行性调查

调查范围：`hongguo-switch`（borealis + deko3d + prebuilt libmpv/ffmpeg 的 Switch 自制客户端）。
本文只回答四个问题，每条结论都给出 `file:line` 或真实命令输出。

---

## 结论速览

| 问题 | 结论 |
|---|---|
| Q1 | **可以**。`brls::Image::setImageFromMem(const unsigned char*, int)` 就是内存入口（`image.hpp:106`）。没有 loader 注册表，但有更底层的 `brls::Image::innerSetImage(int texture)`（`image.hpp:108`）可直接塞 nanovg 纹理句柄。 |

## Q1. `brls::Image` 能否从内存拿像素？

### 公开构造函数

只有一个：

```cpp
Image();          // image.hpp:66
~Image();         // image.hpp:67
```

`Image` 没有接收像素的构造函数，尺寸/内容一律靠 setter 后置设置。

### setter / 公开方法（精确签名，均取自 `image.hpp`）

| `file:line` | 签名 | 说明 |
|---|---|---|
| `image.hpp:82` | `void setInterpolation(ImageInterpolation interpolation)` | 仅影响**后续**重新加载 |
| `image.hpp:90` | `void setImageFromRes(const std::string& name)` | romfs 资源名 |
| `image.hpp:98` | `void setImageFromFile(const std::string& path)` | 磁盘路径 |

| `image.hpp:110` | `void setImageAsync(std::function<void(std::function<void(const std::string&, size_t length)>)> cb)` | 异步拉取后走 `setImageFromMem` |

### 哪一个吃内存缓冲

**`setImageFromMem`**。实现只有三行（`image.cpp:348-354`）：

```cpp
void Image::setImageFromMem(const unsigned char* data, int size)
{
    NVGcontext* vg = Application::getNVGContext();
    // Load texture
    innerSetImage(nvgCreateImageMem(vg, 0, const_cast<unsigned char*>(data), size));
}
```

它把**已编码的文件字节**（JPEG/PNG/...）原样交给 nanovg；解码发生在 nanovg 内部
（`extern/nanovg/nanovg.c:842-853`，`stbi_load_from_memory` + `nvgCreateImageRGBA`）。
注意 `size` 是 `int`，且调用方必须保证 `data` 在调用期间有效——调用后即可释放。

若已有**解好的 RGBA 像素**（例如 ffmpeg 解码结果），则不要用 `setImageFromMem`，
应直接调 `nvgCreateImageRGBA()` 再 `innerSetImage()`；wiliwili 走的就是这条路（见 Q3）。

### 是否存在 loader 注册表 / `setLoader` 钩子？

**没有。明确地说：borealis 里不存在静态图片加载器注册表，也不存在 `setLoader` 风格的钩子。**

在 borealis 全库内检索 `setLoader|Loader|nvgCreateImageMem|stbi_`，命中的 `Loader` 只有字体系统
（`core/font.hpp:40` 的 `class FontLoader`、`platforms/switch/switch_font.hpp:25` 的
`SwitchFontLoader`），与图片无关。图片的加载是**硬编码**的：

- `image.cpp:341` → `nvgCreateImage(ctx, path, flags)`（文件路径）
- `image.cpp:353` → `nvgCreateImageMem(vg, 0, data, size)`（内存）

nanovg 侧也没有可替换的图片 IO 回调。因此要接任意字节来源，只有两条路：
**(1) 自己解码后调 `innerSetImage()`**，或 **(2) 把编码后的字节喂给 `setImageFromMem()`**
并接受 nanovg 内置 stb_image 的解码能力（JPEG/PNG/TGA/BMP/GIF，**不含 WebP**，见 Q2）。

### borealis 是否 vendor 了 stb_image？

**是，vendor 了头文件，并通过 `nanovg.c` 编译进 `libborealis.a`。**

- 头文件位置：`upstream\wiliwili\library\borealis\library\include\borealis\extern\nanovg\stb_image.h`
  （**注意不在** `lib\extern\` 下 —— `lib\extern\` 只有 fmt/glad/glfw/libretro-common/libromfs/
  nanovg/nxfmtwrapper/SDL/switch-libpulsar/tinyxml2/tweeny/yoga，**没有 stb_image**。
  该头文件位于 `include\borealis\extern\nanovg\`。）
- **没有** `stb_image.c` / `stb_image.cpp`；实现在 `nanovg.c` 内联展开：
  - `extern\nanovg\nanovg.c:29` → `#define STB_IMAGE_IMPLEMENTATION`
  - `extern\nanovg\nanovg.c:30` → `#include "stb_image.h"`
- 编译脚本确实编译了它：`scripts\build-borealis.ps1:124`

  ```powershell
  $sources += Get-Item "$ext\nanovg\nanovg.c"
  ```

  （该行处于 95–132 行的 `$sources` 汇总段内，`$ext = "$lib\lib\extern"` 定义在 `:47`。）
  `build-borealis.ps1` 中**没有任何独立的 stb 源文件条目**——没有，也不需要，因为它随 `nanovg.c` 一起进。

**直接推论：本项目今天就已经链接了完整的 stb_image（JPEG/PNG/TGA/BMP/GIF/PSD/PIC/PNM/HDR），
零新增依赖。** 缺的只有 WebP。

## Q3. wiliwili 如何把网络图片放到屏幕上

完整链路（`wiliwili\source\utils\image_helper.cpp`）：

| 步骤 | 位置 | 做什么 |
|---|---|---|
| 1. 发起 | `image_helper.hpp:41` | `void load(const std::string& url)` —— 主线程调用 |
| 2. 查缓存 | `image_helper.cpp:169` | `brls::TextureCache::instance().getCache(imageUrl)` 内存纹理缓存 |
| 3. 入队 | `image_helper.cpp:188` | `this->requestImage()`，交给 `ImageThreadPool`（`:101-103`，`cpr::ThreadPool`，默认 `REQUEST_THREADS=1`） |
| 4. **取字节** | `image_helper.cpp:206-216` | **`cpr::Session session; ... session.SetUrl(cpr::Url{imageUrl}); cpr::Response r = session.Get();`** —— 底层是 curl（`:207` 取 `CURL*` 句柄设置 `CURLOPT_SHARE`/DNS 缓存） |
| 5. 失败处理 | `image_helper.cpp:219-225` | 非 200 或 0 字节或已取消 → `clean()` 返回 |
| 6. **解码** | `image_helper.cpp:242` | **`stbi_load_from_memory((unsigned char*)r.text.c_str(), (int)r.downloaded_bytes, &imageW, &imageH, &n, 4)`** —— 强制 4 通道 RGBA，就地解码内存中的响应体 |
| 6b. WebP 分支 | `image_helper.cpp:236` | `WebPDecodeRGBA(...)`，仅 `#ifdef USE_WEBP`（`:234`） |
| 7. 回主线程 | `image_helper.cpp:260` | `brls::sync([...]{...})` |
| 8. 二次查缓存 | `image_helper.cpp:262-265` | 命中则 `imageView->innerSetImage(tex)` |
| 9. **交给 nanovg/deko3d** | `image_helper.cpp:273` | **`nvgCreateImageRGBA(vg, imageW, imageH, 0, imageData)`** → `image_helper.cpp:283` `this->imageView->innerSetImage(tex)` |
| 10. 记录到 LRU | `image_helper.cpp:280` | `brls::TextureCache::instance().addCache(imageUrl, tex)` |
| 11. 释放像素 | `image_helper.cpp:287-293` | `stbi_image_free` / `WebPFree` |

`nvgCreateImageRGBA` 的实现（`extern\nanovg\nanovg.c:856-859`）：

```c
int nvgCreateImageRGBA(NVGcontext* ctx, int w, int h, int imageFlags, const unsigned char* data)
{
    return ctx->params.renderCreateTexture(ctx->params.userPtr, NVG_TEXTURE_RGBA, w, h, imageFlags, data);
}
```

即回调进 deko3d 后端的 `DkRenderer`，最终由
`lib\extern\nanovg\deko3d\dk_renderer.cpp:63` 的 `Texture::Initialize(...)` 完成上传
（`:82-83` `image_pool.allocate` + `m_image.initialize`，`:88` `UpdateImage(...)`）。

### 是否缓存到 SD 卡？

**否。** `brls::TextureCache` 是**纯内存** LRU：
`include\borealis\core\cache_helper.hpp:299`

```cpp
LRUCache<std::string, size_t> cache = LRUCache<std::string, size_t>(200, 0);
```

键是 URL 字符串，值是**纹理 id（`size_t`）**，容量 200（`:299`，`DEFAULT_CAPACITY=400` 见 `:56`）。
全文件无 `fopen`/`ofstream`/文件 IO。进程退出即全部丢失（`:244-245` 退出时 `clean()`）。

### 是否依赖本项目未链接的库？

**不依赖。** 逐个核对：

| wiliwili 用到的东西 | 本项目状态 |
|---|---|
| `cpr::Session::Get()`（`:206`） | cpr 是 curl 的 C++ 包装；**本项目已链接 curl**（`libcurl.a` 存在于 portlibs）。若项目直接用 `curl_easy_perform` 亦可，语义相同 |
| `stbi_load_from_memory`（`:242`） | **已在 `libborealis.a` 内定义**（Q2 已验证） |
| `nvgCreateImageRGBA` / `innerSetImage` | 已在 `libborealis.a` 内定义（Q2 已验证） |
| `brls::TextureCache` | borealis 头文件即可用，纯内存 |
| `WebPDecodeRGBA`（`:236`） | **仅 `#ifdef USE_WEBP` 分支**。libwebp **不存在**于本环境，因此**编不过**该分支——但它是**可选的**，不定义 `USE_WEBP` 即可（此时 `IMAGE_EXT` 为 `.jpg`，见 `image_helper.hpp:55-59`） |

**结论：wiliwili 的这条链路，去掉 WebP 分支后，完全落在本项目现有依赖之内。**

## Q4. 结论与实施方案

### 三路线排序

| 路线 | 工作量 | 风险 | 评价 |
|---|---|---|---|
| **(a) 复用链接里已有的解码器** | **最低**（~60–120 行，一个文件） | **低** | ★ **推荐**。stb_image 已在 `libborealis.a` 里，JPEG 封面一步到位 |
| (b) 编译入 stb_image 并挂到 image loader | 中（若照抄 (a) 则**无意义**——见下） | 中 | 只有当需要 WebP 时才值得；但见下方"关于 stb_image 的说明" |
| (c) 保持纯文本列表 | 零 | 零 | 作为回退始终保留（解码失败不崩 UI） |

**关于路线 (b) 的重要澄清**：任务描述设想"编译入单个文件的 stb_image 并接到 borealis 的
image loader"。但 Q1/Q2 已证明 **borealis 没有 `setLoader` 钩子**，且 **stb_image 已经在
`libborealis.a` 里了**。所以 (b) 的"编译入"部分是多余的；真正需要的只是"调用"。
路线 (a) 与 (b) 因此**收敛为同一件事**：实现一个 `requestImage()` 风格的函数。
唯一会让 (b) 独立成立的场景是 **WebP**——那需要额外引入整个 libwebp（本环境完全没有），
成本远高于收益，**不建议**。

### 推荐路线 (a) 的具体计划

**新增文件**：`hongguo-switch/src/cover_loader.hpp` + `cover_loader.cpp`（与项目现有 `src/` 并列）。

**核心 API 调用序列**（照搬 `image_helper.cpp` 的已验证路径）：

1. `curl_easy_perform`（本项目已链接 curl）取封面字节到 `std::string`；
   或复用项目已有的 HTTP 封装。
2. `stbi_load_from_memory(bytes.data(), (int)bytes.size(), &w, &h, &n, 4)`
   —— 声明于 `include\borealis\extern\nanovg\stb_image.h:422`，
   定义已确认在 `libborealis.a`。
3. `brls::sync([...]{ auto* vg = brls::Application::getNVGContext();
   int tex = nvgCreateImageRGBA(vg, w, h, 0, pixels); img->innerSetImage(tex); })`
   —— `NVGcontext` 取法与 `image.cpp:350` 一致；`
   `innerSetImage` 见 `image.hpp:108`。
4. `stbi_image_free(pixels)`。

**行数估计**：解码 + 上传主路径 **约 40 行**；加上 curl 取字节、线程池
（可先用 borealis 的 `brls::async`/`Threading`，或简单 `std::thread`）、
以及"下载中/失败"占位图，总计 **约 100–150 行**。

**更省事的替代**：如果封面 URL 能先落到 SD 卡，直接
`img->setImageFromFile(path)`（`image.hpp:98`）零解码代码；或若有编码后字节在内存，
`img->setImageFromMem(data, size)`（`image.hpp:106`）同样零解码代码——
nanovg 内部已用 stb_image 解码（`nanovg.c:845`）。**先评估这两条，可能一行解码都不用写。**

### 上机风险（deko3d 纹理上传 / NPOT / 内存）

1. **NPOT**——从代码看**不构成风险**。deko3d 后端
   `dk_renderer.cpp:73` 直接 `dk::ImageLayoutMaker{device}.setFlags(0).setDimensions(w, h)`，
   **没有任何 2 的幂对齐或 `nearest_po2` 处理**；格式固定 `DkImageFormat_RGBA8_Unorm`（`:75`）。
   反过来说：**不做对齐，也不报错**，任意尺寸都按原样建立纹理。
   （对比 GXM 后端才需要 DXT 压缩与 po2——`image_helper.cpp:247-258`，Switch 上不走这条。）
2. **纹理内存**——真正的风险在显存池。`dk_renderer.cpp:82`
   `m_image_mem = image_pool.allocate(layout.getSize(), layout.getAlignment())`，
   池子的大小在 `DkRenderer` 构造时（`:108`）由调用方给定。
   **大量封面 + 无淘汰 = 池耗尽**。缓解：把封面尺寸压到
   `@168w_224h` 一类的缩略后缀（照 `image_helper.hpp` 的 `h_ext/v_ext` 思路，
   `:84-85` 桌面端即 `@672w_378h_1c`），单图 `168*224*4 ≈ 147 KB`。
   另外 `TextureCache` 容量上限 200（`cache_helper.hpp:299`），**注意缓存命中会占用引用计数，
   计数非 0 的条目永不淘汰**（`:46-48` 注释）。
3. **尺寸守卫**——`nvgCreateImageRGBA` 的 `w/h` 是 `int`，`setImageFromMem` 的 `size` 也是 `int`
   （`image.hpp:106`）。stb 解码失败返回 `NULL` 时**必须跳过 `nvgCreateImageRGBA`**，
   否则会走 `innerSetImage(0)` 并打印 `"Cannot set texture: 0"`（`image.cpp:370-373`）——
   不崩，但也没图；建议自己判空后再调。
4. **线程**——`nvgCreateImageRGBA` 会触碰 deko3d 设备与内存池，
   **必须在主线程调用**（wiliwili 正是用 `brls::sync` 从工作线程切回，`image_helper.cpp:260`）。
   在下载线程里直接建纹理是这类改造最典型的上机崩溃点。

### 单次上机最具决定性的检查

**用现有文本列表启动，在代码里硬编码一个已知的封面 JPEG URL，走
下载 → `stbi_load_from_memory` → `brls::sync` 内的 `nvgCreateImageRGBA` → `innerSetImage`
这条最小路径，只渲染一张封面。**

这一次运行能同时证伪/证实三件最关键的事：(1) curl 在 Switch 上确实取得到字节；
(2) stb_image 在这个 `libborealis.a` 里确实能解出 JPEG；(3) deko3d 的
`image_pool` 能容纳并正确显示一张封面纹理。三者全过 = 路线 (a) 成立，剩余只是工程化；
任一失败 = 已在问题的最小复现点，无需再猜。

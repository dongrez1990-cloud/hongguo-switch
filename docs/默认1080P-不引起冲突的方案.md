# 目标：默认 1080P，**不引起冲突** —— 实施方案（下一轮照此执行）

## 一、为什么前几次会"冲突"（= 必须避开的三个坑，均有日志证据 ✓）

| 坑 | 现象（日志原文） | 原因 |
|---|---|---|
| **坑 1：开播后再切档** | `build120`：双重音频 + 跳集 + 灰闪 ✓ | 切档 = **再发一次 loadfile** ✗，而流还在启动 → 拆了又装 ✓ |
| **坑 2：多一次网络往返** | `build136`：切集时**灰屏变长** ✗ | "先取阶梯定档"多一次请求 ✓（**无重载** ✓，但空档变长 ✗） |
| **坑 3：菜单/状态与播放不一致** | `playing tier stays 0` 而 `plan = 360p` ✗ | 阶梯只回 1 档时匹配不到 → 播种落到 `index 0` = 1080p ✗ |

**服务端本身不稳** ✓（同一集 20 秒内 `plan=360p` ✗↔`1080p` ✓、`ladder=5档` ✗↔`1档` ✓）→ 所以**必须自己按阶梯定档** ✓，且**不能依赖第 0 项** ✗。

## 二、做法（四处改动，**互不冲突** ✓）

### ① 缓存阶梯（解决坑 2 ✓）
- 位置：`PlayerView::Impl` 里加
  ```cpp
  std::string ladderCacheEpisodeId;                 // 这个阶梯属于哪一集
  std::vector<Client::QualityTier> ladderCache;     // 上次取到的完整阶梯
  ```
- 逻辑：**同一集**第二次及以后取阶梯时**直接用缓存** ✓ → **零额外往返** ✓✓
  （请求只在**第一次**发生 ✓；失败/空则照旧重新请求 ✓）
- 只有当 `ladderCache.size() >= 2` 时才认为缓存可用 ✓（**1 档的响应不缓存** ✗ → 避免把"只有 1 档"固化 ✓）

### ② 开局按 1080p 定档，只发一次 loadfile（解决坑 1 ✓）
- 位置：`PlayerView::start()` 里**发 loadfile 之前**（**绝不在 file-loaded 之后** ✗）
- 逻辑：
  ```
  取阶梯（优先缓存 ✓）
      ↓ 成功
  在阶梯里找 label 以 "1080" 开头的档 ✓ ；找不到 → 取第 0 档（阶梯最优在前 ✓）
      ↓
  Client::fetchPlayPlanForSource(episodeId, tier.sourceIndex, plan)   // 一次定档 ✓
      ↓ 失败
  退回 Client::fetchPlayPlan(episodeId, plan)                         // 保证能播 ✓
  ```
- **绝不调用 `switchQuality`** ✗（那是"重载"路径 ✓ = 坑 1 ✓）
- **不记住用户手动的选择** ✗：下一集**仍然默认 1080p** ✓ → 行为可预测 ✓、无冲突 ✓✓

### ③ 蓝点诚实（解决坑 3 ✓）
- 位置：阶梯到达处的播种（`impl->playingTierIndex = current;`）
- 逻辑：`current < 0`（匹配不上）时 → **`playingTierIndex = -1`** ✓ → **任何一项都不点亮** ✓
  （菜单**光标**仍可停在第 0 项 ✓ —— 那只是光标 ✓）
- 日志：`QUALITY: which tier is playing could not be determined … the menu will not mark any tier [build143]`

### ④ 灰屏期间给状态（可选，但推荐 ✓）
- 位置：`start()` 的 worker 里，取阶梯**之前**写一行状态文字（复用 `statusLabel` ✓）：
  `"正在选择清晰度…"` ✓（用 `hg_tr` 新键 ✓ 或先用英文 ✓）
- 目的：那一次往返有反馈 ✓ → 不像卡死 ✓

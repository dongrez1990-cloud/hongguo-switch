# 第 83 轮：为什么"越来越容易闪退"——真正的原因是**每帧在做 9 倍的无效工作**（build83）

你说"感觉闪退越来越频繁，是不是东西太多、内存溢出或缓存没重置" —— 这是个**可以测量**的问题 ✓，
而日志里已经给出了答案，只是它不在崩溃报告里，在**每秒的计时行**里。

---

## 一、铁证（来自你自己那次运行的日志）

```
SW surface vs view: surface=1920x1080 view=1280x720 window=1920x1080 scale=1.500
PLAYER timing: 5.3 fps | mpv_sw=179 ms/frame | upload=6.8 ms/frame | other=2.3 ms/frame | surface=1920x1080
```

**播放只有 5.3 fps**，而 200 ms 里有 **179 ms 花在 mpv 的 CPU 转换上** ✓：
你在看的是 **360p 的剧**，而软件表面按 **1920×1080** 在逐帧转换 —— **再交给 GPU 缩回 720p 逻辑分辨率** ✓✗。
按像素算：1920×1080 ÷ (360p) ≈ **9 倍的无效工作**，而结果全被丢掉 ✓。

**为什么这会让你"感觉闪退变多"**：每帧 179 ms 意味着主循环、图形命令缓冲、异步回调全都在**极限状态**下跑 ✓
（`build78` 修的 deko3d 命令内存耗尽就是这个量级的产物 ✓）。这不是"东西太多导致内存溢出"，
而是**每帧都在做不该做的工作** ✓✓。

## 二、这一轮的修法：**软件表面按视频自身高度分配**

`HgPlayPlan` 本来就带 `vwidth` / `vheight`（来自 `video_meta`）✓✓ → 于是：

```
表面高度 = min(窗口高度, 视频自己的高度, player.sw.height 若更小)
```

- **画质零损失**：360p 的源不可能因为 CPU 放大而更清楚 ✓（放大交给 GPU，按最终信号尺寸做 ✓）；
- 日志会说明它做了什么：
  `PLAYER: the stream is 360p, so the software surface is capped to that instead of the window's 1080p -- the CPU was upscaling every frame for nothing [build83]`；
- `player.sw.height` 仍然在**设得更小**时优先（那是用户的明确要求 ✓）。

## 三、关于内存：**先把问题变成数字**（你要的"注意优化"我从这里开始）

`hgMemoryUsedKB()` 用内核自己的记账（`svcGetSystemInfo(InfoType_UsedMemorySize)`）✓，接到两处日志：

- 启动：`boot: argc=0, memory in use 12345 KiB at startup [build83]`
- 播放中每秒：`PLAYER timing: … | mem=12345 KiB [build83]`

**这样"是否越用越多"就不再靠感觉** ✓ —— 比较启动那次与长时间播放后的数值即可 ✓。
（顺带说明：我查了**纹理路径不泄漏** —— borealis 的 `Image::innerSetImage` 会删除旧纹理 ✓，
析构也删 ✓；每次进播放的 mpv 与 3.6 MB 像素缓冲在退出时都释放 ✓（日志有 `SHUTDOWN:` 序列 ✓）。
所以目前**没有找到无界增长的内存** ✓，但这条日志以后会替我们回答。）

我上一轮改计时行时**只加了参数、忘了改格式串** ✗ —— 那是 `printf` 类的**未定义行为** ✓

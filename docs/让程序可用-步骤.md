# 让程序能够真正使用：步骤

## ★★★ 全链路已在真机跑通（2026-10-08）

```
[1] 首页      → 36 张卡片（真实 186 KB 页面 → 45,598 字节 _ROUTER_DATA）
[2] 详情页    → 509,397 字节 → 76 集分集列表
[3] 签名视频模型 → POST 200，19,381 字节
    播放计划  → codec=bytevc1  360p 360x640  bitrate=241691
                encrypt=1  kid=6822c083f8818b957fb273630002ebeb  cenc-aes-ctr
    派生密钥  → 86c22eed79003130e78191b09b7588e5
[4] mpv       → 带该密钥：time-pos=0.27 picture-type=B  【解出真实帧】
                不带密钥：NO FRAMES
                故意错密钥：NO FRAMES
```

**最后那个三组对照是全项目最关键的一次测量。** 它同时证明：

1. **`--demuxer-lavf-o=decryption_key=` 在 Switch 版 mpv 上确实生效**
2. **`hg_spade_content_key()` 派生出的密钥是正确的**——用它对一个**真实在线加密流**解出了帧
3. **CENC 解密是必需的，且已工作**

### 为什么这个对照非做不可

第一次 A/B 只跑了"有密钥 / 无密钥"，两组都报 `DECODE OK`。**但那什么也没证明**：
`width`/`height`/`duration` 来自**未加密的容器头部**，加密乱码样本一样会让 mpv 报出它们。
**如果只看那一次，会得出"播放零特殊处理"的结论，从而砍掉一整套必需的解密代码。**

真正把它们分开的是**第三组：故意错误的密钥**——它和无密钥表现完全一致，而正确密钥出帧。

**判据必须是"有没有解出帧"（`time-pos` 推进 / `picture-type` 出现），不是"头部能不能读"。**

### 一个未能解释的现象（不掩饰）

上一轮无密钥那次报 `width=360 height=640`，本轮是 `width=0`；**两次 CDN 主机不同**
（`v95-bjb-mc-…` → `v5-daily-cm-…`）。可能是不同节点对未授权请求行为不同。
**本轮的 C 对照自洽且决定性**，但这个差异我没有解释。

## ★ 播放链实测结构（本机跑通，非推断）

**整条链已在本机验证通过**：首页 → 详情页（222 集）→ 签名视频模型请求 → 21,836 字节真实响应 → 可播放 URL。

### 响应是**双重编码**的

```
外层: {"BaseResp":{...},"code":0,"data":{"<vid>":{"video_model":"<JSON字符串>",...}}}
内层: JSON.parse(data[vid].video_model)
      → { status, message, version, video_id, video_duration, url_expire,
          big_thumbs, fallback_api, video_list, pallas_vid_labels }
```

**`video_list` 在内层。** 在顶层找它永远找不到——请求再成功也没用。

### `video_list[]` 条目的真实字段

```
main_url, backup_url, video_meta, encrypt_info, check_info,
volume, quality_type, pallas_fid_labels, feature_id, gear_des_key
```

**关键：三个字段都在子对象里，不在条目顶层。**

```json
"encrypt_info": { "encrypt": true,
                  "kid": "6ac13d1b476d5a03cc1186750002ebeb",
                  "spade_a": "o7wt82W8HvJTiAPxerox8Xq7A/R/iAPEf7gExlSWKtlmly6IiA==",
                  "encryption_method": "cenc-aes-ctr" },
"video_meta":   { "definition": "360p", "codec_type": "bytevc2", "vtype": "mp4",
                  "vwidth": 640, "vheight": 360, "bitrate": 216741, "size": 5172264 },
"quality_type": 40
```

| `hg_play.c` 当前在哪找 | **实际在哪** |
|---|---|
| `main_url` 顶层 ✓ | 顶层 |
| `spade_a` 顶层 ✗ | **`encrypt_info.spade_a`** |
| `codec_type` 顶层 ✗ | **`video_meta.codec_type`** |
| `key_seed` 顶层 ✗ | **不存在**（`main_url` 本来就是明文） |

**不实测就上真机的后果**：过滤器失效 → 挑中 `bytevc2` → 黑屏；
`spade_a` 取不到 → 没有 CENC 密钥 → mpv 解不开 → 黑屏。
**两个都不报错，都只是"没画面"。**

### 流本身确认

`main_url` 是 696 字符明文 URL（无 `key_seed`，不需要 spade 解密），
`Range: bytes=0-127` 返回 **206 / `video/mp4` / `Content-Range: bytes 0-127/5172264`**，
首字节 `0000001c 66747970 69736f6d`（`ftyp isom`）——**是真的 MP4，能播**。

**所以 CENC 解密确实是必需的**（`encryption_method: cenc-aes-ctr`），
第 2–11 轮做的那些工作没有白费。

> 一条补充教训：我曾因为**在顶层找不到 `spade_a`** 就断定"流没有加密"，
> 下一轮就自己推翻了。**字段在哪一层必须实测**——这和"参数名靠猜"是同一类错误。

### ⚠ 字段名按「位置」分两组，不能统一

**这是本文档先前的一个错误，实测纠正后如下：**

| 位置 | 标题字段 | 封面字段 |
|---|---|---|
| `bannerList[]` / `mBannerList[]`（横幅） | **`series_name`** | `series_cover` / `background_cover` |
| **`homeSections[].video_list[]`（板块卡片）** | **`series_title`** | 见下 |

实测计数（36 张板块卡片）：**`series_name` 出现 0 次，`series_title` 出现 36 次。**

> 先前本文档写"首页用 `series_name`"——那是**从横幅的形状推广出来的**，
> 没有单独去看板块卡片。照那个写，**36 张卡片的标题会全部被判为缺失而丢弃**。

`mBannerList` **没有** `series_cover`（只有 `background_cover`），所以封面需要一个回退链。

| 用途 | hg_api 原先推断的 | **实测真实的** |
|---|---|---|
| 剧集 ID | `series_id` ✓ | `series_id` |
| 标题（横幅） | `title` ✗ | `series_name` |
| 标题（板块卡片） | `title` ✗ | **`series_title`** |
| 封面 | `cover` / `cover_url` ✗ | `series_cover` / `background_cover` |
| 简介 | `video_desc` ✗ | `series_intro` |

**封面 CDN 主机名会轮换**（`p3-` / `p6-` / `p11-` …），所以断言应写不变量
（非空、https、`byteimg.com`），**不能断言主机前缀**。

### `codec_type` 不止一种

实测 `video_list` 里同时出现 **`bytevc2` 和 `bytevc1`**。
**`bytevc1` 是可解码的另一种编码**，把它和 `bytevc2` 一起当成"不可解码"会**拒掉唯一可用的 1080p 源**。
过滤只能排除 `bytevc2` / `bvc2`。

各页的 `loaderData` 键**是动态的**（含路由名），不能写死：

| 页面 | loaderData 的键 |
|---|---|
| 首页 | `layout`, `page` |
| 分类 | `category_layout`, **`category_page`** |
| 搜索 | `search_layout`, **`search_(keyword)/page`** |
| 榜单 | `rank_layout`, **`rank_hot-comic-drama/page`** |

所以解析器必须**按"取第一个含内容的对象"来找**，而不是按固定键名——这与 Kotlin 的
`router(url).getJSONObject("loaderData")` 之后的处理方式一致。

## 步骤 1：HTTP + 签名，在真机上打出一次真实响应 ★最高价值

**做什么**：`hg_http.c` —— 基于已编好的 libcurl（Switch 侧走 libnx TLS），
把设备参数与签名头（`x-gorgon`/`x-helio`/`x-medusa`/`x-argus`/`x-khronos`/`x-ss-stub`…）装上去，
发一个**真实的签名搜索请求**。

**为什么先做这个**：它是**一次就能验证整条链**的判据——DNS、TLS、证书、HTTP、签名、
header 拼装、响应读取，全在这一次请求里。**任何一环错，屏幕上立刻看得到。**

**产物**：`hg_http.{h,c}` + 一个新的自检 NRO，屏幕上打印 HTTP 状态码、响应长度、以及响应前若干字符。

**怎么验证**：真机跑，看到 HTTP 200 且响应里出现 `series_id` / `title` 字样。
若 403/签名错误，报文会直接告诉我们哪一步不对。

**依赖**：无。

**风险**：需要决定**设备指纹问题**（那 27 项 Redmi 参数）。上游可能因为它与真实设备不符而拒绝——
这一步会**第一次给出答案**，且失败信息是可诊断的。

## 步骤 1 的精确规格（已从参考实现提取，不必再读 JS）

来源：`server/vendor/hongguo.cjs` 第 25–27、79–85、405–437 行。

### URL 编码（`pythonUrlEncode`，第 79 行）

**保留字符集**：`A-Z a-z 0-9 - _ . ~ *`
（JS `encodeURIComponent` 额外保留 `! ' ( )`，但紧接着被 `.replace(/[!'()]/g, %XX)` 转义，
所以最终安全集就是上面那八个类别。）

其余字节按 **UTF-8** 逐字节编码为 `%XX`，**十六进制大写**。键与值都编码，用 `=` 连接、`&` 分隔。

> 注意 `*` 被保留而 Python 的 `quote` 会转义它——**这一个是签名相关的差异，不能想当然。**

### 请求参数

`{ ...DEVICE, ts: String(khronos), _rticket: String(ticket) }`

- `DEVICE` 就是 `hg_tables.h` 里的 `HG_DEVICE`（27 项，顺序即插入顺序，**必须保持一致**）
- `khronos` = 秒级 Unix 时间
- `ticket` = 毫秒级 Unix 时间（`Date.now()`）

### 搜索（GET）

- URL：`https://api5-normal-sinfonlinea.fqnovel.com/reading/bookapi/search/tab/v?<query>`
- body：无
- `random = floor(rand()*65536)`
- 响应：`{"code":0,...}`，`code != 0` 视为失败

### 视频模型（POST）

- URL：`https://api5-normal-sinfonlineb.fqnovel.com/novel/player/multi_video_model/v1/?<query>`
- body（JSON 字符串，原样发送）：
  ```json
  {"biz_param":{"detail_page_version":0,"device_level":3,"disable_digg_stat":false,
    "need_all_video_definition":true,"need_mp4_align":false,"use_os_player":false,
    "use_server_dns":false,"video_platform":1024},
   "mixed_video_id_map":{"1004":["<vid>"]}}
  ```
- **branch 重试**：`_rticket` 从 `ticketBase` 起 +0…+31，取第一个 `branchOf(url, body, khronos) !== 1` 的。
  （即接受 branch 0 或 2，只避开 1 —— 见 hg_sign.h 的 BRANCH COVERAGE。）

### 签名头（两处共用）

| 头 | 值 |
|---|---|
| `User-Agent` | 搜索用 `HG_APP_UA`；视频模型用 `HG_VIDEO_UA`（都在 `hg_tables.h`） |
| `Accept` | `application/json; charset=utf-8,application/x-protobuf` |
| `Content-Type` | 仅 POST：`application/json; charset=UTF-8` |
| `x-ss-req-ticket` | `ticket`（毫秒，十进制字符串） |
| `x-tt-request-tag` | `t=0;n=0` |
| `sdk-version` | `2` |
| `passport-sdk-version` | `50561` |
| `x-xs-from-web` | `0` |
| `x-vc-bdturing-sdk-version` | 仅 POST：`3.7.2.cn` |
| `x-khronos` | `khronos`（十进制字符串） |
| `x-ladon` | `base64(be32(khronos))` ← **大端** |
| `x-argus` | `base64(le32(khronos))` ← **小端** |
| `x-gorgon` | `hg_xgorgon(query, body, khronos, random)` |
| `x-helios` | `hg_helios(khronos, rng, …)` |
| `x-medusa` | `hg_build_medusa(url, body, len, khronos, rng, …)` |
| `x-ss-stub` | 仅 POST：body 的 **大写** MD5（`hg_hex_upper`，注意是大写） |
| `x-tt-dt` | 空字符串 |

**注意 `x-medusa` 需要完整 URL（含 query），不是只要 query。**

## 步骤 3：播放链路 —— 到这一步就"能看片"了 ★

**做什么**：把取到的播放信息交给 libmpv：
1. `main_url` 是 Spade 加密的 → `hg_spade_decrypt_url()`（已实现）
2. `spade_a` → `hg_cenc_derive_key()`（已实现）
3. mpv 参数：
   - `--http-header-fields="Referer: https://novel.snssdk.com/,User-Agent: <VIDEO_UA>"`
   - `--demuxer-lavf-o=decryption_key=<hex>`

**为什么这一步是分水岭**：它是**唯一还没被任何测试覆盖过的假设**。
我在第 7 轮验证了 switch 版 `libavformat.a` 确实带 `decryption_key`、`libmpv.a` 支持 `demuxer-lavf-o`，
但**从没真实链接验证过**。这一步要么确认那条路径成立，要么证明需要退回自写解密数据源。

**产物**：一个能播单集的最小程序（无 UI，屏幕上出画面即成功）。

**怎么验证**：真机出画面 + 有声音。

**依赖**：步骤 2。

---

## 步骤 4：应用外壳（UI 与手柄焦点）—— 到这一步才"好用到能天天用"

**两条路，建议 B**：

| | A：fork wiliwili 换 API 层 | B：独立小程序（推荐） |
|---|---|---|
| 做法 | 保留它的 Activity/XML/RecyclingGrid，重写全部 presenter | 用 borealis（wiliwili 的 UI 子模块）+ libmpv 自己搭 |
| 优点 | UI 完成度天然高 | 代码量小得多；不背 wiliwili 那套 B 站耦合 |
| 代价 | 要把每个 presenter 从 B 站改成红果，工作量大且散 | 列表/详情/播放三个页面要自己写 |

**建议 B** 的理由：wiliwili 的 UI 是围绕 B 站的领域模型搭的（稿件、番剧、直播间、动态…），
红果只需要"列表 → 详情 → 选集 → 播放"四个页面，**移植它的抽象比重新搭更慢**。

**产物**：`hg-app` —— 主页（封面网格）+ 详情（选集）+ 播放器（mpv + 手柄控制）。

**怎么验证**：手柄方向键能刷、A 键进详情、B 键返回、播放中能暂停/快进/切集。

**依赖**：步骤 3。

## 步骤 5：打包与分发

**做什么**：
- NRO（现在就能出）→ 直接放 `sdmc:/switch/`
- NSP：`hacbrewpack` 已能跑，只差组装 `exefs/main.npdm`（从仓库自带 `template/npdm.json` 生成）
  + `exefs/main` + icon。也可用本机已有的 `nsp-server.mjs`（DBI 的 Home server）直接安装。

**依赖**：步骤 4（内容定了才值得打包）。

## 顺序与可验证性小结

| 步骤 | 能否离线验证 | 能否真机验证 | 阻塞后续 |
|---|---|---|---|
| 1 HTTP+签名 | 部分（可对本地服务） | ✅ 一次请求看全部 | ✅ 是 |
| 2 端点+模型 | ✅ 合成响应 | ✅ 打印中文标题 | ✅ 是 |
| 3 播放 | ❌ | ✅ **出画面** | ✅ 是 |
| 4 UI | ❌ | ✅ 手柄操作 | — |
| 5 打包 | ✅ NRO 结构 | ✅ 从 hbmenu 启动 | — |

**关键判断**：步骤 1 和 3 是**两个不可离线验证的关口**，而它们恰好是"能不能用"的全部风险所在。
其余（2/4/5）都只是工作量。

---

## 建议的立即动作

**做步骤 1**，并且**用一个最小的自检 NRO**（不碰 UI）——因为：
- 它一次验证整条网络+签名链路
- 失败信息可诊断（状态码 + 报文）
- 成功之后，步骤 2 几乎是照抄 JSON 读取器已有的能力

如果步骤 1 就撞上"设备指纹被拒"，那是一个**必须在做 UI 之前知道**的结论——
否则会把 UI 全部做完才发现接口根本不通。

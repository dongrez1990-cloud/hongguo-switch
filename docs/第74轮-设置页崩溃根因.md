# 第 74 轮：设置页那次崩溃的根因（K8）（build74）

上一轮从截图里发现：**11:25/11:30 那两次崩溃发生在设置页，与后来的"启动必崩"不是同一次**。
这一轮把它**按代码查实了** —— 又是同一类 use-after-free，但藏在另一个地方。

---

## 一、根因：网络探测往**已销毁的行走**里写

```cpp
auto* rows = new NetState();          // 故意泄漏：这个结构要活过 makeNetworkGroup()
                                      // 但它里面存的是 DetailCell* —— 那些行会随界面销毁
cell->registerClickAction([rows](brls::View*) { runProbe(rows); return true; });

void runProbe(NetState* st) {
    st->rows[NET_ROW_API]->setDetailText("running...");
    hg::runDetached([st]() {
        NetworkProbe p = Client::networkProbe();        // 一次 HTTPS，要几秒
        brls::sync([st, p]() {
            st->rows[NET_ROW_API]->setDetailText(...);  // ← 此时设置页可能已经退出了
        });
    });
}
```

**"结构是泄漏的、所以指针还有效" 是这里最要命的错觉**：`NetState` 自己活着 ✓，
但它指向的 `DetailCell` **随界面一起销毁** ✗ —— 于是回调写进已释放的内存 ✓✓。

这解释了截图看到的一切：崩在**同步任务**里 ✓（栈在 `task_loop` / `_Function_base::~_Function_base` ✓）、
崩在**设置页** ✓、**间歇性**（取决于用户是否在探测返回前离开 ✓）。

**顺带排除了另一个猜想**：borealis 的 `performSyncTasks` 是"先把任务表**拷到局部**再执行"
（`thread.cpp:102-119`）→ 所以"任务里再投任务"是安全的 ✓，不是它 ✗。

## 二、修法：存活令牌传进探测

`SettingsActivity` 现在也持有令牌（与另外六个界面一致 ✓），并且：

- 析构里 `kill()` ✓；
- `createContentView` 取出 `const AliveToken alive = this->alive_;` ✓；
- 网络页的构建函数 `makeNetworkGroup(alive)` ✓ → 点击回调与探测回调都捕获它 ✓；
- 回调**第一行** `HG_GUARD_ALIVE(alive);` ✓ —— 界面一走，回调直接返回 ✓。

> 顺带一个确认：**wiliwili 上游自己用的正是这套做法** —— 它的 Presenter 宏 `ASYNC_RETAIN` / `ASYNC_RELEASE`
> 就是"捕获令牌、回调里先检查"（`wiliwili/include/presenter/presenter.h`）。也就是说这个修复不是自创，
> 而是回到上游的既定约定 ✓。

# 第 60 轮：画面滤镜"改了没变化"的根因与修复（I3）（build60）

**先取日志，再改代码** —— 而日志本身推翻了两件事。

---

## 一、日志给出的两条事实

我把主机的 `/switch/hongguo.log` 取了回来（31 KB）：

```
[hg 14:37:47] === hongguo app log, built Oct 10 2026 14:29:08 ===     <- 跑的是 build39
[hg 14:37:47] CFG: option hwdec = 'no'
（整个日志里 PLAYERMENU 行数：0）
```

1. **`hwdec = 'no'`** → 这个 App 跑的是**软件解码** —— 交接文档 §2.5 猜的"直接硬解绕过滤镜链"**站不住**
   （这一点交接文档自己也标了怀疑）。
2. **整个运行里没有一条 `PLAYERMENU`** → 那次没打开过画面菜单，所以**这条日志无法定因**（差一次实测）。

## 二、顺着"软件路径 + 滤镜无效"查下去，找到了更可能的根因

源码里两条：

```
player_view.cpp:821   mpv_set_option_string(mpv, "vo", "libmpv");
player_view.cpp:960   MPV_RENDER_API_TYPE_SW          <- 软件渲染 API
```

mpv 的 **`brightness` / `contrast` / `saturation` / `gamma` / `hue`** 是它的"video equalizer"，
**由 GPU 视频链当作 shader 参数**应用 —— **软件路径没有这一级**。
于是：**属性写入成功、读回也对，画面就是不变** ✓✓ —— 与用户报的现象**逐字吻合**。

## 三、修复：同一个意思，改用**真正的滤镜**说

ffmpeg 的 `eq` / `hue` 是**普通视频滤镜**，在任何路径（含软件）都生效。新增 `hg_pmenu_vf()`
**一次构造整条 `vf` 链**，转换按两边各自的中性点：

| mpv 属性 | 中性 | 滤镜参数 | 中性 | 换算 |
|---|---|---|---|---|
| brightness | 0 | eq brightness | 0 | `v/100` |
| contrast | 0 | eq contrast | 1.0 | `1 + v/100` |
| saturation | 0 | eq saturation | 1.0 | `1 + v/100` |
| gamma | 0 | eq gamma | 1.0 | `1 + v/100` |
| hue | 0 | hue h | 0° | `v × 1.8` |

三个设计点：

1. **中性值不写链**：全是中性时 `vf` 是**空串** —— 带中性参数的 `eq` 仍要过一次滤镜，
   在主机这条软件路径上，那正是这台机器没有的 CPU。
2. **一个写入者**：镜像原来单独写 `vf`，两个写入者会**悄悄丢掉一半**；现在整条链在一个字符串里组装。
3. **`player.eq.mode=props`** 保留旧行为（只写属性），一行 cfg 就能退回 —— 这是本项目对每个有风险的改动
   的固定做法。

**属性仍然照写**：GPU 路径会用它们，而且不要钱；日志会把这件事说清楚：

```
PLAYERMENU: vf = 'eq=brightness=0.5000:contrast=1.0000:saturation=1.0000:gamma=1.0000' -> set rc=0, read back '...' (rc=0) [build60]
PLAYERMENU: the five properties are for a GPU path; on THIS software path the 'eq=...' chain is what changes the picture
```

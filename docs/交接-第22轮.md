## 1. ★ 第一件事：一次请求拿全（去掉每集第二次请求）

### 为什么现在做得了

build156 换上的新接口是**单条**的 `/novel/player/video_model/v1/`，**一次响应就带着整条 `video_list`（五档全给）**。
**而"计划"和"档位"读的本来就是同一个内层文档**，只是两个解析器：

```
一次 POST 的 body
  └─ hg_play_model_inner()            解出内层 JSON 字符串（data.video_model，双重编码）
       ├─ hg_play_plan_from_model()   → 计划（选一条源）      ← fetchPlayPlan 用
       └─ hg_api_parse_video_model()  → 全部档位（建菜单）    ← fetchQualityLadder 用
```

**所以不需要新接口、也不需要新解析**，只要让这两条路**共用同一次 POST 的那份 body**。

**但现在的代码仍然发两次请求**：
```
player_view.cpp  fetchPlanOnPreferredTier → Client::fetchPlayPlan         ← 请求 1
                  startQualityLadder       → Client::fetchQualityLadder    ← 请求 2
```

**真机上看得见的代价**（第 21 轮实测）：
```
19:48:45 PLAYER: mpv started, plan = 1080p 1920x1080  codec=bytevc1  CENC key derived
19:48:46 QUALITY: ladder ready (1 tiers, first '1080p  ·  HEVC')     ← 同一次会话、前两集都是 5 档
```
服务端**仍会偶发少给档位**。两次独立请求时，谁拿到"少档位"的那份谁就退化 → 菜单显示与实际播放可能不一致。
**共用同一次响应之后，两者来自同一份数据，不可能再对不上。**

### 落点与做法
- **只改 `hg_client.cpp`**：加一个入口（如 `fetchPlayPlanWithLadder(episodeId, plan, tiers)`），
  一次 POST，然后把**同一份** `g_page` 分别喂给两条**现有**解析路径（不要另写解析）。
- **`fetchQualityLadder` 不删**：换档（`fetchPlayPlanForSource`）**仍要重新取** —— URL 是限时签名的。
- `player_view.cpp`：`startQualityLadder` 改成"计划成功时把 tiers 一起交出来"。

### 怎么验（**注意：现在日志里看不出发了几次 POST** —— 先补一行日志，别靠猜）
1. **先加可数的日志**：`postVideoModel()` 与 `fetchPlayPlan()` 各打一行（如 `QUALITY: video-model POST (plan path)`）。
   **现在两条路都不打请求行** ✗，所以"只发一次"这件事**无法从日志证明** —— 这本身就是第一个要补的东西。
2. 开播路径里不应再出现 `Client::fetchQualityLadder`（`grep` 可见）。
3. 真机：菜单 5 档、"正在播的那一档"与 `plan = …` 一致；每集只出现一行 POST；`PLAYCHECK` 自检仍全绿。
4. 顺带消掉一个已知症状：`QUALITY: ladder ready (1 tiers…)` 应当不再出现。

> **也可以改做 §5 里别的**（⑤ 续播、④ 触屏拖动、⑥ 剩余中文）—— 但 §1 是唯一"少一次请求 + 消掉一类偶发不一致"的，
> 且改动被限制在 `hg_client.cpp` 一处。

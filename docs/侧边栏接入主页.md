## 1. 关键点：导航是"布局"给的，不是"按键拦截"给的

整个接入就是一次布局改动：

```
box (COLUMN)                        ← 活动的内容视图
 ├─ headerRow (ROW)                ← 标题 + 刷新按钮
 └─ mainRow (ROW, grow=1, STRETCH)  ← ★ 新加的这一层
     ├─ SidebarView (COLUMN, 宽 120)
     └─ 网格（grow=1，原来直接挂在最外层 box 上）
```

有了这一层 ROW，框架自己的遍历就把四个方向都做对了：

| 方向 | 谁在做 |
|---|---|
| **左右** | `mainRow` 是 ROW，遍历它的两个孩子 → **在侧边栏和内容之间来回** |
| **上下** | ROW 不处理上下，交给孩子；侧边栏自己是 COLUMN，于是**在栏内逐项走**（间隔用的 spacer 不是 `Item`、也不可聚焦，自动跳过） |
| **上到第一项** | 继续交给父节点 → `headerRow` → 刷新按钮（和网格里一样） |

**没有拦截任何按键，没有轮询，网格和侧边栏都没有自己调用 `giveFocus`。**
这一点在这两轮里格外重要：前两轮刚刚从这块屏幕上**删掉**了第二个移动者，
为了放一个侧边栏再重新引入一个是同一个错误换个名字。

**唯一的补丁**（两行）：两个网格的 `getNextFocus` 在收到 LEFT/RIGHT 时，
以前一律 `return nullptr`（"不是我的问题"），现在把这个死路**交给父节点**：

```cpp
if (this->getParent()) return this->getParent()->getNextFocus(direction, this);
```

不交出去，焦点就永远出不了网格的左边界，侧边栏也就够不着。这正是
`Box::getNextFocus` 对"做不到的方向"的做法（`box.cpp:416-419`）。
选集网格同样改了：那边左边没有东西，父节点找不到目标，行为与以前完全一样——
两个网格写成一模一样是为了它们不会各自漂移。

## 2. 收藏 / 历史 为什么是灰的（以及一条要更正的旧结论）

侧边栏的四项：`主页`（sections）、`收藏`（sections）、`历史`（sections）、`设置`（pinned，沉在底部）。

`hg_sidebar_build` 拿到的是**事实**：这一版**没有**收藏、**没有**历史。
交接文档 §2.3 里写过"播放开始时写历史记录（`hg_history_put` + `hg_history_save`）"，
**那是错的**：全项目搜下来，`app/hongguo/` 下**没有任何地方调用 `hg_history_*` 或 `hg_fav_*`**
（只有 `hg_sidebar_view` 自己提到过这两个词）。数据层（92 项测试）写好了，但**还没接进播放器和详情页**，
所以那两个文件在 SD 卡上根本不存在。

模型对这种情形的规则是**建出来但置灰**，而不是隐藏：

> "a user who has saved nothing sees a dim entry they can read and understand, instead of walking
> into an empty page to find out it is empty."

为了让"灰"不成为一个谜，这两项还各自带了一行副标题 `还没做好`（`HG_T_NOT_BUILT_YET`）。
等收藏/历史那两个页面做出来（§6 第 5 项）并把数据层接上，两个 flag 变成真实的条数，
这两项就会自动亮起来，侧边栏一行都不用改。

**激活行为**（`onSidebarActivate`，按**语言键**而不是下标分派，插入新项不会错位）：

| 项 | 按下 A / 点一下 |
|---|---|
| 设置 | push 设置界面（和主页按 Y 同一条路） |
| 主页 | 把焦点送回内容（已经在主页了，这是"回内容"最实在的含义） |
| 收藏 / 历史 | 通知 `还没做好`（灰项无法聚焦，副标题已经把话说在前面） |

## 3. 这一轮**没有**做的（诚实清单）

- **LB / RB 换组**：模型有 `hg_sidebar_step`（组内环绕、跳过灰项），本该挂在肩键上。
  但这一版只有"主页"和"设置"两项是 enabled 的，而它们各自是组里唯一一项，
  `hg_sidebar_step` 会原样返回——**按了没有任何可见效果**，所以先不接，留给收藏/历史落地时一起。
- **收藏 / 历史两个页面**（§6 第 5 项）。
- **回到主页时刷新侧边栏状态**：数据层接上以后需要在 `HomeActivity::onResume()` 里重读条数，
  这一版两个 flag 是常量，接了也是空转。
- 侧边栏**不是抽屉**、不可折叠：wiliwili 的电视版也是常驻左栏。

**退路（不需要重新构建）**：`hongguo.cfg` 里加一行 `home.sidebar=no`，内容行就没有侧边栏，
和这一轮之前完全一样。这是项目对"改动一块本来能用的屏幕"的硬要求。

## 6. `build34` 第一次装机闪退：根因、修复、以及为什么之前没抓到

**症状（用户报告）**：「安装了 34，怎么直接闪退了？没有任何提示报错」——屏幕上确实什么都没有。

**原因在日志里**（`sdmc:/switch/hongguo.log`，取回后是 `out/crash-hongguo.log`）：

```
[hg 12:37:11] HOME: ENTER createContentView
[hg 12:37:11] HOME: refresh button added to the header row
[hg 12:37:11] FATAL std::terminate reached (uncaught exception or explicit call)
[hg 12:37:11] FATAL exception what() = Unknown theme value "brls/separator" in size: 35
[hg 12:37:11] FATAL the process is about to abort; the line above is the reason
```

**机制**：`SidebarView` 的构造函数给左侧描边取颜色时用了 `"brls/separator"` ——
**这个主题里没有这个键**（真实存在的是 `"brls/sidebar/separator"`）。而 borealis 的
`ThemeValues::getColor` 对未知键是**致命**的（`theme.cpp:155-156`）：

```cpp
if (this->values.count(name) == 0)
    fatal("Unknown theme value \"" + name + "\" in size: " + ...);
```

`fatal()` 抛出（`util.cpp:43`），没人接住，`std::terminate` → abort。
**进程在第一帧画出来之前就没了**，所以屏幕上没有任何提示——这正是"日志优先"这个习惯存在的理由：
**没有那条 FATAL，这一轮就只能靠猜**。

**为什么之前没抓到**：这个视图是**第 17 轮**写的，写完一直没有被实例化过——**直到这一轮才第一次真正执行**。
一行从没跑过的代码，里面有一个错的颜色键，在它上线的瞬间把整个 App 杀掉。

### 修法（三层，缺一层都可能再来一次）

| 层 | 改动 |
|---|---|
| 1. 用对的键 | `brls/separator` → **`brls/sidebar/separator`**（两个主题变体里都有） |
| 2. 让颜色键再也杀不掉 App | 该文件新增 `themeColor(key, fallback)`：`try/catch` 包住查询，失败时**记一行日志并返回兜底色**。颜色取错的正确失败方式是"某个边框颜色不对"，而不是"进程消失" |
| 3. 让这个错误在主机上就被抓住 | `app/src/tests/run.ps1` 新增一节 **theme keys**：把 `app/hongguo/*.cpp` 里用到的每个 `brls/...` 键与 borealis 的 `theme.cpp` 表对照，缺一个就整个套件失败并**报出键名和文件名** |

第 3 层做过**反向验证**：把坏键临时写回去、跑一次套件，输出是

```
theme keys: 35 defined, 5 used by the app
MISSING theme key: brls/separator (used in hg_sidebar_view.cpp)
FAIL  an unknown theme key calls fatal() in ThemeValues::getColor and kills the app
```

—— 也就是说，这个检查**本可以在装机前就挡住这次闪退**。还原后套件恢复全绿。

## 7. `build35` 的两处界面问题（用户实测反馈，`build36` 已修）

用户原话：「侧边栏**太厚了**，导致"更多"又出现在了**第二排**……在**历史记录的下面有一个设置界面**，
然后在**底部也有一个设置界面**，留下底部的那个」。

### 7.1 太厚 → 网格从 8 列掉到 7 列

日志给了确切的数字（build35 那次运行）：

```
HOMEGRID: layout #1 w=1112 COMPACT -> 7 columns, cell 145.1x0.0, contentH=2492
```

侧边栏 120 px（图标在左、文字在右），网格只剩 1112 px，`floor(1112/140) = 7` ——
而每一栏是"7 张卡 + 第 8 格更多"，**第 8 格就被挤到第二排**去了。

**修法**：把每一行改成 **图标在上、文字在下**（wiliwili 电视版自己的形状），
宽度 120 → **72**。算式：1232（1280 - 两侧 24 内边距）- 72 = **1160**，
`hg_grid_columns_for(1160, 140) = 8` ✅（只要 ≤112 px 都能成立，所以 72 不是卡在边界上）。
海报因此从 140 宽变成约 131 宽（同一排 8 张，风格不变），这是收窄必然的代价。

### 7.2 设置出现了两次

`SidebarView::rebuild` 里有两个循环，**第一个循环遍历了全部模型项**（包括 pinned 的"设置"），
第三个循环又在 spacer 之后把 pinned 的加了一遍 —— 于是"设置"画了两次，
一次在"历史"下面，一次在底部。

**修法**：抽出 `addRow(i)` 一处建行；第一个循环显式 `continue` 掉 pinned 项；
并把 `itemAt(index)` 从"数第几个可聚焦子视图"改成 `rebuild` 时填好的
**index → 视图**表（原来那个假设"绘制顺序 == 模型顺序"，正是它让重复项没被发现）。

## 9. `build36` 仍然挤掉一列 → 挪到顶部横排（`build37`）

用户原话：「**还是影响排版，更多还在第二排，把它放到顶部去，横排摆放**」。

收窄到 72 px 仍然不够：网格的列数是 `floor(宽度 / home.cellW)`，掌机 720p 下
`floor((1232-72)/140) = 8` —— 刚好卡在边界上，任何一点额外开销（内边距、间隔取整）
就会掉到 7。**只要它在左边占哪怕一个像素，就是在赌这个余量。**

**改法**：布局回到最简单的三段式 `COLUMN: [标题行] [横排栏] [网格]`，
栏本身 `Axis::ROW`、高 54 px、**宽度由父容器给满**（不再有 `WIDTH` 常量）。
横排栏**在水平方向不占网格任何宽度** → 网格重新拿到完整的 1232 px → 8 列、海报尺寸回到原来的 140。

随之而来的导航（仍然是框架自己在做，没有拦键、没有轮询）：

| 从哪 | 按什么 | 到哪 |
|---|---|---|
| 网格里 | 上 | 横排栏（因为栏就在网格上方，外层 COLUMN 盒会先遍历到它） |
| 横排栏里 | 左/右 | 栏内逐项 |
| 横排栏里 | 下 / 上 | 网格 / 标题行的"刷新"按钮 |
| 栏内第一项再往左 | — | 到头（抖动提示） |

条目形状也跟着横排：**图标在左、文字在右**（副标题在文字下面），
`设置`（pinned 组）由 spacer 推到**最右端**——原来"沉在底部"的语义改成"靠右"。

# 「每集开头跳回 0 秒」——根因与修复（build33）

**症状（交接-第19轮 §2.3）**：每集开始播约 3 秒 → 跳回 0 秒 → 重播，之后就正常。
**状态**：根因已定位、已修、已部署 `build33`（待真机确认）。

---

## 1. 证据：build32 的真机日志里有完整的一次

`out/console-log-build32.txt`（2026-10-10 11:05，用户实测那一轮）：

```
11:05:59  PLAYER: mpv started, plan = 360p 640x360  codec=bytevc1  CENC key derived
11:05:59  PLAYER setupMpv: loadfile rc=0 url=https://v5-se-ex-...        <- 第一次加载（正常）
11:06:00  SW draw #10: ... <-- FIRST FRAME WITH PICTURE CONTENT           <- 出画面
11:06:01  MPV: PLAYING   00:01 / 01:31
11:06:01  QUALITY: switching to '360p' (tier 4, source 0, 640x360)        <- ★ 切到"已经在播的"那一档
11:06:02  QUALITY: options rewritten ok (decryption rc=0, headers rc=0)
11:06:02  QUALITY: loadfile issued rc=0 url=https://v95-zjbjx-...         <- ★ 整条流重新加载
11:06:02  QUALITY: switched to '360p' -- now 360p 640x360
```

**起播到第二次 loadfile 是约 3 秒**，与用户描述的"播约 3 秒跳回 0 秒"完全吻合；而且
**"之后就正常"** 也对得上——这次多余的切换只发生一次（见下面 lastQualityIndex 的机制）。

---

## 2. 根因：清晰度菜单把"被播种的行"当成了"用户改了行"

菜单每帧有一段规则（`player_view.cpp` 菜单 tick 末尾）：

```cpp
if (this->menu.qualityCount > 0 && this->menu.qualityIndex != this->lastQualityIndex) {
    this->lastQualityIndex = this->menu.qualityIndex;
    this->switchQuality(this->menu.qualityIndex);       // 一次完整的重新加载
}
```

它问的是"**行里的索引**和**上一次为它下发过切换的索引**是否不同"，用来把一串按键折叠成一次请求。

而清晰度梯度（ladder）是**起播之后**才异步取回来的（`startQualityLadder` 有意放在播放已经开始之后，
"一个等菜单才出画面的播放器是把依赖装反了"）。回调里它做了一件事：

```cpp
self->menu.qualityCount = (int)tiers.size();
self->menu.qualityIndex = current < 0 ? 0 : current;   // current = 正在播的那一档
```

`current` 是按 `plan.quality_type` 匹配出来的**正在播放的那一档**（日志里是 tier 4），
但 **`lastQualityIndex` 仍然是初值 `-1`**，于是：

> 行的索引从 -1 变成 4 → 菜单 tick 认为"用户把行挪到了第 4 档" → `switchQuality(4)` →
> 重新取一次签名 plan（新的 URL、新的 CENC 密钥）→ `loadfile` → 画面回到 0。

**修复的第一半**：播种时同时写 `lastQualityIndex`，也就是把"这一行是播种来的，不是改来的"记下来。
`switchQuality` 里两条失败回滚路径早就把这两个字段一起写（为了同样的原因），**只有播种这条路漏了**。

**修复的第二半**（更重要，因为它不依赖"请求是怎么来的"）：

```cpp
if (impl->playingTierIndex == tierIndex) {
    hg::logPrintf("QUALITY: tier %d ('%s') is ALREADY playing -- not reloading the stream [build33]", ...);
    return;
}
```

切到**正在播的那一档**根本不是一次切换：要播的流已经在播了，代价却是一次新签名请求、一把新密钥和
一个跳回开头的画面。加了这道门之后，"同样的东西被重新加载"这件事**不可能再发生**，
不管是哪条路问过来的。

`playingTierIndex` 是**新加的独立状态**，只在这两个地方写：
ladder 回调里匹配上正在播的那一档时；切换的选项写入**被接受之后**。

**为什么不直接用 `impl->plan.quality_type`**（它看起来就够了）：`switchQuality` 在**选项写入之前**
就把 `impl->plan` 换成了新 plan（`player_view.cpp` 的 `impl->plan = plan;`），
所以一次**失败的**切换之后 `plan` 会声称一个并没有在播的档位——用它做这道门，
用户就会**没法重试同一档**。这是一个**独立的小瑕疵**，本轮只记录、没有改（它需要把 plan 的采纳
推迟到选项写入被接受之后），因为它不在本症状的路径上。

## 3. 一个诚实保留的疑点

**日志里没有 `PLAYER: quality ladder: ...` 这一行。** 那是播种回调的最后一条日志，
而 `menu.qualityCount > 0` 只能由那条回调设置（`qualityCount` 全项目只有这一处写），
所以回调一定跑过、那行日志一定执行过；可是在 `out/console-log-build32.txt` 里按字节搜
`quality ladder` 是 **-1（不存在）**，同一段时间里它周边的日志都在。

可能的解释是那次 `openAt(..., "a")`/写入失败（`hg_log.cpp` 的写失败是静默的），但**我没有证据**，
所以不写成结论。**这个疑点不影响修复**：第二半的门把它变成了"无论谁问、切同一档都不重载"。
`build33` 加了三行诊断日志，下一次真机日志会把这件事说清楚：

```
QUALITY: row seeded to tier 4 of 5 (playing tier 4) and marked as already applied -- no reload is issued for it [build33]
QUALITY: tier 4 ('360p') is ALREADY playing -- not reloading the stream [build33]      <- 若仍有人问
QUALITY: the menu row moved -- index 4 (last issued -1, 5 tiers, playing tier 4) [build33]  <- 若仍发生切换
```

第三行特意打了四个数字：**行的索引、上次下发过的索引、梯度档数、播放器认为在播的档**。
如果下次还出现多余的加载，这一行会直接说明是谁把行挪动的。

1. **随便点开一集看开头 5 秒**：画面应当**不再跳回 0 秒**、不再重播。

## 5. 为什么这一条没有主机测试

本轮改的是**视图层里的状态同步**（哪个索引被当成"用户改的"），不是可离线验证的算术，
而主机套件只覆盖 `app/src` 的纯 C 层。它的验证方式是上面那三条日志与真机行为——
这也是这一轮先加日志再改的原因（项目规矩 §4.6）。

arithmetic 那一半（"哪一行是正在播的档"的匹配）确实有三处重复，理论上可以抽到 `hg_quality.c` 里去测，
但那需要在 `std::vector<Client::QualityTier>` 和 `HgQualityTier` 之间转换，三处调用都要加转换代码，
**净增代码而不是净减**，所以本轮不做。

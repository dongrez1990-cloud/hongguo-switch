# 第 93 轮：按排加载封面、可见性只在变化时写、以及大气层那两次崩溃（build93）

你报了两件事：**大气层崩了两次** ✗、**封面不按排加载** ✗。这一轮两件都有明确结论。

---

## 一、封面"第二排没完就跳第三排" = **落地顺序 = 网络完成顺序**

你观察得很准 ✓：它一次请求了 **11 个** ✓，然后第二排还没填满就开始填第三排 ✓。
原因是我这套逻辑**每轮把所有格子都问一遍** ✗ → 抓取名额被"循环先扫到的格子"占满 ✓，
而**哪一张先显示**取决于**哪一张先下载完** ✓（网络快慢决定 ✓）→
于是第三排里一张快的封面，会插在第二排一张慢的封面前面 ✓✓。

**改成一次只请求一排** ✓✓（正是你要的）：

```
找到"第一个还有缺封面的排" → 只请求这一排的 8 个格子
后排的格子保持深色占位，等这一排到齐（或都被拒绝）才轮到它们
```

排的划分用的是**网格自己的列数**（`hg_grid_layout` 算的、有主机测试 ✓），
所以"排在哪里结束"只有一种说法 ✓，不存在第二套判断 ✓。
日志会写：`HOMEGRID: cover retry pass 3 -> ROW 1 only (8 cells asked; later rows wait for this one, at the user's request)` ✓。

## 二、大气层那两次崩溃 = **触摸滚动路径内的野指针**

崩溃报告（`01791694647`）与之前所有崩溃**完全不同** ✓：

```
Result 0x2A8  (Instruction Abort)
  ← std::string::_M_construct                ← 在构造字符串
  ← brls::Event<brls::View*>::fire
  ← ScrollingFrame 的 PanGestureStatus lambda  ← 触摸拖动
  ← ScrollGestureRecognizer::recognitionLoop
```

`Instruction Abort` ＋ 在构造字符串时崩溃 = **指针已经无效** ✓，不是算错 ✓。
而最可疑的正是**我上一轮加进去的剔除** ✓：它**每帧对每个格子调 `setVisibility`** ✗，
而 borealis 的 `setVisibility` 不是单纯一个标志位 ✓（它会**让布局失效**、可能把视图**加入/移出焦点链** ✓），
同时触摸拖动时框架又在调 `Application::giveFocus(this)` ✓ → 两边同时改焦点相关状态 ✓ → 很容易出这种崩 ✓。

**修法**：**只在真的需要变化时才写可见性** ✓✓ —— 先读 `getVisibility()`，相同就什么都不做 ✓。
稳定画面上现在**每帧零次写入** ✓（原来是每格一次 ✗）。

> 说明白一点：**我没有证据能把这次崩溃 100% 归到这一处** ✗（崩溃报告被扰动过 ✓），
> 但它是唯一由我在崩溃前引入的、且在触摸滚动路径上的改动 ✓，
> 所以先把它的"每帧写入"消掉 ✓ —— 这是当前最有价值的一刀 ✓。若再出现，我会撤掉整个剔除 ✓（那也会同时撤掉它的性能收益 ✓）。

## 三、顺带优化：上传间隔 120 → 60 ms

你要的"还需要优化" ✓：`HG_IMAGE_INSTALL_GAP_MS` 从 **120 ms 降到 60 ms** ✓
（= 每秒最多 16 张 ✓，且仍是"一张一张落地" ✓，不会回到一次性爆发 ✗）。
它当初设 120 ms 是为了压住 `BlitCopyEngine` 那类命令内存耗尽 ✓，而那个问题现在还有**屏幕外不画**兜着 ✓，所以降到 60 ms 是安全的 ✓。

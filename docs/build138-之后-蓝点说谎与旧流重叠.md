## 二、定性（第 2 条证据最强，且能解释一大半）

### (a) 蓝点在说谎 —— `playingTierIndex` 的播种会落到 0

播种逻辑（`player_view.cpp`，阶梯到达时）：把**计划里的 `quality_type`** 到阶梯里**匹配** ✓；
阶梯是 **`hg_quality_build` 排序过的最优在前** ✓（`hg_quality_test` 断言 `t[0] = 1080p` ✓）。

`build136` 撤掉后（`build138` 回到 build135 行为 ✓），**开局不再按记忆档选源** ✓ →
计划取的是**上游第一档（常为 360p）** ✓；而播种**匹配失败**时会落到 **index 0** ✗ →
**`playingTierIndex = 0` = 1080p** ✗✓ → **菜单显示 1080P（蓝点），实际是 360P** ✓✓ = 用户原话 ✓。

**结论**：这是**状态显示错误** ✓，不是"切到了 1080p" ✓；但它会让用户以为切档无效 ✓，并可能诱发重复切档 ✗。

### (b) "听到别的声音" + 很卡 —— 换集时旧流没有干净地停下

切集（ZR）走 `startEpisode()` ✓，而它**复用同一个播放器** ✓（`player_activity.cpp` 注释原文：
"starting one means asking the view to fetch a fresh play plan" ✓）→ 于是是**再发一次 loadfile** ✓。
mpv 的音频输出缓冲不会在 loadfile 的瞬间清空 ✗ → **旧声音仍可能响一小段** ✓；
若新流卡在缓冲/重连 ✓，这段"重叠"就被听到 ✓，同时**卡顿** ✓。

## 三、下一轮的做法（按顺序，每步都能单独验证 ✓）

## 四、可选：让"默认 1080P"与"更快开局"两者兼得 ✓

`build136` 的做法（先取阶梯再 loadfile ✓）能给 1080P ✓ 但多一次往返 → 灰屏更长 ✗；
`build138` 回到一次请求 ✓ 但默认 360P ✗。
**兼得办法**：**缓存阶梯** ✓ —— 同一部剧的阶梯在上次取过后**留在内存** ✓（或落盘 ✓），
下一集**直接用缓存** ✓ → 零额外往返 ✓✓ 且能开局选对档 ✓✓。
这是下一轮之后最有价值的一步 ✓（用户明确要"1080P 持续观看" ✓）。

## 一、为什么这一步是「勘察」而不是「实现」

第 5 步交付的拖动预览显示**目标时间**而不是画面，理由写在 `可拖动进度条-步骤5.md` §二：
要画面就得**本地抓帧**，有两条路：

| 路线 | 代价与风险 |
|---|---|
| 1. mpv `screenshot-raw` | 一条命令 |
| 2. **第二个软件渲染上下文** | 同 mpv 句柄开两个 context **这里没人验证过**，失败的样子是**黑屏** |

当时**把路线 1 排除掉**，依据是一句话：

> "screenshot-raw 需要可用的 VO，而 libmpv 的渲染 API 没有。"

**那是读文档得出的结论，不是测量。** 而且文档并不一致：手册自己的 caveat 讲的是
**D3D11 上的颜色**问题；能查到的最接近权威的讨论是一个长期存在的抱怨帖
（[mpv-player/mpv#5128](https://github.com/mpv-player/mpv/issues/5128#issue-151778)）。
**两者都不能为"这一个构建"下结论。**

所以在**猜第三次之前先测一次**。这一步交付的是**证据**，不是缩略图功能：

- `player.shotprobe=yes` → 播放开始后 mpv 被问一次，答案写进 `hongguo.log`；
- 成本：**一帧的渲染 + 一行日志**；
- 产出：决定缩略图是"一条命令之遥"还是"必须走路线 2"。

## 二、探针怎么做的，以及为什么是 `mpv_command_ret`

```c
const char* args[] = {"screenshot-raw", nullptr};
mpv_command_ret(mpv, args, &result);      // 阻塞，直到回复到达
```

**在线程上跑，不在渲染线程上。** 它放在取 plan 的那个工作线程里（请求已经完成，
再跑这个不耽误用户等待的任何东西），而且**在播放已经起来之后**——早于有帧可抓的时刻去问，
测到的是错的东西。

`mpv_command_ret` **阻塞到回复到达**，这对这个线程正确、对渲染线程就是**卡住帧循环**。
这恰恰也说明了**为什么它不能用来做实时缩略图**：一个会卡住帧循环的预览是预览的反面。
**如果探针说可以**，缩略图的正确路径是 `mpv_command_async` + 在 `drainMpvEvents` 里接
`MPV_EVENT_COMMAND_REPLY`——那是另一块有自己线程问题的工作，探针只负责决定**那块工作值不值得做**。

回复是一个 `mpv_node` 树，读四个字段**不需要 JSON**。`hg_shot` 的文本解析器是给
**另一种形状**用的（控制台测试与主机套件），两者各自覆盖自己能覆盖的那一半。

## 三、`hg_shot` 里真正被测的是什么

36 项主机测试，其中**最重要的一条是"不要谎报成功"**：

**`data` 的长度与它自己的 `w`/`h`/`stride` 矛盾时，必须判为失败。**
一个 stride 错的帧画出来是**斜的**——而那看起来像 nanovg 的渲染 bug，不像回复坏了。
**在这里谎报成功会让整个缩略图功能走错路**（去写一条其实不能用的抓帧路径）。

另外三条也是刻意的：

- **"不是对象"、"字段缺失"、"字段互相矛盾"是三个不同的判定**——它们指向三种不同的下一步；
- **空的 `data` 数组不等于格式错误**——mpv 完全可能合法地答"没有像素"，
  这是与"解析器读不懂"不同的事实；
- **`strange_colors` 单独一个判定**——它会让**每个像素都错**而不是缺失，与"没有帧"是不同的问题。

## 五、观察点

在 `hongguo.cfg` 里加一行 `player.shotprobe=yes`，进播放页，然后**取日志**：

**路线 1 可用时**：

```
SHOT: probing screenshot-raw (player.shotprobe=yes)
SHOT: 1920x1080 format=bgr0 stride=0 data=8294400 bytes (declared 8294400) -- OK -- a usable frame came back
SHOT: VERDICT -- screenshot-raw WORKS under this render configuration. A progress-bar thumbnail can be captured with mpv_command_async + MPV_EVENT_COMMAND_REPLY; the second render context is not needed.
```

**路线 1 不可用时**（三种，指向不同的下一步）：

```
SHOT: mpv_command_ret failed rc=-4 (property unavailable)
SHOT: VERDICT -- screenshot-raw does NOT give a usable frame here (...)  -> 走路线 2
```

```
SHOT: 1920x1080 format=bgr0 stride=0 data=0 bytes (declared 8294400) missing='' -- the reply's data does not match its own w/h/stride
```
（命令"成功"了但内容是空的——这正是**最需要这个探针**的一种情况。）

```
SHOT: 0x0 format=bgr0 data=0 bytes (declared 0) -- the reply describes a 0x0 image
```
（命令被接受了、什么都没渲染——这是**反对**路线 1 的证据，不是支持。）

判读：

| 现象 | 结论 |
|---|---|
| 完全没有 `SHOT:` 行 | `player.shotprobe` 没写对，或 mpv 没起来 |
| `rc=-4 (property unavailable)` | 这就是"需要可用 VO"那条读文档结论的**实测版本** → 走路线 2 |
| `VERDICT -- ... WORKS` | 缩略图是**一条命令之遥**：写 `mpv_command_async` + 命令回复事件即可 |
| 有 `SHOT:` 但没有 `VERDICT` | 说明在解析或日志中途出了问题——把原始行发我 |

## 七、这次"先测再说"避免掉的是什么

如果按第 5 步的判断直接去写**第二个软件渲染上下文**，可能发生的是：

- 最好的情况：能用，但白写了；
- 最坏的情况：**把本来正常的视频渲染搞黑屏**，而且因为没法在构建机上验证，
  排查要靠用户来回描述屏幕——而这个项目已经为"看不见屏幕"付过代价。

**一帧 + 一行日志**换掉这个风险，是这一步的全部理由。

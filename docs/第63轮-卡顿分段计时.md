# 第 63 轮：给卡顿**先量再修**（I2 的分段计时）（build63）

上一轮找到了"主机模式下软件表面比画面大 2.25 倍"这条杠杆。但那只说明**工作量大**，
没说清**时间花在哪一段**：

1. mpv 的 CPU 色彩转换与缩放（`mpv_render_context_render`）
2. 整块表面的纹理上传（`nvgUpdateImage`）
3. 其余（nanovg 绘制、框架、vsync 等待）

**在不知道这个之前做优化就是猜** —— 而这个项目的规矩是：关于硬件的断言必须有数字。

---

## 一、做法：每帧读三次时钟，每秒汇总一行

```cpp
const double tRender0 = nowMs();
mpv_render_context_render(...);          // 1. mpv 的软件渲染
this->frameRenderMs += nowMs() - tRender0;

const double tUpload0 = nowMs();
nvgUpdateImage(vg, image, pixels);       // 2. 整块上传
this->frameUploadMs += nowMs() - tUpload0;
```

每秒打印一次（`brls::getCPUTimeUsec()`，不是系统调用，可以长期留着）：

```
PLAYER timing: 29.8 fps | mpv_sw=22.4 ms/frame | upload=6.1 ms/frame | other=4.7 ms/frame | surface=1920x1080 [build63]
```

这一行同时给出**帧率**、**三段耗时**和**表面尺寸**，所以下一次真机运行就是答案 ——
不用再靠"看起来卡"来判断。

## 二、怎么读这一行（写给下一次的我自己和用户）

| 观察 | 结论 | 下一步 |
|---|---|---|
| `mpv_sw` 最大 | 瓶颈在 mpv 的 CPU 转换/缩放 | `player.sw.height=720` 会**直接**减小它（像素少 2.25 倍）；还不够就 `540` |
| `upload` 最大 | 瓶颈在**上传带宽** | 换上传格式（RGB565 减半）或只在画面变化时上传 |
| `other` 最大 | 瓶颈不在视频路径 | 查框架/叠加层（控制条、封面） |
| `fps` 明显低于 30 而三段都很小 | 等待（vsync/调度） | `app.fps.limit` 与 `app.fps.show` 配合看 |

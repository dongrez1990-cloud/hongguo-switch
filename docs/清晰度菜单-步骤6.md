## 一、先测量，再动手

动手前先量了真实响应（`app/src/tests/fixtures/video_model.json`）：

| `quality_type` | `definition` | `vwidth × vheight` |
|---|---|---|
| 40 | 360p | 640×360 |
| 30 | 480p | 854×480 |
| 20 | 540p | 1024×576 |
| 10 | 720p | 1280×720 |
| **1** | **1080p** | **1920×1080** |

**五档齐全，而且顺序和直觉相反**：数字**最小**的是**最高**画质，`quality_type` 永远不送 0，
而**上游是"最差在前"发的**（40 在 entry 0，1 在 entry 4）。

所以任何**按 `quality_type` 升序排**的菜单都会**把 360p 放在最前面并称它为最好**——
它看起来完全像一个能用的菜单，而且是错的。这是这一步最大的坑，也是 `hg_quality.c`
存在的理由：它的 43 项主机测试**就是用这五行真实数据驱动的**。

---

## 二、做了什么

X 面板多了 **Quality** 一行（在 Hue 之后、Aspect 之前）：

- 面板打开时若梯子已到，行上显示**真实档位名**（`540p`），不是 `3 of 5`；
- 梯子还没到时显示 `(not available)`——**空菜单和错菜单长得一样**，除非行自己说清是哪种；
- ←/→ **循环**切换（和 Aspect 一样；两端做成死键会让菜单读起来像坏了）；
- 改一次档 = **重新取一次 video model + 一次 `loadfile`**。

**mpv 不拆不重建**：渲染上下文、fence、framebuffer 交接是这个播放器最难做对的部分，
换清晰度没理由碰它们。**会变的是 CENC 密钥**，所以密钥是**重写**而不是沿用——
不同档位是不同的流、有自己的密钥，沿用旧密钥的结果是**没画面且没错误**。

响应**重新取而不是缓存**：URL 是签名的、有时效，缓存的 plan 几分钟后就是错的东西。

## 三、四个刻意的决定

1. **按像素高度排，不按 `quality_type`**。`quality_type` 的方向是上游约定、随时可能变；
   而"更高的画面是更好的画面"按定义成立。高度相同时用码率，两者都相同则**保持上游顺序**
   （稳定排序），这样菜单不会在两次运行之间莫名换位。

2. **梯子在播放开始之后才取**，用独立 worker。**让播放器等菜单是把依赖关系搞反了**。
   取失败只是没有菜单——**不会让正在播的视频停下**。

3. **切换失败是可存活的**：旧流还在播，只是档位没变。通知 + 日志 + **把菜单行拨回实际
   在播的档位**，而不是把这个请求的失败升级成拆掉播放器。

4. **改了 `hg_play`**：`hg_play_model_inner()` 被抽出来公开。原先
   `hg_play_plan_from_model` 自己走一遍"双重编码信封"的解包，而清晰度梯子需要
   **整份源码列表**（plan 只挑一个、其余丢掉——对"播这一集"正确，对"提供其他档位"无用）。
   两份解析逻辑就是两处等下一个修复只改一半，而这段逻辑**已经错过一次**
   （它曾在顶层找 `video_list`，那里永远找不到）。

## 五、观察点

**屏幕**：X 面板第 6 行是 Quality，右侧显示 `1080p`（或当前档位）；按 ←/→ 档位名变化，
画面在 1–2 秒后按新档位重新加载。

**日志**：

```
PLAYER: quality ladder: 1080p > 720p > 540p > 480p > 360p  (playing tier 0)
QUALITY: switching to '540p' (tier 2, source 2, 1024x576)
QUALITY: options rewritten (decryption rc=0, headers rc=0)
QUALITY: loadfile rc=0 url=https://...
QUALITY: mpv reports path=https://...          <- 回读：真正打开的是哪条流
QUALITY: switched to '540p' -- now 540p 1024x576 codec=h264 CENC key derived
```

判读：

| 现象 | 结论 |
|---|---|
| `quality ladder: ... > ...` 顺序**不是**从 1080p 开始 | **排序 bug**——这是 `hg_quality` 测试覆盖的正是这一条 |
| `quality ladder failed '...'` | 梯子取不到（网络或接口），**播放不受影响**，菜单该行保持不可用 |
| `(not available)` 一直不消失 | 同上；看有没有 `quality ladder:` 那行 |
| `loadfile rc=0` 但 `mpv reports path=` 还是旧 URL | 命令被接受但没生效——这正是回读存在的理由 |
| `switch ... FAILED ... still playing the old tier` | 取新档位失败，旧流继续；菜单行已拨回实际档位 |
| `a switch is already in flight` | 连按太快，第二次被挡（防止两个请求抢结果） |
| `options rewritten ok` 之后**画面没换** | 看 `QUALITY: demuxer-lavf-o set rc=…, readback rc=… matches=1/0` 那一行：**`matches=0` 就是"mpv 没接受新值"**（该行会自己说明后果）。`matches=1` 而画面仍未换，才说明是"写进去了但没生效"——**那一种只能靠眼睛**。另见 `代码审查-第13轮.md` §三 |
| `mpv refused the rewritten options` | 选项写入被拒 → **已中止切换**（第 13 轮审查修复），旧流继续播，不走"用旧密钥开新流"的黑屏路径 |

## 七、主机测试抓到的又一个真问题

`hg_quality_build()` 第一版**先按 `cap` 截断、再排序**。`cap` 小于供给数时，
它保留的是**上游先发的那 `cap` 条**——而上游先发最差的（40 = 360p 是 entry 0）。
所以 `cap=3` 会给出 360p / 480p / 540p 并把 **360p 当成最好的档位**。
测试抓到（"keeps the BEST three"），屏幕上看不出来。

改成**先排序、后截断**，`work` 数组按 `HG_QUALITY_MAX` 定尺寸（正是 `hg_api.h` 已有的上限）。

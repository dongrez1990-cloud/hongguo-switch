# 第 5 步：可拖动进度条（+ 预览读数）

交接文档 §二 的第 5 步。**代码已完成、已构建已部署、未上机。**

---

## 一、做了什么

按住 **←/→**（粗调用 **LB/RB**）不再让视频实时跟着走，而是**在进度条上拖动一个目标点**：

- 进度条上出现**白色圆点光标**跟着你的拖动走；
- 上方浮出**预览面板**，大字显示**目标时间 / 总时长**；
- 松手时发出**一次** `seek <秒> absolute`；
- 拖动期间时间行从 `PLAYING 1:23 / 45:00` 变成 `SEEK 12:30 / 45:00`。

### 为什么改成"拖动"而不是继续用相对 seek

原来的实现是**按住即实时相对 seek**（每帧一条 `seek ±N relative`，带加速曲线）。它能用，但有两个真问题：

1. **它无法预览任何东西**。相对 seek **没有目标**——目标就是"最后停在哪"——所以没有任何东西可以显示。wiliwili 的滑杆不是这样：拖动设定一个**点**，条上画出那个点，松手时才 seek
   （`video_progress_slider.hpp`：拖动中 `progressEvent`，松手 `progressSetEvent`）。
2. **每一个中间位置都要解码**。在两小时的视频上以 60 s/s 的速度按住 → 拖动期间 mpv 每帧解一个 GOP。这是这个播放器能被要求做的最贵的事，而除了最后那个位置**全部被丢掉**。

所以现在：一次拖动 = **一条命令**，而且条上显示的就是它要落到的位置。

## 二、预览是「时间读数」，不是「画面缩略图」—— 这是一个实测限制，不是偷懒

wiliwili 的缩略图预览**画面来自服务端**：它的 `VideoSnapshotCore` 消费一个描述
**精灵图（sprite sheet）**的 `VideoSnapshotData`（`view/video_snapshot_core.hpp`）。
**这个服务不提供任何这类数据**——视频模型里只有 URL 和 CENC 密钥。

要在这里显示画面，只能**本地抓帧**，有两条路，各自都是独立的一块工作：

| 路线 | 代价与风险 |
|---|---|
| mpv `screenshot-raw` | 在目标位置**再解一次码**，返回一大块像素缓冲，再上传成 nvg 纹理 |
| **第二个软件渲染上下文** | 用 `MPV_RENDER_API_TYPE_SW` 渲到小块 RGBA 缓冲直接当缩略图。本 App **已有软件路径**（`renderer=sw`），所以这条更有希望——但**同一个 mpv 句柄上开两个 render context 是这里没人验证过的配置**，而它失败的样子是**黑屏** |

**所以这一步交付的是"预览之所以有用"的那部分：你即将落到的时间，大到拖动时能看清。**
比"差一点就做完"、但塞进一个**本轮无法上机验证**的第二个渲染上下文要好。
写在这里是为了让这个缺口是**记录在案的决定**，而不是疏忽——这是本项目对"暂时不做"的规矩。

> **第 13 轮补充：这个判断的依据被换成了一次实测。**
> 上面 §二 排除路线 1（`screenshot-raw`）用的是**读文档**得出的结论，而且文档并不一致——
> 手册自己的 caveat 讲的是 D3D11 的颜色，能查到的最接近权威的讨论是一个长期存在的抱怨帖
> （[mpv-player/mpv#5128](https://github.com/mpv-player/mpv/issues/5128#issue-151778)）。
> 现在有了 `player.shotprobe=yes`：**一帧 + 一行日志**就能让主机回答
> "在这个渲染配置下 `screenshot-raw` 到底能不能给出可用的帧"。见 `缩略图管线勘察.md`。
>
> 结论仍然未知，但**它不再是一个需要猜的问题**：
> `SHOT: VERDICT -- ... WORKS` → 缩略图是一条命令之遥；
> `SHOT: VERDICT -- ... does NOT ...` → 才去写路线 2。

## 三、退路（不用重编译）

| 退路 | 效果 |
|---|---|
| `player.scrub=live` | **回到原来的实时相对 seek**——那是真机验证过的行为，也是最便宜的回路 |
| 不按 ←/→ | 进度条一切照旧，只是多了个光标概念（不拖就不出现） |

两条路子是**互斥**的，而且这一点在**一个地方**强制执行（`const bool dragArm` 同时控制两条分支），
不是各自内部加标志位：两个都跑的话，一次按键会同时移动目标**并且**发出相对 seek，两者会抢位置。

## 四、观察点

**屏幕**：播放中按住 →（右），进度条上出现白点向右移动，上方浮出黑色小块显示目标时间，
标题行变 `SEEK …`；松手后画面跳到那个位置，时间行变回 `PLAYING`。

**日志**：

```
SCRUB: drag begin at 83.4 s of 2700 s (dir +1)
SCRUB: direction reversed, ramp restarted                 （中途反向时才出现）
SCRUB: drag end at 412.0 s -> committing an absolute seek
PLAYER seekAbsolute: seek 412.0 absolute -> request 0
PLAYER seekAbsolute: time-pos is now 411.93 (asked for 412.0)
```

判读：

| 现象 | 结论 |
|---|---|
| `cannot drag -- duration is 0` | mpv 还没报出时长（刚 load），再按一次即可——**不是 bug** |
| `drag end with no movement -- no seek issued` | 按了一下没拖——这正是**故意**的：seek 到当前位置会让 mpv 重新加载整个流 |
| `seek … -> request 0` 但 `time-pos` 没变 | 命令被接受但没生效（边界/还没解出帧）——这正是回读存在的理由 |
| 条上的点会动但松手不跳 | 看有没有 `drag end … committing`——有则是 mpv 侧，没有则是按键边沿判定 |

## 五、主机测试抓到的两个真问题

### 1. 把「秒」加进了「比例」字段

`hg_scrub.c` 第一版：`pos` 存的是**比例**（0..1），而 `hg_scrub_step` 收到的是**秒**。
`0.1 + 60` 是一个完全合法的 double，它只是**没有意义**——测试第三条就抓到了
（"the target moved by 60 s of 6000"）。现在状态**全程是秒**，
唯一存在比例的地方是两个条几何函数（因为"条上的位置"本来就是比例）。

### 2. TinyCC 的 `snprintf` 截断时返回 −1 且不写终止符

实测（这正是主机测试用的编译器）：

```c
char b[4]; snprintf(b, 4, "%d:%02d:%02d", 1, 1, 1);
// 写入 "1:01"（4 字节，没有终止符），返回 -1
```

C99 要求返回"本应写入的长度"**并**终止缓冲。所以 `hg_scrub_format_time` 不再依赖它：
先格式化进私有缓冲，再用**自己的**边界拷贝，返回值也是它自己数的长度。
这个坑在这个项目里已经踩过第二次（第一次在 `hg_pmenu`），现在两处都注释了。

## 六、顺带修掉的一个绘制顺序问题

进度条原本画在**视频渲染之前**。它在软件路径下能看见，是因为**软件路径的视频本身就是一个 nvg 图像**、画在稍后，两者在**同一批**记录里，后画的赢。
一个浮在画面上的**预览面板**就不一样了：nanovg 只**记录**命令（`nvgEndFrame` 统一提交），
而 mpv 是在它自己的渲染调用里**立刻**把命令推进 deko3d 队列——
所以**在那之前记录的一切都会被画面盖住**。

现在进度条、光标、预览都画在**视频渲染之后**，两条渲染路径上都正确。

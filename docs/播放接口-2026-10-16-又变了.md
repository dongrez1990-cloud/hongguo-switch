## 2. 这不是我们的 bug —— 有对照实验

用**参考实现自己的签名器**（`_dl/hongguoTV-main/server/vendor/hongguo.cjs`）从 PC 上直接打：

| 请求 | 结果 |
|---|---|
| `POST /novel/player/video_model/v1/` 有签名 | **200 + 0 字节** |
| 同上，**完全没有签名头** | **200 + 0 字节**（一模一样） |
| 同上，**故意改坏 x-gorgon** | **200 + 0 字节**（一模一样） |
| `POST /novel/player/multi_video_model/v1/`（旧路） | 200 + 117 字节 `{"Code":110001,"Message":"未知异常"}` |
| `POST /novel/player/video_detail/v1/` `{"series_id":"<字符串>"}` | **200 + 58 KB 真数据** ✓ |
| `POST /novel/player/multi_video_detail/preload/v1/` | **200 + 58 KB 真数据** ✓ |
| `/novel/player/video_model/preload/v1`、`/novel/player/play/v1/` 等 | **404 Page not found** |

⇒ **`video_model` 这条路对任何人、任何签名、任何参数、任何 id、两个 host 都回同一个空 body** ⇒
**它被退役成 stub 了**（和旧 multi 路现在回 110001 兜底是同一件事）。**换参数救不回来。**
⇒ 另外两条 `video_detail` 路由**活着**，而且 `video_detail` **完全不做签名校验**（无签名/坏签名照样给 58 KB）。

**上游也没跟上**：`N3urda/hongguoTV` 最后推送 2026-09-24、`zhenyong97/hongguo-downloader` 09-24、
`zhangbaio/hongguo` 07-14 —— **都在这次服务端变化之前**，所以没有现成答案可抄。

## 3. 替代方案（从**活的网页客户端**里读出来的，已实测成功）

网页播放页 `https://hongguoduanju.com/player/<series_id>/<vid>` 今天仍然 200，且带
`loaderData[..].protectedPlayback = true`。它加载的 bundle 里写得很清楚：

```js
l = axios.create({ timeout: 5000,
    headers: { "X-Xs-From-Web": "1", "Content-Type": "application/json" }, params: { aid: 8662 } });
...
t = { series_id: e, item_id: n, definition: "720p" };
s({ url: "/api/video/protected/play-info", method: "POST", params: {}, body: t },
  { domain: window.location.origin });
// 失败分支：response.status==502 && data.error=='encrypted_resource_unavailable'
//   -> PROTECTED_ENCRYPTED_RESOURCE_UNAVAILABLE，否则 PROTECTED_PLAYBACK_UNAVAILABLE
```

**实测（本机，2026-10-16 01:12）**：

**要点**：
- **不需要任何签名**（没有 `x-gorgon`/`x-argus`/`x-ladon`…），只要 `X-Xs-From-Web: 1` 和 `aid=8662`；
- `item_id` 是 **`vid`**（详情响应 `video_data.video_list[].vid`，也正是网页播放页 URL 里的那个）；
- 返回是 **DASH 的视频/音频两路**（各自带 `init_range`/`index_range`）+ `kid` + `player_access_key`（CENC 密钥材料）；
- `definition` 可调（网页用 `720p`；我们默认 1080P ⇒ 试 `1080p`/`1080p+`）。

## 4. 要改什么（下一轮）

1. `hg_request.c`：把"取播放地址"换成 **网页那条**（新 host `hongguoduanju.com` + 新 body + 新头），**保留**旧路的代码路径不做改动以便对照；
2. `hg_play.c`：新增一个**解 `play_info` 信封**的解析（现有 `unwrapModel` 处理的是旧的 `video_model` 信封）；
3. **待验证的关键点**：返回的是**DASH 视频+音频两路**，而 mpv 现在喂的是**单个 URL**。
   要么（a）让 mpv 同时吃两路（或合成一个 DASH manifest），要么（b）确认某个 `definition` 会返回**渐进式 mp4**（网页自身的 `player.be6c1b8992.js` 里有 `/video/public/<vid>/360p.mp4` 这条公开兜底路径，值得一并测）。
   **这一点必须先量清楚再动播放器代码。**
4. 判据：`play_info` 的 `expires_at` 到了会失效 ⇒ 这正是 build171 那个"自动换新地址"要覆盖的场景，改完之后它**终于有东西可换了**。

## 5. 复现用的脚本（都在 `_probe\`）

| 脚本 | 作用 |
|---|---|
| `vm-routes.mjs` | 扫路由 × 请求体，给出 404/兜底/活着 三分类 |
| `vm-sweep-vm.mjs` | 扫 model 请求的 host × 参数组合（证明都无法唤醒它） |
| `vm-detail.mjs` | 问活的 detail 路由要什么参数（`series_id` **必须是字符串**，数字会被 400 拒） |
| `vm-inspect-detail.mjs` / `vm-dump-entry.mjs` | 摊开 detail 响应，证明里面**没有**播放地址 |
| `vm-sig.mjs` | 有签名/无签名/坏签名对照（证明 detail 不校验签名、model 对谁都回空） |
| `vm-routes2.mjs` | 候选新路由发现（找到 `multi_video_detail/preload/v1` 是活的） |
| **`web-playinfo-live.mjs`** | **直接打网页的 play-info 并打印结果 —— 修复的验收脚本** |
| `web-playinfo-code2.mjs` | 从当前 bundle 里挖出这段代码（bundle 名字带哈希、会变，所以要重取页面） |
| `web-bundle-play.mjs` | 扫全部 chunk，找播放相关字符串 |
| `gh-check.mjs` | 查上游仓库有没有同步更新（结论：没有） |
